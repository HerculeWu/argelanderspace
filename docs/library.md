# 文库、身份与正文获取

状态：现行，包含 Stage 13 手动建条目、Stage 15 LaTeX arXiv 获取及后续 Web arXiv PDF 获取语义。来源：`46093915` 的旧 product-and-architecture、contracts-and-decisions，以及 Stage 13/15 inbox；原文索引见 [history](history.md)。领域定义见 [CONTEXT](../CONTEXT.md)，冻结和用户数据保护见 [contracts](contracts.md)。

## Work 与 Doc 的身份

- work id：`doi:` / `arxiv:` 等；canonicalId 优先级 doi > arxiv > openalex > title-slug。用于 search/note/label 等文献管理。
- doc id：`arxiv-…` / 本地 `latex-…` / LaTeX zip 上传 `upload-…`；用于 read/show/ref/list/annot 与阅读器。`search` 行的 `doc_ids` 映射正文。
- LaTeX Doc 经身份归并可被多个 Work 引用；**本地 PDF Doc 恰好属于一个 Work**，归属权威仅为 Library `doc_ids`。主 Doc 为 **`doc_ids[0]`**；主位是用户选择，不是发表稿或最新版本判定。
- `ingest` 只写 output；**随后必须 `library build`** 才成为可 search/note/label 的 Work。docless Work 也可来自 bib 导入、历史 graph-node 或 DOI 建条目。
- CLI 支持 arXiv id/URL、本地 `.tex`、目录和 tarball。Web 的 Work 内正文入口包括 LaTeX zip attach、本地 PDF 上传和 arXiv PDF 获取；均要求 Work 已存在。**局部修订（2026-10-12，用户论证图第四轮 Q3；见 [argument-graph](argument-graph.md)「CLI」）**：旧定位是本地 PDF Doc 完全不经 CLI/agent 接口暴露；新结论是 CLI 只提供只读的 `pdf-path <docId>`，输出 PDF Doc 原件 `original.pdf` 的绝对路径，由 Claude Code 自己读文件；CLI 仍不读取、不输出 PDF 文字或页面，也不上传、获取、删除 PDF。范围仅限外部 agent 整理论证图等阅读用途、只需支持 Claude Code；原因是用户希望外部 agent 能读到论文原文。PDF Doc 在 server 与 Reader 里的规则（唯一归属、hash 绑定、标注与阅读位置 sidecar）不变；`pdf-path` 本身不核对唯一归属，也不核对原件 hash（与 Reader 的原件端点不同，沿用既有 CLI `read` / `show` 的直读信任模型）。
- CLI 可解析 DOI 建 docless Work：DOI、`doi:` 或 URL 路径明确携带 DOI；Crossref 立即富化，失败留裸条目，重复 DOI 不写盘、不 rebuild。不可解析 DOI 的出版商 URL 或裸字符串仍报错，不能声称任意 URL 都能建条目。`10.48550/arXiv.*` 回 arXiv LaTeX 管线。

## 上传、多 Doc 与主位

所有 Work 都可上传。zip docId 为 `upload-<slug44>-<workId sha1前6>`，只随 Work 身份变化；同 Work 重传覆盖同一 upload Doc。向已有 arXiv/local 正文的 Work 上传会增加独立 upload Doc 并设主，旧 Doc 保留回看，UI 可“设为主”。

上传身份焊死：有 doi/arxiv 则 stamp source，没有则以 work.title 覆盖 doc meta.title，随后直挂 `doc_ids` 并校验；不能按失配标题挂到另一 Work。主位在 lockedRebuild 后锁内 re-assert，防并发 PATCH 覆盖；已有 library 的 seed dst-first 保序。

已有库 rebuild 保序不等于主位独立持久化：library 丢失后从零 rebuild 等残余问题仍由本地 I006 跟踪。本次 PDF 能力没有修复该存量边界。

### 本地 PDF（Web）

- `POST /api/library/upload-pdf?id=<work-id>` 接收原始 PDF bytes，可信服务端 PDFium (EmbedPDF 2.15.1) 检查可读性、加密状态、页数与页几何。上限 50 MiB、100 页，25 MiB 起显示资源警告；可信解析串行，进程空闲内存不足 512 MiB 时拒绝继续。（2026-10-16 局部修订，desktop-app 票 30。旧定位：「空闲内存」在实现里是 `os.freemem()`。新结论：按平台取可用内存——Linux 读 `/proc/meminfo` 的 `MemAvailable`；macOS 取 `vm_stat` 的 free＋inactive＋speculative 页（不加 purgeable，它已在 active/inactive 队列里，加了会重复计），结果缓存 1 秒、并发调用共用一次；Windows 用 `os.freemem()`（可用物理内存）；取不到时退回 `os.freemem()`。范围：探测与原件页材料两处的余量检查（`server/src/available-memory.ts`）；阈值 512 MiB 与「不足即拒绝」不变。原因：macOS 上 `os.freemem()` 不算可回收的 inactive 页，runner 与平常的 Mac 都常不足 512 MiB，PDF 上传被误拒。批准：用户 2026-10-16 在票 30 的裁决。）不可用 OCR 或密码解锁，不以 MIME/文件名/magic 代替解析。
- 每次成功创建 `pdf-<UUID>` 独立 Doc，保存 `original.pdf`、明确 `format=pdf` 的元数据、绑定 hash 的空标注 sidecar 和 null 阅读位置 sidecar，全部完成后才挂 Library 关系。PDF 原文件永不原位替换。
- 完全相同字节仅在目标 Work 内返回既有 Doc，不重建或重置用户 sidecar；另一个 Work 接收相同 bytes 时建立独立物理副本、Doc 与用户状态。文件名/论文身份不会改挂目标 Work。首 Doc 成为主，向有正文 Work 新增 PDF 不抢主位，现有“设为主/全局删除”仍由条目内管理。
- build 只保留合法 Library 关联，不按 PDF 标题 seed Work，也不跨 Work 合并相同 bytes。孤立/损坏 PDF 不自动回挂或删除；唯一 owner 检查失败时 Reader 读取拒绝。
- `GET /description` 是格式/来源展示提示，不作内容一致性证明。Reader 通过 PDF snapshot 与原件端点校验元数据、annotation sidecar 和本次实际 bytes 的 SHA-256；原件 hash 不同为 409，损坏/丢失的原件、metadata 或 annotation JSON 为 500，均不得重置、归档或重绑。reading-position 独立校验；缺失/损坏/未来版本/hash不符时 snapshot 仍提供已验证正文及标注，并附 `reading_position.status=error`，显式告知未恢复、原进度 JSON 保持原样，不当成初始 null。PDF 初始工作台标注是可创建/编辑的空集合，原 PDF 自带内嵌标注只读；初始阅读位置为 null。Work 内工作台标注和位置保存沿 05–07 的 per-Doc sidecar 合同。
- **server 的 PDFium 在 worker 线程里跑**（shelf-followups 08，2026-10-23 用户「要修，开票」）：上传/arXiv 探测与原件页材料（文字与目录、页图像、文本 Doc 的区域图、PDF 文本标注的目标）的引擎调用都在 `server/src/pdfium-worker.ts` 的独立线程里，每个引擎一条线程、随它的 WASM 一起结束；主线程照旧做唯一队列、等待上限、512 MiB 余量检查、校验过的快照与期限（`pdfium-shared.ts`）。PDFium 的同步 WASM 与 PNG 编码因此不再占 server 事件循环：改前一页渲染几乎整段占住事件循环（合成测试 PDF、单跑实测：longEdge 4096 约 1.1–2.2 s、2048 约 0.3–0.6 s，随 PDF 与机器负载变化），改后渲染期间 10 ms 定时器最长间隔约 20 ms（`pdf-material.test.ts` 断言低于 250 ms）。输出字节、像素预算与错误分类不变；到期限时线程被终止，在途调用照旧报 `PDF parser timed out`，不等被放弃的那页；线程意外退出报 `PDF engine stopped unexpectedly`（带原因；页材料路由答 500，上传探测把它当系统失败而不是「文件不可读」，作业记为失败）；启动失败时先等线程结束再报错，队列不会同时跑两份 PDFium；都不挂起请求。代价是每个引擎多约 70–80 ms 起线程、载入引擎（与 WASM 初始化合计约 90 ms）。
- EmbedPDF 2.15.1 worker/WASM 本地随 Web bundle 提供；原 PDF 内嵌标注锁定只读，Reader 只将哈希校验后的 buffer 交给 SDK，不调用带标注导出。许可文本随 app 分发，受测许可证范围见 `packages/app/dist/THIRD-PARTY-EMBEDPDF-NOTICES.txt`（构建生成）。
- **字体回退**（desktop-app 票 28，用户 2026-10-15 裁决：桌面包与浏览器形态都开；只开 CJK、保留全部字重）：PDF 里用了未嵌入字体的 CJK 文字，PDFium 要靠引擎的字体回退才画得出来；此前 server 与页面都以 `fontFallback: null` 建引擎，这类文字渲染为空白（文字层一直正常）。现在两边用同一张表（contracts `pdf-fonts.ts` 的 `PDF_FALLBACK_FONT_PACKAGES`）：`@embedpdf/fonts-jp|kr|sc|tc` 1.0.0（`@embedpdf/engines` 的依赖，Noto Sans CJK，OFL-1.1，许可原文随包且已在 `THIRD-PARTY-EMBEDPDF-NOTICES.txt`）的全部字重，分别答 PDFium 的 SHIFTJIS / HANGEUL / GB2312 / CHINESEBIG5 字符集（Adobe-Japan1 / Korea1 / GB1 / CNS1 的 CID 字体即映射到这几个）。server（`pdfium-shared.ts` → `pdf-fonts.ts`，表与文件路径由主线程算好交给 PDFium worker 线程，线程只读表里列出的文件）从磁盘读：字体包从 `@embedpdf/engines` 自己的位置解析（pnpm 工作区、npm 安装、桌面包依赖目录都成立），读不到的文件只是该字不画、不报错。页面（`PdfReader.tsx`，配置由 `pdf-font-fallback.ts` 的 `pageFontFallback` 构造）的 PDFium worker 用同步 XHR 从**本地 server** 取：`GET /api/pdf-fonts/<包>/<版本>/<文件>`，只答表里的名字（其余 404），`font/otf`、`immutable`（路径带版本）、`nosniff`；绝对地址（worker 跑在 `blob:` 地址上），同源，不改跨来源守卫；**从不用引擎缺省的 jsDelivr CDN**（`fontFallback` 省略时引擎会去 CDN 取 `@latest`），离线可用；web 测试 `pdf-font-fallback.test.tsx` 守住这一点（Reader 交给引擎的配置非空、无 `defaultFont`/`baseUrl`、每个地址同源且在字体路由下）。**证据范围**：页面一侧只在浏览器形态（`serve`＋Chromium）实测过；桌面 webview（WebKitGTK，`blob:` worker 里的同步 XHR）的页面渲染**未验证**，桌面包已核实的是 server 一侧的渲染与字体路由答 200（依赖目录冒烟）。不收 `fonts-latin|arabic|hebrew`（共 11.8 MB）：票 28 探针里未嵌入的 Cyrillic / Greek 简单字体 PDFium 根本不问字体回退（开不开都空白），Arabic / Hebrew 未测。字体包升级时 server 测试 `pdf-font-fallback.test.ts` 会因表与已装清单不符而红。

## Cite key 与统一书目字段

- rebuild 预灌已有键，只给缺失的新 Work 分配并避让冲突，不无条件重排。
- Stage 12 分配规则：分配时有 bibcode → cite_key = bibcode；没有则用原 citeKey()；**分配后永不改**，包括后来才富化出 bibcode 的条目。
- Stage 12 一次性存量改键与稿件同步替换是历史窄授权，不是今后重排授权。它修订了分配侧，没有解除分配后稳定性。
- Stage 13 手动 BibTeX 建条目尊重用户 key；与其他 Work 冲突逐条报错，不静默改名。`library build --bib` 仍系统分配，两条路径语义有意不同。
- DOI stub 可经 title bridging 归并，就地 planFor 和分配键，不隐式全库 rebuild。

**BibTeX 来源无特殊通道**：ADS export、用户给出的 BibTeX、生成兜底都填同一 Work 结构化字段。不存 BibTeX 原文 blob；`library.bib` 仍是唯一派生出口。

Stage 12：enrichAndPlan 中有 bibcode 且无已存字段时，批量 ADS export 拉取并解析 volume/number/pages/eid/month/journal_macro 等，只补空，不覆盖已有 title/authors/year/doi/eprint 等 normalize 结果。`--offline` 跳过；失败不阻塞，下次 build 自然重试；已存不自动刷新，不接 Crossref bibtex。

`workToBibtex` 输出全部非空字段，生成层转义 `& % # _`；**`$` 除外**，保标题数学。有 journal_macro 输出 `journal = {\aap}` 一类宏，无则转义纯文本；venue/journal 显示层仍纯文本。Writer 编译与 zip 导出注入同一组 `\providecommand` 期刊宏，不改 reader 管线，详见 [writer](writer.md)。

**I034 — 已接受语法边界**：分号分隔 cite key、全角逗号等命令错误由用户负责，以 LaTeX/bibtex 真值报错，不新增 server/web 诊断提示；用户明确要求语法辅助时再议。

## Web 手动建立条目（Stage 13）

入口为侧栏导入菜单三个真模式；旧“从浏览器抓取”假占位已删。统一 `POST /api/library/works`，跨站守卫（受保护的 Hono 底座 `server/src/protected-app.ts`，写路由默认受守卫）+ libraryLock，同步就地 upsert/planFor/assignCiteKey/save/广播，**不触发全库 rebuild、不走创建 job**，复用现有解析链。

| 模式 | 接受输入与失败语义 |
|---|---|
| identifier | DOI、`arXiv:<id>` 或 arxiv.org URL；裸 arXiv id 拒绝并教学前缀。解析链全 miss 仍建裸 stub，下次 build 可富化 |
| bibcode | ADS bibcode 单条；ADS 不可用/未命中 fail-fast，不建 stub；创建时 resolve + ADS export 补字段 |
| bib | BibTeX 全文批量；纯本地解析、逐条部分成功；尊重用户 cite key，冲突逐条显式报错 |

CLI 裸 arXiv id 正文摄入路径不变。裸 id 只在 Web identifier 建条目中被拒。

- 手动 bib 保留 title/authors（规范化姓）/year/journal/volume/number/pages/eid/month/doi/eprint 及 journal 宏识别；复用 parseBibtexText + parseAdsBibtexFields。entryType 沿用 isConf（conf，否则 article），不伪造通用 BibTeX 类型支持。
- 身份重合返回 exists，只补空字段，不覆盖既有字段或用户数据。单条成功/exists 关闭对话框并开详情；批量显示逐条创建/存在/失败结果，关闭后刷新列表并选中首个新建项。
- 单条创建时 resolveWork 全链；批量 bib 不做 N×外部请求，富化留后续 build。
- 图谱增量仅作即时尽力可视化：新节点和本地 saved↔saved 边；失败不使创建失败，全局收敛仍由全量 build/refresh 权威。Stage 14 已取消为 suggested 邻居发 OpenAlex 批量请求；批量 bib 只补裸节点。
- Web DOI 比 CLI 多 ADS/OpenAlex 富化属于 Web 新能力；CLI `addDoiWork`、`ingest <doi>` 和 `library build --bib` 既有行为不因此扩展。

## arXiv PDF 获取与既有 LaTeX 来源（Web）

### 默认 PDF 获取

新增 Work 自动任务仍只从既有 identifier、bibcode/Discovery 入库、以及既有解析链已解析出 arXiv ID 的 DOI 路径触发；没有 arXiv ID 不触发，批量 BibTeX 永不自动，不新增 DOI 反查。创建/exists 的 Work 响应仍同步返回；后续以持久 Job 获取 PDF。

- 自动提交和执行时均按 Work 的真实关联/显式 PDF metadata 检查是否已有任意 PDF；已有 PDF（即使其当前文件不可读）会阻止自动获取。只有 LaTeX Doc 不阻止。打开详情、重启和遍历旧库不触发补抓。
- `auto_ingest_arxiv` 默认 true 且提交时现读；false 只关闭自动 PDF 获取，手动仍可用。设置页「项目」组有它的开关「添加文献时自动获取 arXiv PDF」（desktop-app 票 11；键名仍是 `auto_ingest_arxiv`，名字里的「ingest」是 Stage 15 的旧称，它不再自动获取或编译 LaTeX 源码），与手改配置文件同一个键。
- 手动 `POST /api/library/acquire-arxiv-pdf?id=<workId>` 需要现存 Work 和解析后的 arXiv ID；已有 PDF 不阻止用户主动再次获取；`startArxivPdfAcquisition` 有一条防御性的 `busy` 分支（新 Doc id 是刚生成的 uuid，正常使用不会触发），触发时路由回 409 `document busy`（与上传一致）；其余无法排队仍回 409 `could not queue arXiv PDF acquisition`。
- 来源使用 `https://arxiv.org/pdf/<canonical-id>` 获取本次返回的原始 PDF bytes，不做 `export.arxiv.org` 版本查询。metadata 记录 `acquired_via="arxiv_pdf"`、规范 `arxiv_id`、Server 取得时间、原始 byte length、SHA-256、页数和 PDFium 页几何；**不声称已核实官方 `vN`、提交日期或“官方最新版”**。
- 每次新的显式获取在成功后创建新的 `pdf-<UUID>` Doc，即使 bytes 与已有 PDF 完全相同也不去重。相同 Work/格式仍在 queued/running 的同一获取任务会被复用；Job 终态后的再次显式提交是新任务。上传 PDF 原有 same-Work identical-byte 去重完全不变。
- PDF 发布走既有 50 MiB / 100 pages / 512 MiB headroom 串行 PDFium 探测、不可变 stage bundle、DocMutationRegistry pin 和 libraryLock；新 Doc 只追加到用户指定 Work。旧 Doc 的 PDF、标注 sidecar、阅读位置 sidecar 与 `doc_ids` 主位原样保留。若 Work 无 Doc，新 PDF 自然为主；已有主位不改变。
- arXiv PDF 任务复用串行持久 JobRunner，payload format 为 `arxiv-pdf`；`job.done` 先于成功时的 `library.changed{cause:"upload"}`。boot-interrupted 不自动重跑，重复在途提交复用 Job；失败可以通过新的显式提交重试。此 PDF 错误不进入 Stage 15 LaTeX 的 `arxiv-fetch.jsonl` 或 PDF-only LaTeX 引导。

### 既有 LaTeX arXiv 获取保持独立

`POST /api/library/attach-arxiv?id=<workId>` 仍是 Stage 15 LaTeX 源码获取/刷新入口：既有 arXiv LaTeX Doc 沿旧 Doc ID/原位刷新、编译、错误分类与归档契约处理；CLI LaTeX ingest、PDF-only 冻结 CLI 文案和 Writer 不变。PDF-only Work 可显式获取一个独立 LaTeX Doc 并追加在现有 PDFs 后，不抢 PDF 主位；同 Work 若已有其他 LaTeX Doc/LaTeX zip 且不是要刷新的 arXiv Doc，则旧 Scenario C 仍拒绝新增 arXiv LaTeX，不放宽 ZIP 重传或 risk 规则。它不是 PDF 获取端点。arXiv LaTeX 来源和用户 zip 仍是详情里的显式 LaTeX 路径。`auto_ingest_arxiv` 现控制默认自动 PDF 获取，不启动旧 LaTeX 自动刷新。

批量 bib、详情打开、重启、旧库回填、PDF 原位替换、自动官方版本追踪、CLI/agent PDF ingest、OCR/出版商 HTML、任务取消、全局任务页和跨进程同 Doc 并发均不在本范围。

KaTeX 会（经 `trust` 回调精确检出，不靠颜色）把 `\\href`/`\\url`/`\\includegraphics`/`\\html*` 画成红色源码并丢掉内容，给 `math_untrusted_command` warning。`$…$` 的结束 `$` 被裸网址吞掉（`$\\href{http://x}{y}$`）时在网址处给 `math_url_swallowed` equations/codeBlocks/inlineMath/citations/crossRefs/references/unresolved（仅非零时出现）。
- **图片资产、图与表格（票 27）**：
  - **资产**：`POST /api/paper/:id/source/assets?expectedRev=&filename=`，请求体是原始图片字节（`application/octet-stream`），服务端用有界读取（声明与流式均封顶 20 MiB，超限即中止，不整体缓冲）后**按字节内容**判型：PNG/JPEG/WebP 的签名与结构（PNG 须有 IHDR 与 IEND，JPEG 须有帧头与结束标记，WebP 须有 RIFF/VP8·VP8L·VP8X 头），像素尺寸只读头部、不解码，单边 ≤30000 且总像素 ≤64 MP；SVG、HTML、GIF、PDF 及任何其他字节一律拒绝（415/422），按文件名或客户端声明的类型不作判断。文件名只当作词干：含分隔符、`..`、前导点、盘符、NUL 的名字被拒绝（400 `bad_name`），不做“修复”；存储名为 `<安全词干>-<sha256 前 8 位>.<png|jpg|webp>`，扩展名来自判型结果而非用户文件名。`<docDir>/assets/` 必须是真实目录（符号链接被拒），文件以 `wx` 写入、**永不覆盖**（同名未登记文件使本次添加失败且原样保留）；先写图片再原子替换 `text-source.json`（`rev+1`、`assets[]` 含 name/sha256/byte_length/media_type/width/height），源写入失败则删除本次新建的图片。同字节再次添加返回既有资产（`reused`），不变更 rev；并复核已登记文件仍在且 hash 相符：缺失则按原字节重新写入，已损坏则先把坏字节改名为 `<name>.damaged-<时间>-<随机>` 留存（不删除、不覆盖）再重写，响应带 `restored: true`。写入是同目录隐藏临时文件 + `link` 到最终名（EEXIST 不替换；文件系统不支持硬链接时回落为 `wx` 直写，失败即删除本次所建文件），因此中途失败（如磁盘满）最终名上不会留下半个文件、也不会挡住重传；已存在的文件任何情况下都不会被本次调用删除。同一 Doc 最多 500 张。与保存同一 text lock 临界区，Doc 正在删除时拒绝；成功广播 `text-source.changed`，从不触碰阅读正文与标注。更新一张图即得到新名字（新 hash），已发布的 IR 仍指向旧文件，旧文件字节不变；未被引用的资产一直保留到 Doc 删除（无 GC）。图片经既有 `/images/:doc/:file` 路由服务，三条图片响应现带 `X-Content-Type-Options: nosniff` 与 `Content-Security-Policy: default-src 'none'; sandbox`；Reader 经 blob URL 的 `<img>` 显示，SVG 脚本无从执行。
  - **图**：独占一个段落的 Markdown 图片 `![说明](assets/<名称>)`，名称必须是本 Doc 已登记资产；其前紧邻的 `argelander-block` 可给 `id`、`kind:"figure"`、`number`、`label`、`caption`（与代码题注同规则：纯文字、`$..$` 数学、`[cite:]`、`[ref:]`）、`footnote`。`alt` 保留为块的 `content`（说明），不当作题注；标题被忽略并给 warning。URL/data URI/绝对路径/`..`/反斜杠/百分号转义/子目录/未登记名称各有定位诊断（`image_remote`、`image_path_unsafe`、`image_path_invalid`、`image_asset_missing`），句中/标题/列表项内的图片 `image_inline`，alt 含公式或 token `image_alt_token`。IR 为 `figure` 块（`imgPath` 为资产名、`imgWidth/imgHeight` 取自登记的尺寸）。生成时被引用的资产逐个按登记 hash 复核（缺失/被改/不安全 → 500 `asset_unreadable`，不发布）；`source_fingerprint` 为 Markdown 字节加被引用资产的名称与 hash（无图时仍是纯 Markdown hash），标注内容指纹照旧把图片字节 hash 纳入。
  - **表格**：GFM 表格（整张表头/行/列/单元格内容与 `$..$` 数学原样保留，公式内的竖线不分列，表头为 `th`；比表头多出单元格的行会被 marked 截断，故定位报错 `table_extra_cells`；列对齐不保留，给 warning）与围栏 `argelander-table`（`{"rows":[[{text, header?, rowspan?, colspan?}]]}`，严格 schema、未知字段定位报错，跨度为正整数）。网格必须恰好铺满矩形：首行宽度决定列数，每个单元格不得越过右边界或最后一行（`table_span_bounds`）、不得与其他单元格重叠（`table_span_overlap`）、不得留空格（`table_row_incomplete`），错误带 JSON 字段路径与行列。单元格文本全部转义；仅 `$..$` 公式被保留（交 Reader 的共享数学渲染），原始 HTML、cite/ref、行间公式在单元格内为定位错误。每表最多 2000 行、200 列、4 万单元格。生成的 `tableBody` 只含 `<table><tr><th|td [rowspan] [colspan]>` 结构，与既有表格渲染器同一形状。表块同样接受 `argelander-block` 的 `id/kind:"table"/number/label/caption/footnote`。
  - **Reader**：`Block.tsx` 与右栏 `RefCard.tsx` 所有 `tableBody` 的注入现经 `safeTableHtml`（此前 Reader 未清洗，agent/文本源写入的表格可成为活 HTML）；图/表 `footnote` 与题注同样经扫描器读取（公式试排版与宏拒绝、货币与转义规则、`[cite:]`/`[ref:]` 解析或定位报错），IR 中保留原字符串 `footnote`（指纹绑定它）并新增可选 `footnoteSegments`，Reader 按段落渲染（与题注同路径，不再用 `htmlWithMath` 的正则）；只有字符串的 IR 显示为惰性文本。`alt` 作为图片的可访问名称（回退到 `label`）。表格单元格里的字面 `$`（`\$` 或货币）被包进独立的 `<span>$</span>`，使 Reader 的单元格数学排版不会把它们配成公式；含 `$` 的单元格公式是定位错误（`table_math_dollar`）；`safeTableHtml` 允许 `span` 与最多 4 位数的 `rowspan`/`colspan`，使通过校验的网格（≤2000 行、200 列）渲染一致。GFM 单元格按 marked 的 `splitCells` 规则计数（反斜杠奇偶），多出的单元格定位报错 `table_extra_cells`；单元格内的 HTML/链接/图片错误定位到所在单元格；网格问题超过 20 条时汇总为 `table_more_problems`。扫描器/marked 一致性、恰好一次不变量与已提交的属性（fuzz）测试已扩展到图与表。
- **来源 PDF 与删除**：来源 PDF 只是文件关系（Doc id + sha256），删除 PDF 不级联；删除文本 Doc 复用全局物理 DELETE（源、IR、当前/归档标注、全部 Work 关联）。旧 CLI 对 text IR 不承诺支持（`list` 显示 unreadable，退出码 0）。

## 文献仓

文献仓（[CONTEXT](../CONTEXT.md)「文献仓（Shelf）」、[ADR 0013](adr/0013-shelf-copy-not-global-library.md)）是全局数据，与项目之间只经复制；数据保护条文是 [contracts](contracts.md)「文献仓」，条目格式、目录与跨进程锁见 [architecture](architecture.md#数据与配置)「文献仓的存储」（infra `shelf/store.ts`）。server 的接口形状在 contracts `shelf-write.ts`（写）；每个拒绝都是 `{detail, code, …}`，`code` 是页面与 Copilot 比对的值，只点名对象（Doc id、条目 id）与原因类别，不含正文。文献仓的写入成功后广播 `shelf.changed{cause: add|replace|delete, entry_id, rev, removed}`（`removed`：随这次变化消失的条目版本——替换时为确认过的全部目标〔第一个以新 rev 沿用 id，其余被移除〕，删除时为被删的那个，加入时为空；只有本 server 的写入，另一工作台进程写的不通知）。

### 加入 / 替换 / 删除（shelf 票 03）

- **`POST /api/shelf/entries`**：`{workId, docs: [{docId, annotationIds}], argumentGraph, note, confirm?}`。`docs` 是用户勾选的 Doc（条目里按 Work 的顺序，主 Doc 在前），`annotationIds` 是该 Doc 勾选的标注（空＝不带）；论证图（非空时）与笔记（非空时）各是一个开关。书目总是带：Work 去掉 contracts `SHELF_EXCLUDED_WORK_FIELDS` 的全部字段。条目记来源为 server 的项目目录与 Work id。成功 200 `{entry, replaced, carried, notCarried, archived}`。实现 `server/src/shelf-add.ts`。
- **读取在一个同步临界区里**：经标注访问路径的 `together`（`annotations-access.ts`，app 唯一的 annotationLock），所以复制的每个文件都是同一时刻的，本 server 的标注保存、PDF 标注写入、文本 Doc 发布、Doc 删除的占位、上传的 pin 都插不进来（跨进程仍不支持，I013）。顺序：①库：Work 存在（否则 404 `work_not_found`），每个所选 Doc 都在它的 `doc_ids` 里（否则 409 `doc_not_in_work`）；②所选 Doc 都不忙（DocMutationRegistry 的内容忙：在写或在删，否则 409 `doc_busy`）；③逐 Doc：种类（`text-<uuid>` 按 Doc id 即为文本 Doc，不看源文件读不读得到——源文件是链接/目录报 `not_a_regular_file`、缺失报 `incomplete`，绝不当 LaTeX 带走；其余有 PDF 元数据为 PDF，否则 LaTeX）、文件（contracts `shelfDocFileAllowed`/`shelfDocRequiredFiles` 是唯一规则：LaTeX 不带 `src/`、`build/`；PDF 不带阅读位置，标注 sidecar 只作标注副本；以点开头的临时文件不带；`assets/` 下带不了的文件或链接、该是普通文件处是链接都算校验不过，不静默略去）与校验——PDF：恰好一个 Work 持有、原件对上记录的字节数与 SHA-256、sidecar 的 schema 与 `doc_id`/hash 绑定（PDF Doc 的 sidecar 每次都校验，不论是否勾了标注）；文本 Doc：源文件与登记的图片（大小与 hash）；LaTeX 与已生成的文本 Doc：阅读正文能解析且属于本 Doc，它声明的每张图（figure/table 的 `imgPath`，按 core 的解析：裸文件名在 `assets/` 下，带目录的相对 Doc 目录）都在带走的文件里——落在 `assets/` 之外的报 `asset_outside_carried`、缺失报 `asset_mismatch`，不静默缺图——以及只读的内容指纹可算，不写任何东西；④勾了的论证图与笔记；⑤**最后**才读所勾 Doc 的当前标注：LaTeX/文本 Doc 经访问路径的 ensure（三态照旧：相同＝有效；不同＝照常归档并建空 current、广播 `invalidate`，带走的是新的当前标注，通常为空；无法计算＝系统错误，不碰标注；Doc 忙时 ensure 自己拒绝，不 ensure 不归档），PDF 读已校验的 sidecar；按所选 id 逐条筛选，其余键原样保留，筛完为空则不带标注副本。归档永不读取。没勾标注的 Doc 不调 ensure，所以即使它的标注已过期也不归档。
- **任一项读不了或校验不过 → 整次中止**：500 `item_unreadable {item, problem}`（`item` 为 `doc`/`annotations` 带 `docId`，问题落在一个文件上时带 `path`——Doc 目录内的相对路径，不是正文；或 `argument_graph`、`library`；`problem` 见 contracts `SHELF_ITEM_PROBLEMS`），文献仓零写入；项目只可能有 ⑤ 里访问路径本来就会做的归档（busy 与 ①–④ 的失败都在任何 ensure 之前）。ensure 的两种写入失败各有类别（同 `annotations-access` 的 `describeError`）：`annotations_archive_failed`＝旧批次未能移入归档、原样保留；`annotations_new_current_failed`＝旧批次**已归档**而新空 current 未建成（契约的中间态，下次访问重建），文案如实说已归档，只说文献仓未写入。**中止也如实报告已做的归档**（契约「文献仓」2026-10-23 局部修订）：读到第 ⑤ 步之后的每个回答——成功，以及其后的每个拒绝（`item_unreadable`、ensure 遇忙的 `doc_busy`、文献仓的 `shelf_busy`/`confirmation_*`/`shelf_write_failed`/`shelf_unreadable`/`lock_lost`）——都带 `archived: [{docId, count}]`（本次各 ensure 归档的 Doc 与条数，`new_current` 中间态的条数取 ensure 前只读的 current 条数），非空时 `detail` 写明哪些 Doc 的旧批次已在项目的归档里；例如 A 已归档、B 读不了时，回答点名 B 的问题并报告 A 的归档。勾了但已不是当前标注的 id（期间被删，或被那次 ensure 归档）不算失败，列在 `notCarried`。
- **同一篇与替换确认**：只认 DOI、arXiv（去版本号）、OpenAlex 号（infra `shelfIdentityOf`）；三者都没有的 Work 不做同一篇判断，每次加入都新建条目。首次请求在读取项目**之前**先查文献仓：已有同一篇 → 409 `confirmation_required {impact}`，零写入、也不读项目（不会因询问而归档）。`impact.entries` 列出将被替换的每个条目（可能不止一个，例如一篇先以 DOI、另一篇以 arXiv 号加入）：`entryId`、`rev`、标题、加入时间、来源项目路径（`sourceProject`）、Doc 列表（`docs`：`docId`、种类、字节数）、标注数、有无论证图与笔记——都是该条目在该 rev 的函数（条目就位后不再原地改写）。页面确认后把 `impact` 原样作为 `confirm` 回传：先与文献仓当前的同一篇条目逐项比对（集合与每项都要相同），再读项目，最后 store 在跨进程锁内按条目与 rev 再比一次（`put` 的 replace targets）；任何不符 → 409 `confirmation_changed`，仍有同一篇时附最新 `impact`，已无可替换时不附（即使此时已无风险也拒绝，用户重新加入即可），零写入。等待确认期间不持有任何锁。替换是整条替换、不合并：新条目沿用第一个条目的 id、rev+1，其余条目在新条目就位后移除；成功结果 `replaced` 列出被替换的条目。没有 `confirm` 的请求在读取之后、写入时才撞上同一篇（另一请求抢先加入）同样回 `confirmation_required`。
- **`POST /api/shelf/entries/preview`**（供 Copilot 确认卡在执行前展示，票 07）：与加入同一请求体，不收 `confirm`；同一临界区、同一顺序与同一批拒绝（busy、读不了、校验不过），但第 ⑤ 步**不调 ensure**：读当前标注文件（schema 校验），它绑定的指纹与只读指纹相同才按所选 id 计数，属于旧内容的整批视为不带（加入时访问路径会归档它们），列入 `notCarried` 作预估。200 `{impact, carried, notCarried, wouldArchive}`，`impact` 为若此刻加入将要求确认替换的条目（同加入的 `confirmation_required`），没有同一篇为 null；`wouldArchive: [{docId, count}]`（票 07）逐 Doc 列出所选了标注、当前标注文件属于旧内容、加入时访问路径会归档的批次及条数（没有标注文件的不算，没勾标注的 Doc 不看）。零写入、零归档、不广播。进程内的加入可带期望（`ShelfAddOptions.expect`，只供 Copilot 确认卡，不在 HTTP 请求体里）：读取之后、写文献仓之前比较 carried、notCarried 与本次归档是否就是那份预演，不同即 409 `carried_changed`，文献仓零写入。
- **文献仓自身的失败**：等锁超时 503 `shelf_busy`；某个条目读不了（它可能就是同一篇）500 `shelf_unreadable {errno}`；写入失败 500 `shelf_write_failed`（只限 store 对输入的拒绝与其写入的系统错误；store 已删掉暂存，不改已有条目；其余意外错误照常抛给 app，不报成写入失败）；写入中途锁被别的进程接管 500 `lock_lost {written, removed}`（`written` 非空表示新条目已就位，此时也广播；`removed` 与广播的 `removed` 都只列确实已不在的目标——写入后重新列出文献仓比对，第一个目标的旧 rev 已被新 rev 取代，其余未移除的仍会列出）。
- **`DELETE /api/shelf/entries/:entryId?rev=<n>`**：删除页面显示的那个 rev 的条目（确认由页面负责，接口带 rev）。200 `{deleted}`；rev 不是正整数 400；没有该条目 404 `not_found`；已被替换 409 `rev_mismatch {currentRev}`；503 `shelf_busy`；500 `lock_lost`。只删文献仓那份，不碰任何项目；看不懂格式的条目也可以删。
- **页面**（票 05，`web/src/shelf/`）：Work 详情头部「加入文献仓」与加入对话框（替换确认是同一对话框的下一步）；摄入成功的一次性提醒（只认本页看到的 `job.done`，不认 `hello` 重放；关掉或经它加入后该 Work 不再提醒，按项目文件夹存在浏览器 localStorage）；「导入文献」菜单第四项「从文献仓」打开文献仓对话框（列表＋搜索｜摘要、取入、结果），删除确认是叠在它上面的独立小对话框；列表随 `shelf.changed` 与重连重读。入口在教程 Project 与普通 Project 里相同，页面不判断当前是不是教程 Project，也不读教程状态（2026-10-24 教程加文献仓，契约「文献仓」局部修订三；摄入提醒仍按项目文件夹各自记忆，文件夹取自设置）；加入对话框的列表走只读的 `GET /api/shelf/add-candidates/:workId`（各 Doc 的种类、文献仓会带的字节数，以及经标注访问路径 `peek` 读的当前标注：不 ensure、不归档、不广播；旧内容的标注报 `stale`，对话框说明这次加入既不带入也不归档（没勾标注的 Doc 不经访问路径），下次正常访问该 Doc 时才按规则归档，并禁用其勾选；PDF 标注照旧由页面读 snapshot），所以打开对话框不会让任何 Doc 归档；server 的路由与 Copilot 的 `shelf` 工具同样不判断当前是不是教程 Project。
- **添加时「文献仓已有」提示**（票 06，`web/src/shelf/already-on-shelf.tsx`）：「从 DOI / arXiv ID」对话框提交后、探索候选点「加入文献库」后（详情页脚与列表视图的按钮都算），页面先按 DOI / arXiv 号经只读的 `GET /api/shelf/lookup` 查文献仓（只在提交之后问，输入时不问；裸 arXiv 号、bibcode、BibTeX 与 Copilot 的保存不查；项目里已有同一篇时不查，DOI 与 arXiv 号都比，arXiv 的 DataCite DOI 当 arXiv 号；查询期间改了输入、或在探索里改选了别的候选或关了详情，迟到的回答丢弃，不提示也不添加），命中再逐条 `GET /api/shelf/entries/:id` 取摘要；有命中则不添加，显示提示（Doc 数、标注数、论证图及其论证条数〔条数未知时只说有论证图〕、加入时间与来源项目）与「从文献仓取入…」（一条命中直达取入步，多条打开第一条的摘要供选择）/「照常创建条目」「照常加入」（照原路添加，不再查）。没有命中，或查询失败（拒绝、无应答，视作「不知道」），都照原路添加、不提文献仓。探索里取入完成后留在探索；文献仓对话框里可以改选任何条目，只有取入的是该候选的命中条目之一时才把候选标为已在文献库；只有结果里的「在文献库中查看」离开探索。教程 Project 里照样查；探索图与候选列表上不加标记（Q22）。
- **Copilot**（票 07）：`shelf` 工具的列出/搜索与加入、替换、删除、取入的真人确认卡，复用本节的 writer、取入与预演，语义不变；机制见 [architecture](architecture.md)「文献仓的 Copilot 工具」。

### 取入与查询（shelf 票 04）

（shelf 票 04；契约见 [contracts](contracts.md)「文献仓」（含 2026-10-23 局部修订二），决定见 [ADR 0013](adr/0013-shelf-copy-not-global-library.md)，存储见 [architecture](architecture.md#数据与配置)「文献仓的存储」。代码 `server/src/shelf-take.ts`，应答形状 contracts `shelf-take.ts`。）

**只读接口**（读的是用户的全局数据，与 `/api/tutorial` 一样受跨站守卫，`no-store`）：

- `GET /api/shelf`：`{entries}`，每条带 `status`：`ok`（书目摘要、`identity`、各 Doc 的 id/种类/字节数/带的标注数、标注总数、有无论证图/笔记、论证条数 `argumentCount`、`bytes`、来源项目路径与 Work id）、`incompatible`（`needsUpdate: true`、声明的 `format`、尽力读出的标题——页面标「需要更新工作台」，不能取入）、`damaged`（原因类别）、`unreadable`（errno，系统错误，不是损坏）。整个文献仓读不了 → 500 `shelf_unreadable`，不答空列表。
- `GET /api/shelf/entries/:id`：该条目的摘要加整份书目快照与笔记开头 `notePreview`，取自清单（与列表同一次读取，Doc 文件不逐个 hash）；看不懂的版本、损坏、读不了各有 `status`；没有该条目 404。逐文件核对留给预演与取入。
- **论证条数与笔记开头**（shelf 后续票 01）：`argumentCount` 在读取时从条目自己的 `argument-graph.json` 现算（infra `readPart`，只核对这一个文件的大小与 SHA-256），不写进清单——清单是严格 schema，加字段会让旧版本把新条目当损坏，已有条目也没有这一项。没带论证图为 null；带了而本版本数不了（更新的版本、不合本版本的论证图格式、文件已不在或与清单不符、读不了）也是 null，表示「不知道」，不是错误，该条照常 `ok`。条数不是正文，列表、摘要与 Copilot 的 `list` 都给。`notePreview` 是笔记的前 200 个字符（按码点，`SHELF_NOTE_PREVIEW_CHARS`）与 `truncated`，没带笔记或笔记文件读不了、对不上时为 null；**只有这个摘要应答带它**，供页面取入步骤的笔记勾选项预览，列表与 Copilot 工具都不带笔记文字（契约「文献仓」、票 07）。页面（按已审阅的原型）：摘要的「论证图」一行与取入步骤的论证图勾选项写「N 条论证」（条数未知时照旧说「有」/带着论证图）；摘要的「Work 笔记」一行与取入步骤的笔记勾选项显示这段开头（被截断时加「…」，读不到时照旧说「有」/带着笔记）；「文献仓已有」提示写「论证图（N 条论证）」；取入计划为保留本地论证图（`kept_local`）时，提示写「本项目这篇已有论证图（N 条论证）」，N 由页面经既有的只读 `GET /api/works/:id/argument-graph` 读目标 Work 的图现数，读不到时照旧不带条数。
- `GET /api/shelf/entries/:id/annotations[?rev=]`：逐 Doc 列出条目带的每条标注：`id`、种类、位置（LaTeX/文本：由条目内 IR 推出的节路径「1 Introduction › 2.1 …」与结构目标的印刷号；PDF：零基页号，文字目标取首页，整篇批注为 null）、片段（引文或快照文字，至多 200 字符）、批注正文、时间。给页面的「逐条取消」用；这是唯一带标注正文的文献仓应答，Copilot 工具（票 07）不经它暴露正文。读条目逐文件核对；版本、损坏、替换的答法同取入。
- `GET /api/shelf/lookup?doi=&arxiv=&openalex=`：同一篇（只认这三者，规范化同存储层）的条目，供添加时「文献仓已有」提示（票 06）；三者都没给 400。
- 其余应答不带标注正文；除摘要的笔记开头外，任何应答都不带笔记文字，也都不带论证图内容（论证条数不算内容）。

**预演与取入**：`POST /api/shelf/entries/:id/take/preview` 与 `POST /api/shelf/entries/:id/take` 同一请求体 `{rev, excludeAnnotations?: {<docId>: "all" | [标注 id…]}, argumentGraph?: bool, note?: bool, planDigest?}`（后两者缺省为取；标注缺省全取，spec Q6）。两者都先不加锁地 `read(id, {rev})`（逐文件大小与 SHA-256），再由同一个不写盘的计划函数（`planTake`）对着项目现状算出计划：预演直接返回 `{plan, planDigest}`、零写入；取入在锁内重算计划并照它执行。取入带了 `planDigest` 而重算的不同 → 409 `plan_changed`（附新计划与摘要），零写入——供票 07 的真人确认卡绑定确认时看到的内容。计划与取入成功的应答是同一形状：`{work: {id, title（填充后的值）, created, citeKey, filled（写入的书目字段）}, mainDoc: {before, after, changed}, docs: {taken: [{docId, kind, annotations, stamped}], skipped: [{docId, kind, reason, wouldJoin?}]}, argumentGraph, note}`；摘要是 `{entryId, rev, result}`（`result` 即计划）的 SHA-256。

- **条目与内容检查**：条目被替换 → 409 `changed`（带 `currentRev`）；看不懂的格式 → 409 `incompatible`（绝不改写）；损坏 → 422 `damaged`。只检查要取入的 Doc（注定跳过的 Doc 不检查、不会因它失败）：PDF 元数据合 schema、`doc_id` 相符、`original.pdf` 的字节数与 SHA-256 符合元数据；LaTeX/文本 IR 里的 `docId` 是这个 Doc；文本源合 schema 且 `doc_id` 相符；标注副本合各自 schema（PDF 的还要 `doc_id` 与原件 SHA-256 相符）；论证图合 schema、不是更新的版本。内容对不上 → 422 `entry_invalid`（`docId`/`part`/`problem`；取消那一部分的标注或论证图可以绕开）。`excludeAnnotations` 只认条目里的 Doc 与标注 id（按自有键查，`constructor` 一类名字不会误中），不认识 → 400。
- **锁**：取入的重算与写入在 `libraryLock` 内套 `argumentGraphLock` 的一个同步段里（中间没有 await，其他请求、任务和文件监视都插不进来）。
- **目标 Work**：项目里按 DOI、arXiv、OpenAlex 找同一篇（规范化同文献仓）。恰好一个 → 并入：书目只填库里为空（缺、null、""、[]、{}）的字段（core `fillWorkNarrow`，原始 JSON 窄写，未知键、项目字段、其他 Work 不动），Doc 按条目顺序追加，主 Doc 不变，原本无 Doc 时条目的第一个取入的 Doc 成为主位；cite key 保留。不止一个（如 DOI 命中一个、arXiv 命中另一个）→ 整次 409 `multiple_works`（`workIds`），先在 Library 合并（同导入的 bridge reject，用户 2026-10-23 裁决）。没有 → 新建：id 按 canonicalId（DOI > arXiv > OpenAlex > 标题 slug＋年）从快照推出，已被另一 Work 占用 → 409 `id_taken`（同手动导入，不造后缀）；字段取快照里类型化模型认识的那些，`origin: "manual"`、`added_at` 为取入时间，cite key 按本项目规则分配（有 bibcode 用 bibcode，否则姓＋年避让），`acquisition` 按 `planFor` 现算。
- **笔记**：只在新建 Work 且用户选取时写入；并入时一律不写，项目笔记非空时为 `kept_local`，为空时 `existing_work`。
- **Doc 跳过（本地字节一个不动，`docs.skipped` 说明）**：`exists`（`output/<id>` 已存在，任何类型）、`linked`（某 Work 的 `doc_ids` 已列着这个 id，目录不在——再挂上会让 PDF 归属不唯一）、`annotations_present`（`annotations/<id>/` 已存在，绕过入口删 Doc 后留下的孤儿标注；不覆盖）、`seed_conflict`（见下）。要写的 Doc 正被上传任务写或正被删除（`isDocumentContentBusy`）→ 整次 409 `busy`。
- **下次 `library build` 落回目标 Work（身份焊接）**：库构建对每个 LaTeX Doc 按其 IR 的 DOI/arXiv/标题做 `upsert`（core `seedWorkFor`，从 `seedFromOutput` 抽出、行为不变）。计划在「写入后的库」的类型化副本上按名字顺序模拟同样的 `upsert`，要求只匹配到目标 Work 一个。不是时，按上传路径的做法（core `stampSourceData`，即 `stampSource` 的内存版）把目标 Work 的 DOI/arXiv 写进这份 IR 的 `source`（`acquired_via` 保持原值，Work 详情的来源标签不变），目标 Work 没有这两者时用其标题覆盖 `meta.title`，再模拟一次；只改 `source`/`meta`，sections/blocks、图片、Doc id 与标注不变（它们本不进指纹），文献仓里的条目不改（契约局部修订二，用户 2026-10-23 裁决）。`docs.taken[].stamped` 如实报告。焊接后仍会落到别的 Work、新 Work，或会让构建经 IR 的标题把另一个本地 Work 折叠进目标（bridging）时，不取这个 Doc，记为 `seed_conflict`（`wouldJoin` 为那个 Work，新 Work 为 null）——宁可不取也不让取入引发合并。PDF 与文本 Doc 不按标题 seed，不受影响。
- **标注**：LaTeX/文本 Doc 的副本写成 `annotations/<id>/current.json`；PDF 的副本写回 `output/<id>/annotations.json`；PDF 一律新建 `reading-position.json`（rev 0、`position: null`、绑定原件 SHA-256）；PDF 不带标注或全部取消时新建空 sidecar（rev 0、同一绑定）。没有取消任何一条时写副本原字节（含未知键）；取消了部分时只从原始对象里滤掉那几条，其余键与 `rev` 不变；全部取消时 LaTeX/文本不写文件。计划时对 LaTeX/文本 Doc 用条目内的字节现算内容指纹（core `docContentFingerprintOfFiles`，与磁盘上的算法同一投影）：算得出且与副本的 `content_fingerprint` 不同 → 422 `entry_invalid`（`problem: "stale"`），因为下一次访问会把它们整批归档；算不出（本版本读不了那份 IR）时照项目既有规则原样放下、不碰。取入本身从不归档、不读 archive。
- **论证图**：未选或条目没带分别为 `not_chosen`、`not_carried`；该 Work 已有非空图 → 保留本地（`kept_local`，文件字节不动）；本地图读不了 → 500 `argument_graph_unreadable`（不覆盖）；否则把 `work_id` 改成目标 Work、以本地 rev 写入（`replaceArgumentGraph`，rev+1）。出处指向未取入的 Doc 时只剩显示文字（Q19）。
- **写入顺序与回滚**：先清掉崩溃留下的 `output/.shelf-take-*`、`annotations/.shelf-take-*`（本进程的取入都在一个同步段里，此时不会有别的取入在写；跨进程不支持，I013）。全部 Doc 先写到 `output/.shelf-take-<uuid>/`（`wx`）→ 逐个改名为 `output/<id>` → 标注目录暂存后改名为 `annotations/<id>` → 论证图 → 库（新建用 `saveWorksNarrow` 追加，并入用 `fillWorkNarrow`；json 与 bib 同既有窄写）。任一步失败按相反顺序撤销本次新增（删掉放下的目录、恢复论证图与库文件的原字节、删掉本次新建的空目录），返回 500 `write_failed`；撤销有一步失败时 `cleanedUp: false`，`detail` 说有部分没能删掉（不带路径），否则 `cleanedUp: true`。成功后尽力更新库图缓存（失败等下次刷新）。确实写了东西（新建或补字段、追加 Doc、写论证图）才在锁外广播 `library.changed{add}`，写了论证图时再广播 `argument-graph.changed`；全部跳过、无可补字段、图保留本地的取入不广播。
- **并发范围**：只在本 server 进程内串行；与 CLI 或另一进程同时改同一项目不支持（I013 不扩展）。

## 离线与派生数据

`library build --offline` 已 gate ADS、Crossref、OpenAlex，缓存仍可读；不推断所有 CLI 命令全局断网。DOI stub 富化、摄入缓存命中和 arXiv 恒新鲜 job 各自按路径判断。

库图 `graph.json` 是版本化派生缓存，saved-only 自愈规则见 [discovery](discovery.md)；`library.json` 损坏不能当缓存 miss。metadata 缓存的字节兼容规则见 [engineering](engineering.md)。
