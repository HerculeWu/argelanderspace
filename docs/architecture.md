# 产品与架构

ArgelanderSpace（npm `argelanderspace`，MIT，© Wenjie Wu）是单用户科研工作台。用户通过 webui 独立操作、亲自阅读，也通过 CLI + skills 与 agent 协作。领域语言见 [CONTEXT](../CONTEXT.md)，不可擅改的边界见 [contracts](contracts.md)。

本页记录当前能力和结构，不列待实现任务。产品事实来自 Stage 15 关闭后的记录；阶段结果见 [history](history.md)，新工作由用户决定。

## 能力入口

- **文献库与正文**：arXiv LaTeX / 本地源码摄入，条目内 LaTeX zip 挂载；现支持 Work 内不可变本地 PDF 上传、阅读、原件下载、设主与删除。Web 添加时的 arXiv 获取仍只处理 LaTeX 源码。身份、存储规则及获取场景见 [library](library.md)。
- **文献发现**：从详情页进入 ADS related/useful 临时探索；库图只含已存 Work。边义、失败语义、缓存与用户状态分离见 [discovery](discovery.md)。
- **阅读器**：LaTeX Reader 用共享 IR/标注及共同 epoch；本地 PDF 使用固定 EmbedPDF 2.15.1、同次 hash 校验的原始 bytes 和独立用户 sidecar，PDF 内嵌标注只读。PDF 基础分页/缩放/下载已接入，PDF 工作台标注编辑、搜索/目录和进度保存不属于此边界。LaTeX 规则见 [annotations](annotations.md)，PDF 数据保护见 [contracts](contracts.md)。
- **论证图**：Work 级项目数据（每个 Work 至多一张，不是 Doc，存于 `<dataDir>/argument-graphs/`），是文献页内与「探索相关文献」同级的模式，入口在 Work 详情与 Reader 顶部；论证为 Toulmin 六字段加种类与出处，边带角色，审计现算不落盘。页面可从空图手动整理；外部 agent 经 CLI `argument get` / `argument put` 整图读写（skill `argelander-argument-graph`），Copilot 经 `argument` 工具编辑，整图替换/清空须经真人确认卡。数据保护见 [contracts](contracts.md)，机制见 [argument-graph](argument-graph.md)，取舍见 [ADR 0009](adr/0009-argument-graph-work-owned.md)。
- **计划页**：默认 landing，plans→tasks 的列表/看板/时间线/今日聚焦，webui 可独立 CRUD。详细模型和否决项见 [plans](plans.md)。
- **Writer**：独立稿件、八型 cell、CodeMirror、显式 Render/Shift+Enter、共享编译→IR 预览及源码 zip；不展示 PDF。工作流见 [writer](writer.md)，文件协议沿用 [writer-data-model](writer-data-model.md)。
- **web i18n**：zh-CN/en，默认中文、不探测浏览器，设置页与标题栏的外观速调即时切换；语言与其余界面偏好存在 `config.toml` 的 `[ui]`，经设置接口读写，浏览器本地存储只留一份不作权威的副本（desktop-app 票 10，见[设置接口、文件监视与界面偏好](#设置接口文件监视与界面偏好desktop-app-票-10)）。server detail/job.error 和用户数据不纳入翻译；CLI 不变。
- **尚未完整的写路径**：文献 note tab 当前只读；持久 note/label 主要通过 CLI，右键色点 overlay 仅会话级。这是能力缺口，不推翻独立应用定位。
- **不在 main**：OCR/出版商 HTML 摄入封存于 `ocr-features` 快照分支。现行 PDF 是不可变原文件阅读，不是 OCR/LaTeX 转换能力。

## 数据与配置

默认项目级 `./literatures`，只按 cwd 相对解析，不向上查找。优先级：

`--data-dir` > config.toml `data_dir` > `./literatures`。

config.toml 的 `data_dir` 只接受相对路径，写绝对路径是配置错误（点名该键、不回显值）；`--data-dir` 是单次显式覆盖，可以给绝对路径。

工作台的配置只有一个来源：`config.toml`，加命令行参数（`--data-dir`、`--port`）作单次覆盖。工作台自己的环境变量（数据目录、端口、全局数据目录、全局缓存目录、web dist 位置）自 2026-10-13（desktop-app 票 05）起不再读取，设置了也不起作用；操作系统自己的变量（`XDG_CONFIG_HOME` 等）照旧。OpenAlex 的 key 的环境变量不在这次改动内（只有空白的值当作没设，desktop-app 票 12）；ADS token 自 desktop-app 票 12 起只从凭据存储读取，环境变量 `ADS_DEV_KEY`、config.toml 的 `ads_dev_key` 与 `~/.ads/dev_key` 都不再生效（见下文「凭据存储」）；联系邮箱原先的环境变量 `OPENALEX_MAILTO` 自 desktop-app 票 11 起不再读取（见下文「联系邮箱」）。默认端口 1859 是 contracts 的常量 `DEFAULT_PORT`，CLI 深链接、`serve` 与 web 的开发代理共用。

配置通常在 `~/.config/argelanderspace/config.toml`，支持 XDG_CONFIG_HOME；未知键忽略，已知键类型错只报键名、不回显值。`auto_ingest_arxiv` 默认 true：添加带 arXiv 号的文献时自动获取 arXiv PDF（语义见 library）；设置页「项目」组有它的开关「添加文献时自动获取 arXiv PDF」（desktop-app 票 11 起，不再是隐藏设置；开关名是用户 2026-10-14 的裁决，键名不变）。`[ui]` 分组（`language`、`theme`、`accent`、`density`、`labels`）是界面偏好的权威位置，设置页与标题栏的外观速调都改它（desktop-app 票 10）。`log_level`（`debug` / `info` / `warn` / `error`，默认 `info`）是用户日志的最低级别，见[用户日志](#用户日志)。`contact_email` 是 Crossref 与 OpenAlex 请求所带的联系邮箱，唯一来源就是这个键（见下文「联系邮箱」）。完整的键表、严格与宽松两种读取、按行修改与写入见本节末的 [Settings 的 schema、两种读取与按行修改](#settings-的-schema两种读取与按行修改desktop-app-票-09)。

**全局数据**（[ADR 0007](adr/0007-global-data-scope.md)，2026-10-06 决定；目录解析已在 infra 实现，Mail 账户已使用）：属于用户本人、跨项目共享的数据（首个使用者是 Mail 账户）不放 dataDir。全局数据与可丢弃的全局缓存分开，按 `env-paths`（name `argelanderspace`、无 suffix）取各 OS 标准目录：Linux `$XDG_DATA_HOME`/`$XDG_CACHE_HOME`（默认 `~/.local/share`、`~/.cache`），macOS `~/Library/Application Support`、`~/Library/Caches`，Windows `%LOCALAPPDATA%\argelanderspace\Data`、`…\Cache`。覆盖优先级 config 键 `global_dir` > OS 默认；全局缓存对称：`global_cache_dir` > OS 默认，两者互不影响（改数据目录不移动缓存）；只认 config.toml 的键，不认环境变量（2026-10-13 起，desktop-app 票 05；此前各有一个优先于 config 的环境变量）。空白值视为未设，相对路径一律拒绝（ConfigError，只报键名；按探测到的平台判断绝对路径，避免随 cwd 分裂全局目录）；`global_dir`/`global_cache_dir` 类型错只报键名。`resolveGlobalDirs` 不访问文件系统（未传 config 时读 config.toml）；OS 默认目录由 env-paths 在 import 时固定 homedir，测试隔离须在导入前把 `HOME`/`XDG_*` 指向 tmp；目录由 `ensureGlobalDirs` 按需创建，权限 0700（infra `global-dirs.ts`）。既有 config.toml 位置不变，项目数据不迁移。

**凭据存储**（Mail 票 02，ADR 0008；infra `credential-store.ts`，Mail 账户服务与 ADS 凭据已调用）：按「用途加标识」寻址（desktop-app 票 12）——一个存储对象服务一种用途：`mail`（默认，邮箱密码，标识是账户 id）或 `ads`（ADS token，标识固定为 `ADS_TOKEN_ID` = `token`，`createAdsCredentialStore`）；每种用途有自己的钥匙串服务名（`argelanderspace.mail`、`argelanderspace.ads`）与自己的后备文件（`credentials.json`、`ads-credentials.json`，同在全局数据目录、同一格式与派生方式，派生标签按用途区分），所以两种用途的读写互不干扰，ADS 的写入不会重写邮箱密码的文件；`mail` 用途的服务名、文件名、文件格式与密钥派生与泛化前逐字节相同，已保存的邮箱密码不经迁移即可读到（`credential-store-purpose.test.ts` 按泛化前的写法造数据钉住）。钥匙串后端的方法多带一个 service 参数（`get(id, service)` 等），由存储按用途传入。窄接口 `get/set/delete(id)`，加 `status(id)`（票 12：已存与否、在钥匙串还是文件、这次钥匙串有没有应答，从不返回值；为分辨损坏的文件条目会解密一次，值随即丢弃）；`CREDENTIAL_STORE_METHODS` 列出接口的全部方法，包装（server 的 `observedCredentials`）按它生成，新增方法不写进去就编译不过，不会被包装静默丢掉。后端 `@napi-rs/keyring`（MIT，service 按用途，原生模块惰性加载，失败按“不可用”处理；Linux 上 Entry 显式固定 `{linux:{store:"secret-service"}}`，否则绑定会静默回退到内核 keyutils（仅内存、重启即失），固定后无 Secret Service 时构造抛错即“不可用”；app 包将其列为运行时依赖，因原生 `.node` 不可内联）且可注入。钥匙串任何失败都返回 `keychain-unavailable`，不自动降级；仅当调用方传 `{ fileFallbackConsent: true }`（严格 `true`，表示用户已在 UI 同意）才写全局数据目录下该用途的后备文件——邮箱密码是 `credentials.json`，ADS token 是 `ads-credentials.json`（两者都是 0600，tmp+rename 原子替换，AES-256-GCM 轻度加密，密钥由文件内盐与本机用户名/主机名派生，只防误看，不防同用户读取），结果带 `keychainProtected:false` 供 UI 持续标示。读取时钥匙串优先、其次文件；钥匙串可用后再 `set` 会迁入钥匙串并移除文件副本。钥匙串写成功后若旧文件副本无法移除，结果带 `staleFileCopy:true`；钥匙串不可用但文件副本已删时 `delete` 返回 `{status:"deleted", keychainUnavailable:true}`（钥匙串里可能仍有副本，未检查）；文件重写失败为 `file-write-failed`。失败结果只含状态码（`invalid-input`/`file-unreadable`/`file-write-failed`），不含异常消息或密码；唯一含密码的是成功 `get` 的返回值，调用方不得日志/广播/回显。跨进程：文件读-改-写同刻并发写不同账户可能丢一次写（后写者胜），按 ADR 0007 的要求在此明示并同步写入 contracts，可接受（用户重输一个密码）。账户 id 在文件中以 Map 保存，`__proto__` 等同普通键。

**Mail 账户**（Mail 票 04，ADR 0007/0008；infra `mail/account-store.ts`、`mail/protocol.ts`，server `mail-accounts.ts`/`mail-routes.ts`，contracts `mail.ts`；账户添加/重输密码/移除的最小 Web UI 随票 05 在 Mail 页内，设置编辑等另票）：账户列表是全局数据 `<globalDir>/mail/accounts.json`（`{version, rev, accounts}`，不含密码；每个账户有 id `acc-<12 hex>`、显示名、地址、preset、IMAP/SMTP 主机端口加密方式 `tls|starttls`〔不接受明文〕、两个登录名、`credentialRef`（＝id，凭据存储键）、`credentialProtection`（`keychain|file`，`file` 即未受钥匙串保护，UI 持续标示））。每次修改在 proper-lockfile 跨进程锁（`accounts.lock`）内读—比对 `rev`—写（tmp+rename，0600，rev+1）；rev 不符抛冲突、一字节不写，REST 回 409 `rev_mismatch` 带当前 rev；文件损坏/校验失败为 500 且不覆盖。预设（Gmail/iCloud/自定义，主机端口见 contracts `MAIL_PRESETS`；大学、研究所等其他邮箱一律走自定义，不按机构单列预设，2026-10-09 用户决定）只补全省略字段，显式字段优先；iCloud IMAP 登录名取地址 @ 前部分、SMTP 取完整地址。协议库 imapflow 2.2.7（MIT）与 nodemailer 10.0.15（MIT-0）只在 infra `protocol.ts` 内引用，窄接口 `MailProtocol.verifyImapLogin/verifySmtpLogin` 只返回失败码（`auth_failed`/`host_not_found`/`connection_refused`/`timeout`/`tls_failed`/`starttls_unsupported`/`protocol_error`/`unknown`），库的错误文本与服务器应答一律丢弃；要求 STARTTLS 而服务器不支持时失败，绝不退回明文登录；证书默认严格校验。REST（`/api/mail`，同 provider 的 CSRF 守卫，`no-store`）：`GET /presets`、`GET /accounts`、`POST /accounts/test`（只测不存；`accountId` 且无密码时用已存密码）、`POST /accounts`（先分别测 IMAP 与 SMTP，任一失败 422 `connection_failed` 带两协议各自结果且不保存；钥匙串不可用且无 `fileFallbackConsent` 为 422 `keychain_unavailable`；同地址重复 409 `duplicate_address`）、`PUT /accounts/:id`（body 带 `rev`；连接参数或密码变更才重测，仅改显示名不连接；密码在 rev 校验通过后才写入凭据存储）、`DELETE /accounts/:id?rev=`（锁内先删凭据，再删账户记录，再删 `<globalCache>/mail/<id>`；绝不连接远端，不触碰远端邮件；凭据无法确认已删除〔钥匙串不可达/凭据存储出错〕时拒绝删除并保留账户，可重试；缓存删除失败只带 `cache_not_removed` 警告）；`POST /accounts/test` 用已存密码时，主机端口加密方式与登录名必须与已存账户一致，否则 400，避免已存密码被送往任意主机。错误体只含固定文案与字段名，不含密码、用户名、主机应答或 zod 消息。并发范围见 [contracts](contracts.md)：账户配置是跨进程安全的（上述锁+rev），缓存不加锁。

**Mail 实时更新与未读角标**（Mail 票 08；contracts `mail-events.ts`，infra `mail/inbox-watch.ts`〔`MailInboxWatcher`，imapflow 仍只在 infra `mail/` 协议文件内〕，server `mail-watch.ts`/`mail-watch-routes.ts`/`mail-watch-default.ts`，web `src/mail/mailLive.ts`/`MailNavItem.tsx`）：每个 server 进程对每个账户只保持**一条** INBOX 连接（只读 SELECT；服务器通告 IDLE 则 IDLE，每 9 分钟重启，否则每 60 秒 STATUS 轮询），收到 EXISTS/EXPUNGE/FLAGS 即在**已选中的 INBOX 内**取快照（总数＝选中邮箱的 EXISTS，未读＝`SEARCH UNSEEN`；RFC 3501 §6.3.10 不建议对已选中邮箱用 STATUS），轮询模式（不 SELECT）才用 `STATUS (MESSAGES UNSEEN UIDVALIDITY)`；快照连同“自上次以来推送了哪些事件”交给 server，server 与上次比较后经 `/ws` 推 `mail.changed`（`accountId`、`cause: inbox|flags|state`：`inbox`＝邮箱内容变化〔新邮件/EXPUNGE/总数或 UIDVALIDITY 变〕，`flags`＝服务器推送了标志变化（已读/星标等）而内容未变，**即使未读数没变也推**，`state`＝只有 watch 状态变或连接后的首次快照、INBOX 未读数、watch 状态、时间；不含邮件内容、地址或服务器文本）。其他文件夹的变化不推送，刷新时才见。watch 状态：`connecting|idle|polling|offline|auth_failed|credential_missing`。断线按指数退避重连（2 s 起、翻倍、上限 5 分钟，±20% 抖动；连接稳定 ≥30 s 才重置），重连后的首个快照与断线前比较，错过的新邮件会报告；**只有真正的凭据拒绝才算 auth_failed 且不重试**（响应码 AUTHENTICATIONFAILED/AUTHORIZATIONFAILED，或 NO 无响应码；`UNAVAILABLE`/`LIMIT`/`INUSE`/`SERVERBUG` 临时码，以及无码/`ALERT` 且文本只谈连接数〔simultaneous、too many connections/sessions、connection limit〕并且**不含**密码/凭据/登录失败/尝试次数/锁定等字样的拒绝归为可退避重试，watcher 内以 `protocol_error`＋`temporaryRefusal` 表示，不改读路径的失败码语义；**连续 3 次**临时拒绝（中间无成功连接）也转为 auth_failed 并停止），直到账户文件 rev 变化；凭据缺失（credential_missing）按同一退避重试，rev 变化时也立即重启。账户增删改由 server 每 5 秒对照 `accounts.json` 并在账户路由成功后立即对账：只启停/重启受影响账户的连接，`stop()`（`server.close()` 先等它）中止全部连接与定时器；多进程各自连接、互不协调。`GET /api/mail/unread`（`{version,accounts:[{accountId,unread,watch}],total}`）给角标与重连补读；`total` 只计未处于 `auth_failed/credential_missing` 的账户的 INBOX 未读（离线账户保留最后一次的数）。`createServer` 默认**不**启动 watcher（测试服务器因此绝不读真实全局账户），只有 `startServer` 传 `mailWatch:true`。Web：`mailLive.ts` 是整页唯一的实时画面，Shell 的 Mail 入口显示数字角标（>99 为 99+，可访问名称含未读数）；Mail 页把自己新取到的 INBOX 未读与登录失败账户回报给它，使角标与文件夹树同数；`mail.changed`（非 `state`）与 WS 重连后，Mail 页静默重载文件夹树与可见 INBOX 列表（最新页替换、已加载的更旧页保留，失败不显示错误）。无系统/浏览器通知。

**Mail 写信与发送**（Mail 票 07，ADR 0008 / 规格 Q16；contracts `mail-compose.ts`，infra `mail/outgoing.ts`〔`composeMail`＝nodemailer MailComposer；`MailOutgoing`：`saveDraft`/`deleteDraft`/`appendSent`/`sendSmtp`，imapflow/nodemailer 仍只在 infra 邮件文件内〕，server `mail-compose.ts`/`mail-send.ts`/`mail-outbox.ts`/`mail-compose-routes.ts`，web `src/mail/compose-session.ts`〔写信会话：自动保存、发送与撤销、结果报告、留在本标签页的文字；非 React〕/`MailCompose.tsx`/`ComposeWindow.tsx`）：只发纯文本正文（富文本不在第一版）。**草稿**存在服务器 Drafts 文件夹（APPEND，标志 `\Draft \Seen`），身份是 Message-ID（客户端生成 `<uuid@账户域名>`，之后每次保存、最终发送都用它）；保存＝先 APPEND 新副本，再只删除同 Message-ID 的**更旧**副本（uid 更小者），所以两次竞争保存最坏留下两份、绝不会零份。Drafts/Sent 文件夹先按 special-use（`\Drafts`/`\Sent`），再按常见名称查找，找不到 Drafts 则拒绝（`drafts_unavailable`，不发送）。回复/全部回复/转发/编辑草稿的初始内容由服务器按原信源生成（`POST init`）：回复收件人＝Reply-To，否则 From（原信是自己发的则取原收件人）；全部回复再加原 To/Cc，去重并去掉自己；`In-Reply-To`＝原 Message-ID，`References`＝原 References＋原 Message-ID；主题加一次 `Re:`/`Fwd:`（同族前缀不叠加）；回复引用 `> ` 逐行，光标在引用之上；转发带“转发的邮件”头与非内联附件（暂存为待发附件）；只有 HTML 的原信用去标签文本引用。**附件**先上传到暂存区 `<globalCache>/mail/_staged/<attId>.bin|.json`（可丢弃缓存，不挂在某个账户目录下，因为写信时可以更换发件账户而附件要跟着草稿走；缺失在发送/保存时报 `attachment_missing`，用户重新添加；发送成功/放弃草稿时删除，其余 7 天后清扫；编辑 Drafts 里的草稿或转发时，原信的非内联附件被暂存到这里），单个 ≤ 40 MiB、整封 ≤ 50 MiB、≤ 50 个；界面按编码后约 4/3 估算大小，超过服务商文档上限（Gmail 25 MB、iCloud 20 MB，未在本票联网复核；自定义未知）时显示警告但不阻止，真正的拒绝由服务器给出（`message_too_large`，草稿保留）。

**发送与 8 秒撤销**（`POST /api/mail/compose/accounts/:id/send`，body `{sendId, draft}`，202）。服务器按下列顺序执行，这个顺序就是“无重复发送、不丢信”的论证：①对该 Message-ID 取独占 claim：先过进程内守卫（`账户+Message-ID` 集合，缓存目录被删时仍有效），再在缓存里 O_EXCL 创建 `outbox/claim-<hash>.json`；已有 claim 的持有者进程不存在、或属主 pid 相同而 boot id 不同（pid 复用）、或超过 10 分钟，视为陈旧并替换；**无法解析的 claim 若 mtime 在 5 秒内按“对方正在创建”视为 live**，更旧的当垃圾。已被占用回 409 `already_pending`；同一 `sendId` 再次提交（双击、重试，含并发）合并为同一次发送；持有 claim 后再查 **sent 守卫**：该 Message-ID 在 7 天内已被 SMTP 接受过则回 409 `already_sent`（应答丢失后换新 `sendId` 重发、迟到的旧请求、另一个标签页里同一草稿都在这里被拦下）。claim 与 sent 守卫都以**“账户＋Message-ID”**为单位，只在同一发件账户内成立：换一个账户发送同一草稿不受它们约束，所以写信窗在应答未确认期间锁定发件人（见下文前端）；②把**最终版**邮件存进 Drafts（失败则不进入窗口，什么都没发；进入前后两次确认账户仍存在，已删除的账户不会被重建缓存目录）；③严格写标记 `outbox/<sendId>.json`（状态、属主 pid 与进程 boot id、截止时间；写不下去也不进入窗口）并启动**内存里**的计时器（`unref`）；④窗口内 `POST …/sends/:sendId/undo` 清计时器、释放 claim、标记 `cancelled`，草稿原样在 Drafts；⑤到点：属主进程**严格写入** `sending` 标记（写不下去就不发，标 `failed/storage`），做**一次** SMTP 事务（SMTP 永不自动重试），成功后先记 `sent` 并写 sent 守卫（`outbox/sent-<hash>.json`，另有进程内副本；写在释放 claim 之前，所以 claim 与 sent 守卫首尾相接、中间没有空档；清理完成后再写一次，记下 Sent 副本的结果。**磁盘写入是尽力而为**：邮件此时已经发出，写不下去不会让发送失败，但那样守卫只存在于本进程内存里，另一个进程和重启后的进程都看不到它），再决定是否 APPEND 到 Sent（`mailServerSavesSent(account)`：账户可选字段 `serverSavesSent` 优先，缺省取 preset 默认 `MAIL_SERVER_SAVES_SENT`——Gmail 为 true〔其 SMTP 自动保存，不重复〕，其余默认 false，iCloud 未经实测；旧账户文件无该字段仍兼容；用户在添加账户对话框或账户⋯菜单“设置”里改，走带 rev 的 PUT，省略该字段的编辑保留原值）并删除 Drafts 副本；清理完成前对外仍报 `sending`；Sent 副本存不下时保留 Drafts 副本并如实告知。收件人被部分拒绝时邮件已发给其余人，计数告知；全部被拒为 `recipient_rejected`。失败（definite）时草稿仍在 Drafts，界面把原文放回写信窗并给出原因。

**SMTP 结果的判定按协议阶段，不按错误文本**：infra 用 nodemailer 的协议跟踪只读取一个事实——客户端已发出 `DATA` 命令（或服务器对它回了 `354`）；之所以以命令发出为界，是因为从那一刻起断线就无法与“已接受、应答丢了”区分。该日志不保存、不记录任何其它内容。`DATA` 之前的任何失败（连接、TLS、认证、MAIL/RCPT 被拒或断线）都是确定未发出；`DATA` 之后若没有服务器应答（断线、超时、TLS 错误文本都算）一律为“结果未知”（`outcome_unknown`，状态 `unknown`，草稿保留，不重试）；服务器给出了应答码（552/5xx/4xx）则是确定的失败。测试覆盖 RCPT 后断线（确定）与 DATA 后断线（未知）。

**窗口内 server 退出（Q16）与优雅关停**：邮件在步骤②已在服务器 Drafts，窗口不读标记也不会发送；重启后没有任何东西会据标记补发。标记只用于如实报告：属主已不存在的 `pending` 报告为 `interrupted`（未发出、已在草稿、不自动补发），`sending` 报告为 `unknown`（窗口已过，可能发出也可能没有，请先查“已发送”，同样不补发）。**优雅关停**：`createServer().close()` 的第一件事（同步）是 `disposeMailSendServices()`：清除所有计时器、置关停守卫（到点触发器与新的发送都直接拒绝）、把仍在窗口内的发送标记为 `interrupted` 并释放 claim——因此关停期间有慢请求或 Copilot run 要等，窗口也不会在这段时间里变成发送；已交给 SMTP 的发送不被打断。只有属主进程会发送；另一个 server 进程只能观察（`ownedElsewhere`），撤销/关闭该发送回 409 `owned_elsewhere`，对同一草稿再发送回 `already_pending`。页面刷新后 `GET /api/mail/compose/outbox` 列出仍需用户注意的发送（窗口内、发送中、failed、interrupted、unknown，以及**尚未被页面确认的近期 sent**，所以用户不在页面时成功发出的邮件，回到 Mail 页也能看到结果），界面据此恢复倒计时或显示结果；用户关闭/确认时 `DELETE …/sends/:sendId` 才忘记该标记（普通的已确认 `sent` 一小时后清扫；带有需告知结果的 `sent`——没有 Sent 副本、有被拒收件人、Drafts 里留有副本——与其它问题一样保留到页面确认，最长 30 天）。内存里的完成记录释放邮件字节并在 10 分钟后淘汰。

**窗口内的草稿被冻结**：对正在发送的 Message-ID，`PUT draft`、`discard`、以草稿模式 `init` 都回 409 `already_pending`（检查在草稿锁内，排在它之前的保存先完成），避免“发出旧版并删掉新编辑”；撤销后恢复可编辑。**已发出的 Message-ID**（sent 守卫期内）`PUT draft` 回 409 `already_sent`，不把已发出的信放回 Drafts（否则又能从那里再发一次）；`discard` 仍允许，用来删掉清理失败时留在 Drafts 的副本；以草稿模式 `init` 打开这样的副本时响应带 `sent: {sentCopy}`（`failed`/null 表示这份副本可能是所发内容的唯一记录）。超过 7 天的 sent 守卫随 outbox 清扫删除。

**为什么标记在全局缓存而不是全局数据，及其代价**（ADR 0007 判断）：进入窗口前最终邮件已在远端 Drafts（远端为权威），所以标记丢了不会丢邮件；它不是用户数据，不需要保全规则，删除账户会连同缓存目录清掉其标记。**代价必须说清：缓存目录被整体删除时，claim 与 sent 守卫文件随之消失，跨进程互斥失效。** 同一进程内仍有内存守卫（claim 与 sent 守卫各一份）；但若此时另一个 server 进程对同一草稿发起发送，两个进程可能各自进入窗口并各发一次（重复发送），重启后的“未发出”提示也会丢（草稿仍在服务器）。这是用户主动删缓存目录且恰好多进程并发发同一草稿时才会遇到的剩余窗口，没有额外加锁。其余已知剩余窗口：①claim 从取得到释放覆盖**“最终版存草稿（APPEND）＋撤销窗口＋SMTP 事务＋Sent 追加与 Drafts 清理”全程**，而它的 10 分钟陈旧期从取得 claim 时算起；这一整段若超过 10 分钟（大附件 APPEND 慢、SMTP 慢、清理慢都算），属主仍活着时另一进程也会把该 claim 当作陈旧而接管。接管发生在 SMTP 接受之后的，会被 sent 守卫拒绝；发生在之前的，同一草稿可能被第二次发送；②三个进程同时判定同一陈旧 claim 并先后删除/创建（仅发生在同刻发送同一草稿且上一属主刚崩溃时）。

**暂存附件**不属于账户目录，因此删除账户**不会**清掉它们；靠 7 天清扫（server 启动时扫一次，暂存新附件时也扫）以及发送成功/放弃草稿时的删除。**前端**：同时可有多条发送各自倒计时与撤销；撤销/SMTP 失败要恢复写信窗时，若用户正在写另一封，不替换它，而是给带“打开”的通知（打开前先把当前稿存到服务器，存不下则保留）；撤销遇 409 先查真实状态再报告；服务器暂时不可达时倒计时归零后显示“正在重新连接，尚不知道是否发出”；离开 Mail 页卸载时先把未存文字存到服务器（正在发放弃请求的窗口除外）；存不下的文字（连同写信窗状态）保存在本标签页的 sessionStorage（`argelander.mail.leftBehind`），每次进入 Mail 都以通知如实说明并提供“打开”恢复，不自动弹出；**显示通知不等于取走**：只有用户点“打开”且写信窗真正接管，或明确关闭该通知并在确认框里确认丢弃后，才从 sessionStorage 删除该条（每条记录带版本：“打开”只删除它接管的那一版，等待期间若迟到附件并入成了新版，新版保留并继续提示；确认丢弃按记录 uid 删除所有版本），因此不点“打开”就离开或刷新，下次仍在；页面挂载时产生的记录也先写入 sessionStorage 再显示。sessionStorage 只属于该浏览器标签页：关闭标签页即消失；浏览器的“复制标签页”或会话恢复可能把它一并带到新标签页（两个标签页都会提示同一段文字）。**发送请求进行中离开** Mail 页：该请求若随后失败（窗口没打开），尽力把原文存进 Drafts，并同样留在本标签页、下次进入时说明“没有发出”（存进了 Drafts 或没能存进）；若请求没有应答，只说“不知道是否正在发送”，绝不说“没有发出”。**附件上传按发起它的写信窗 uid 回写**：上传未完成时关闭写信窗不关闭并提示“仍在上传”；上传中放弃草稿，完成后删除该暂存附件（从确认放弃起，包括等待在途保存期间，离开 Mail 页都不补存该窗口）；上传中离开 Mail 页，完成后**不再写服务器**——服务器上的草稿可能已在别处（回到 Mail 后、另一个标签页）改过，又没有版本检查，用离开时的旧快照加附件去 PUT 会覆盖较新的文字；所以若该窗口的文字本来就只留在本标签页（离开时没存成），附件并入那条记录，否则删除暂存附件并留下通知“没有加入，请从草稿箱重新添加”；其它情况窗口已不在时删除暂存附件并通知“没有加入任何邮件”——永远不会落到另一封信里。**已发出的信**（发送时得知已发出、保存回 `already_sent`、或打开的是已发出信在 Drafts 的残留副本）：写信窗显示“已经发出，不能再发送或保存”并提供“复制为新邮件”（新 Message-ID，保留文字；附件只有从 Drafts 残留副本重新暂存的才带上，发送后服务器已删掉的暂存附件不带，并在窗内提示需重新添加），发送禁用、不再自动保存；关闭不受阻拦，之后的修改记入本标签页（与离开时一样，关闭其通知需确认）并以“作为新邮件打开”提供；离开 Mail 页时这些修改只记一次（不尝试保存）；放弃时说明“已发送”中是否有副本，没有或不知道时以 danger 明确警告这份可能是唯一记录。草稿保存的结果同样只回写发起保存的窗口；放弃草稿先等在途的保存结束，再按其结果决定是否向服务器发放弃请求（保存应答丢失也发）。**发送应答丢失**（网络错误，请求可能已到服务器）时，其 `sendId` 绑定在该写信窗上，并在弄清之前锁定发件人（claim 与 sent 守卫只在同一账户内成立）；再次发送前先查它的状态：在窗口内或正在发送就并入它（内容已改则提示之后的修改不在其中，可撤销后再改），已发出则不再发送并在窗内说明，结果未知（含 `failed` 且 `outcome_unknown`）则报告且本次不发，其余 failed/interrupted/cancelled 才继续，服务器查无此发送（404）也继续——此时旧请求若仍在准备，它持有 claim，新的 `sendId` 只会得到 `already_pending`；状态查不到（仍不可达）则不发送。内容未变的重试仍复用同一 `sendId`。倒计时、撤销应答和状态查询可能先后结束同一次发送，结果只报告一次。写信窗按“有无服务器没有的改动”判定能否关闭：保存后再输入的改动、被取消的延迟保存都算；发送请求进行中窗口被锁定（不可关闭/编辑/换发件人，“打开”恢复入口无效），发送结果只回写发起它的那个写信窗（按窗口 uid），其窗口已不在则以通知＋“打开”恢复；任何新窗口（含回复/转发的初始内容）遇到已打开的写信窗时都只以通知提供。附件大小提示只对有已知服务商上限的预设显示（Gmail 25 MB、iCloud 20 MB）；自定义无已知上限，不显示大小警告，只有服务器的拒绝才会让发送失败（草稿保留）。离开 Mail 页面不会取消服务器端的发送，也无法再撤销；回到 Mail 页时由 outbox 列表显示结果或中断警告。**已知限制（多标签页）**：两个浏览器标签页（或两个工作台进程的页面）同时编辑同一封草稿（同一 Message-ID）不受支持：自动保存互相覆盖，后存者胜，另一页的修改被替换而没有提示；两边同刻发送由 claim 拦下（`already_pending`），一边发出后另一边再发或再存由 sent 守卫拦下（`already_sent`，7 天内；缓存被删后只剩各进程内的副本）；“留在本标签页”的文字只在离开时的那个标签页里。

`global_dir` / `global_cache_dir` 标「需重启」是用户 2026-10-14 的裁决，与获批原型有一处差别（原型这两行没有重启徽标）。原因：这两个键多数使用方每次调用时现读，只有日志目录在启动时固定，运行中改会让全局数据分到新旧两处。

**机密键**：`SECRET_SETTING_KEYS` 是带机密标记的键，`isSecretSetting(键)` 判断单个键。`redactSettingsValues(values)` 把一份 `SettingsValues` 变成可以交给页面或写进报告的样子：返回 schema 全部键（schema 顺序）的新对象，机密键的位置是 `{ secret: true, set: 布尔 }`，不含值；其余键的值原样。`set` 为假指没设，或设成了空串 / 只有空白的字符串。使用方与此一致（desktop-app 票 12）：`readOpenAlexApiKey` 把只有空白的 `openalex_api_key`（或环境变量）当作没设，请求里不带它，只有空白的环境变量 `OPENALEX_API_KEY` 也不再盖住配置里的 key；这是用户 2026-10-14 的裁决（保留这处修正，设计访谈「明确不动 OpenAlex key 的读取方式」的局部修订，范围只限空白值，非空的值照旧原样使用）；`ads_dev_key` 已不再被读取。`evaluateSettings` 与两种读取的返回不变，仍带机密键的值（`sources` 仍读 `openalex_api_key`；`ads_dev_key` 自票 12 起没有使用方）；凡是要把设置值送出读取它的进程的地方（票 10 的接口）都必须先过这个函数。

分组名是设置页九组里的六个（另三组 copilot、mail、cli 没有配置键）。「需重启」「界面」两列描述的是设置页该怎样呈现，接上行为的是后面的票：例如 `log_level` 今天只在启动时读一次。`[ui]` 的取值与默认值和页面现有偏好（`argelander/theme.ts`、`i18n.ts`）相同，web 的 `tests/settings-schema-parity.test.ts` 在两边不一致时变红。未知键与未知表照旧忽略。

值的校验（`checkSettingValue`）只给原因类别，从不带值：`wrong_type`、`out_of_range`、`not_one_of`、`must_be_relative`、`must_be_absolute`、`must_be_email`（票 11）。「绝对路径」指 POSIX 写法或 Windows 写法任一种下是绝对路径（与 `node:path` 的 `posix.isAbsolute || win32.isAbsolute` 相同，有测试对拍）。`data_dir` 只要求「不是绝对路径」：`""` 合法并解析为 cwd，`"~/lit"` 是名为 `~` 的相对目录，这是既有行为，schema 照实描述。

**两种读取**（infra `config.ts`）：

- **严格**：`parseConfigToml` / `loadConfigFile` / `getConfig`，CLI 的命令用它（`serve` 自 desktop-app 票 10 起不用，见下文「`serve` 的启动与运行中的读取」）。已知键的第一处错即抛 `ConfigError`，点名键、不回显值。文案与一个文件有多处错时报哪一条的顺序和 schema 出现之前逐字相同：各字符串键的类型（`data_dir`、`openalex_api_key`、`ads_dev_key`、`global_dir`、`global_cache_dir`）→ `port` → `auto_ingest_arxiv` → `data_dir` 的相对路径规则 → `log_level`；之后才是新键，按 schema 顺序：`contact_email`、`tex_dir`、`ui` 不是表（`"ui" must be a table`）、`ui.language`、`ui.theme`、`ui.accent`、`ui.density`、`ui.labels`（键写作 `"ui.theme"`；句式与旧键相同：`must be a string` / `must be a boolean` / `must be one of …` / `must be an absolute path`；`contact_email` 不合邮箱形态时是 `"contact_email" must be an email address`，票 11）。`global_dir` / `global_cache_dir` 是否绝对仍在解析目录时按本机平台判断（`global-dirs.ts`），严格读取不查。返回值是文件里写的原值（空白字符串原样返回）。
- **宽松**：`readSettingsText` / `readSettingsFile`，供设置接口用，从不抛出。返回每个键的生效值（文件里的合格值，否则默认值；「空白视为未设」的键写了空白时也是默认值）、每个值来自 `default` 还是 `file`、文件里出现了哪些已知键（据此可知 `ads_dev_key` 是否还在）、文件状态（`missing` / `read` / `unparseable` / `unreadable`）和问题清单。问题清单的每一项是「键名（或表名 `ui`，或表示整个文件的 `null`）加原因类别」：上面五种值的类别，加 `not_a_table`、`unparseable`、`unreadable`。清单里没有值、没有解析器的原句（它会引用文件内容）、也没有未知键的名字。文件无法解析或读不了时全部用默认值，只有一项整个文件的问题；文件不存在时没有问题。

**字节序标记**：文件开头的一个 U+FEFF 在三处读取里一致地被跳过——严格读取、宽松读取、`configFileKeys`——按行修改也跳过它并原样保留。只跳过开头的一个：紧跟其后的第二个 U+FEFF 仍是 smol-toml 不接受的内容（严格读取报 `invalid TOML`，宽松读取是 `unparseable`）；字符串里的 U+FEFF 是值的一部分。文件别处的 U+FEFF 怎么读由解析器决定，与本条无关：smol-toml 在裸数字之后和注释里接受它（见下面按行修改的「裸值」一条），在其余位置不接受。严格读取跳过它是用户 2026-10-14 的裁决（此前带标记的文件对严格读取是 `invalid TOML`），这是严格读取相对 schema 出现之前唯一一处有意的行为改动；带标记的文件得到的结果、报的错与去掉标记后相同。

**`configFileKeys`**（server 启动记录的 `config_keys` / `config_unknown_keys` 用，见[用户日志](#用户日志)）：`known` 是文件里出现的已知键的标识符（`port`、`ui.theme`），按 schema 顺序，值合不合格都算；`unknown` 是其余条目的个数——顶层既不是已知键也不是已知表的条目（未知表算一个，表内不计），加已知表（`[ui]`）里不是已知键的条目；已知表本身不计入；已知表名被写成非表（`ui = 3`、`[[ui]]`）时计一个。未知键的名字与任何值都不返回。文件不存在、读不了或不是 TOML 时是 `{ known: [], unknown: 0 }`。

**按行修改**（infra `config-edit.ts`，纯函数，不读写文件）：`editConfigText(原文, 键, {set: 值} 或 {reset: true})` 返回新原文与是否有变化，或拒绝及原因类别。

- 只改两种形状：顶层的 `键 = 标量`，和一层表头（`[ui]`）下的 `键 = 标量`。被改的只有值的那几个字节；裸值（数字、布尔、日期）的结尾按解析器的算法定——smol-toml 对裸值用 JS 的 `trimEnd`，它去掉的不只是 TOML 允许的空格与制表符，还有 NBSP、U+2028、U+FEFF、换页符、不属于换行符的落单 `\r` 等——这些字节在值之后，原样留在行上；键本身、等号两边的空白、行尾注释、其他所有行、各行的换行符、文件开头的字节序标记原样保留。
- 键名按去引号后的名字比对，`"port" = 1`、`'port' = 1` 都是 `port`，键的写法不动；表头同理（`[ ui ]`、`["ui"]`、表头后带注释）。注释里、字符串里、多行字符串或多行数组内部、别的表、子表（`[ui.extra]`）、表数组（`[[rows]]`）里出现的同名文字都不是这个键；顶层的 `language` 与 `[ui]` 下的 `language` 是两个键。
- 新值与键现有的值相同（按解析后的值比，`port = 0x10` 要改成 16 时）不改任何字节。
- **恢复默认**是删去该键所在的行连同它自己的换行符，别的不动：表里最后一个键被删后空表头保留；被删的是没有换行符的最后一行时，文件改以上一行的换行符结尾。键本来就不在文件里时不做任何事（返回原文，不算拒绝）。
- **键不存在时追加**：放在所属段落最后一个 `键 = 值` 行之后（值跨多行时在它结束的那一行之后），沿用那一行的缩进；段落指顶层的表头之前部分，或表头之后到下一个表头之前。表里还没有键时紧跟表头。顶层还没有键时，放在第一个表头及紧贴其上的注释行之前；文件没有表头时放在文件末尾。
- **表不存在时**在文件末尾空一行后新建表头和这一行（只因 `[ui.extra]` 而隐式存在的 `ui` 也算不存在）。
- **换行符**：新行用它前一行的换行符；前面没有行时用文件里第一个换行符；文件里没有换行符时用 LF。最后一行原本没有换行符的文件，修改后仍然没有（空文件除外，写入后以换行符结尾）。
- **值的写法**：字符串一律写成基本字符串，只转义 `"` 与 `\`，其余字符（含非 ASCII）原样写；含控制字符（U+0000–U+001F、U+007F，换行与制表符在内）或落单代理项的字符串拒绝而不是转义。整数写十进制，`-0` 当作 `0`。Windows 路径的反斜杠因此写成 `\\`。
- **拒绝类别**（都不带原文或值的任何片段，原文不变）：`unknown_key`（不是 schema 的键）、`invalid_value`（新值不合 schema，或改动本身不成形：既不是恰好 `{set: 标量}` 也不是恰好 `{reset: true}`）、`unrepresentable_value`、`unparseable`（文件不是 TOML）、`duplicate_key`（该键写了不止一次；别的键重复属于 `unparseable`）、`dotted_key`（该键或它的表以点号键写成，如 `ui.theme = …`）、`inline_table`（该键的值或它的表是行内表）、`multiline_string`（值是 `"""` 或 `'''` 字符串，即使写在一行里）、`array_of_tables`（它的表是 `[[ui]]`）、`not_a_scalar`（值是数组，或该键被写成了表）、`table_not_a_table`（`ui = 3` 一类）、`unsupported_layout`（解析器接受而本模块的行扫描没能跟上的写法；保守拒绝。它是到得了的：smol-toml 1.8.0 有两处宽松，把后面没有 `=` 的带引号键与下一行连读（`"a=b"` 换行 `port = 80` 读成 `{"a=b": 80}`），把 `[[a]` 之后的任意一个字符当作第二个 `]`（`[[a]x`、`[[a]` 后接空行）；行扫描两种都拒绝，测试钉住）、`self_check_failed`。类型不对的单行标量（如 `port = "x"`）可以改，也可以恢复默认。一个例外会走到 `self_check_failed`：写成数字的键（`data_dir = 12`、`auto_ingest_arxiv = 1`）后面紧跟只有数字之后才被解析器容忍的空白（NBSP、换页符等），而新值是字符串或布尔——保留那些字节后的文本不是 TOML，自检拦下，文件不变；改成数字或恢复默认不受影响。
- **自检**：`proposeConfigEdit` 生成候选原文，`checkConfigEdit` 把它重新解析：目标键必须得到预期值（恢复默认时必须不在），其余所有键的值必须与修改前深相等，字节序标记的有无不变，否则 `self_check_failed`。自检比的是解析后的值，不比写法。看得见的：别的键换了类型或数值、多了或少了键、数组顺序变了、日期换了种类（本地日期 / 本地时间 / 本地日期时间 / 带时区的日期时间，按 smol-toml `TomlDate` 自带的信息分辨）或换了时区写法。看不见的（解析器对两边返回同样的东西）：同一个值的另一种写法（`1.0` 与 `1`、`nan` 与 `-nan`、`0x10` 与 `16`、`"a"` 与 `'a'`）、注释与空行、键的先后。这些之所以不变，靠的是生成这一步从不碰别的行，不是自检；自检只是兜底层。`editConfigText` 是两步的组合，生成这一步可以由调用方传入，测试以此证明坏候选过不了自检；`proposeConfigEdit` 不从 infra 包顶层导出。行扫描是本模块自己写的（没有引入保留格式的 TOML 编辑库），解析仍用 smol-toml。

**写入**（infra `config-write.ts`）：`writeSetting(键, 改动, {path})` 在跨进程文件锁内读取文件、按上面的规则修改、原子替换，从不抛出，结果是「已改 / 无需改」或一个拒绝类别（不带路径、值或系统错误原句）。

- 锁用 proper-lockfile：配置文件旁的 `config.toml.lock` 目录，只在一次写入期间存在；持锁进程崩溃留下的锁 15 秒后被视为过期并接管。等待约 6 秒仍拿不到锁返回 `busy`。同一个键两边都改时后写的赢。
- **锁被判定失效**：活着的持锁进程被挂起超过 15 秒（进程被暂停、机器休眠）时，它的锁同样会被别的写入者当作过期接管，而它自己还以为持有。proper-lockfile 在它恢复后会通知它（`onCompromised`）；`writeSetting` 把通知记成标志（回调本身不抛出——默认实现会从定时器里抛成未捕获异常），在把新文件换到位之前检查：命中则不替换、删掉临时文件、返回 `busy`，对方写下的内容保留。通知来自定时器，可能晚于替换：那时保住两处改动的是下一条的文件身份比对（发现文件在自己手下被换掉的那一方重做），所以「被接管的一方一定得到 `busy`」并不成立，成立的是「不会有一方的改动被静默覆盖，下述剩余窗口除外」。
- **外部编辑器**不认这把锁。防止覆盖它的保存靠的是比对：锁内读取时记下文件的身份（inode、大小、纳秒级修改时间；或「没有文件」），替换之前再看一次，不是读到的那个文件就丢掉临时文件，把「读取、修改、写临时文件」整步在新内容上重做，最多做三次；三次都被改返回 `busy`。读取时不存在而替换前出现了、读取时在而替换前没了，都算变过。**剩余窗口无法完全消除**：最后一次比对到 rename 之间落下的保存仍会被覆盖；inode、大小、修改时间三样都没变的保存任何时候都看不出来（修改时间粒度粗的文件系统上更容易出现）。要关上它只能让编辑器也拿锁。配置路径本身是符号链接时，替换前还会再解析一次链接：链接被改指别处或被换成普通文件（编辑器用「临时文件加 rename」保存链接路径时就是这样）则不替换、返回 `busy`，再次请求会写到链接现在指向的地方；同样留有最后一次查看到 rename 之间的窗口。
- 选项里的 `rename`（把新文件换到位的那一步）与 `beforeReplace`（每次尝试中，临时文件写完之后、最后一次看锁与文件之前执行的一步）是给测试与需要替换这一步实现的调用方用的注入点，不是一次写入的设置：票 10 的接口必须自己构造选项，不得把请求里的任何东西传进来。
- 替换是同目录临时文件写完并落盘后 rename；rename 之前失败时原文件完好，临时文件被删掉。没有变化时不写文件。进程恰在写临时文件时被杀会留下一个 `config.toml.<pid>.<随机串>.tmp`，不会被自动清理，也不影响读取。
- 文件不存在时创建（0600），目录不存在时一并创建（0700）；对不存在的文件恢复默认不创建任何东西。已有文件的权限位保留，与进程的 umask 无关（临时文件创建后再显式设一次权限位）。
- 文件是符号链接时改它指向的文件（锁与临时文件在目标旁边），链接仍是链接；指向不存在目标的链接返回 `unreadable`。
- 写入独有的拒绝类别：`busy`（等不到锁；或自己的锁被接管；或文件在三次尝试里每次都被别人改了——都没有写任何东西，重试即可）、`unreadable`（读不了，或不是普通文件）、`invalid_encoding`（不是合法 UTF-8，解码再写回会改动字节）、`not_writable`（用户对文件没有写权限——即使目录权限允许替换它——或目录不可写）、`write_failed`。
- 并发范围：多个工作台进程可以同时调用；它不与严格/宽松读取互斥，读取方读到的是替换前或替换后的完整文件。

### 设置接口、文件监视与界面偏好（desktop-app 票 10）

实现在 server 的 `settings.ts`；应答的形状、拒绝类别表与 WebSocket 消息在 contracts 的 `settings-api.ts`。硬契约里对应的条文是 [contracts 的「设置与 config.toml」](contracts.md#设置与-configtoml2026-10-13-批准desktop-app-票-10-写入)。

**接口**（应答一律 `Cache-Control: no-store`）：

- `GET /api/settings` → `SettingsSnapshot`：`version: 1`；`path`（配置文件的绝对路径）；`pathDisplay`（同一路径的显示写法：server 的主目录写成 `~`，由 server 按自己的主目录判断，只替换完整的开头路径段；票 11 起，页面不再按常见前缀猜）；`file`（`missing` / `read` / `unparseable` / `unreadable`）；`readonly`（文件在却什么也取不出来，即后两种）；`values`（每个键的生效值，经 `redactSettingsValues`：机密键只有 `{ secret: true, set }`）；`sources`（每个键 `default` 或 `file`，有问题的键是 `default`）；`problems`（`{ key, reason }`，`key` 是已知键、表名 `ui` 或 `null`，从不带值）；`uneditable`（有控件的键里页面现在无法安全修改的那些及其类别；只读时为空）；`legacy`（文件里还留着的已失效键，今天只有 `ads_dev_key`；票 12 起它不再生效，页面在 ADS token 一行里提示）；`running`（票 11：进程**实际在用**的需重启键——`port` 是正在监听的端口〔没在监听时 null〕，`data_dir`、`global_dir`、`global_cache_dir` 是在用目录的绝对路径，`project_root` 是 server 的工作目录〔相对的 `data_dir` 据它解析〕，路径各为 `{ path, display }`；`from_flag` 列出 `serve` 启动时由命令行 `--port` / `--data-dir` 给出的键〔这些键的文件值本次与以后带同一参数的启动都不起作用〕；命令行 `--port` / `--data-dir` 与坏键的默认值都已计入，进程期间不变。它与 `values`〔文件现在的值〕、`startup`〔启动时各位置的来源与问题类别，不带路径〕不同。这些路径含用户名与文件夹名：只进这个 `no-store` 的应答，不进用户日志）；`restartPending`（票 11：需重启的键里，文件现在的生效值与 server 创建时〔`serve`：启动读取的那一份〕不同的那些，按 schema 顺序——进程仍在用旧值，重启后才变；`from_flag` 里的键不算，文件读不出〔`readonly`〕时为空）。读取是宽松读取，从不报错。`uneditable` 在读取时就算出来：对每个 `ui: "edit"` 的键，拿当前文件原文各问一次按行修改器「恢复默认」与「设成另一个合法值」（`editConfigText`，纯函数，不写任何东西），任一次被拒就记下类别；文件字节不是合法 UTF-8 时所有键都记 `invalid_encoding`。
- `PUT /api/settings/:key`，请求体恰好是 `{ "set": 标量 }` 或 `{ "reset": true }`（至多 4096 字节）→ 成功 200 `{ ok: true, changed, settings }`（`settings` 是写入后的 `SettingsSnapshot`；新值与现值相同或恢复一个没设的键时 `changed: false`，不写文件）；被拒绝 `{ ok: false, reason }`，文件字节不变。经 `writeSetting` 落盘（锁、按行修改、原子替换，见上一小节）。与其他写接口相同的 CSRF 守卫（跨站 403 `{ detail }`）。接口只放行 schema 里 `ui: "edit"` 的键；`writeSetting` 的选项由接口自己构造，只给配置文件路径，请求里的任何东西（请求体的多余字段、查询串）都到不了它。

| 状态码 | `reason` |
| --- | --- |
| 400 | `invalid_request`（请求体不是一次修改，或过大）、`invalid_value`（这个键不接受该值）、`unrepresentable_value` |
| 404 | `unknown_key` |
| 422 | `not_editable`（`readonly` 或 `none` 的键） |
| 409 | 文件此刻的写法或状态：`unparseable`、`unsupported_layout`、`duplicate_key`、`dotted_key`、`inline_table`、`multiline_string`、`array_of_tables`、`not_a_scalar`、`table_not_a_table`、`self_check_failed`、`busy` |
| 500 | 文件读不了或写不进：`unreadable`、`invalid_encoding`、`not_writable`、`write_failed` |

应答、问题清单与拒绝原因都不带键的值，也不带文件原文或系统错误消息；接口不把请求里的值写进任何日志，也不新增日志事件。

**文件变化通知**：`createServer` 起一个只看配置文件这一个路径的轮询（`startSettingsWatcher`，间隔与另一个外部写入 watcher 相同，默认 1.5 秒），比较文件的 inode、大小与纳秒级修改时间（或「不存在」），变了就广播 `{ type: "settings.changed", cause: "external", at }`。不用 `fs.watch`：文件是靠 rename 替换的（每次都是新 inode），所在目录可能还不存在，路径可以是符号链接，而写入时短暂出现在旁边的 `config.toml.lock/` 与 `config.toml.<pid>.<随机串>.tmp` 不该算变化——只看这一个路径就都覆盖了。接口自己写入成功且确有改动时立即另发一条 `cause: "write"`，随后轮询还会再发现一次（`external`），页面重取是幂等的。消息不带任何设置内容，页面收到后重新 `GET`；WebSocket 重连（`hello`）时也重取一次。

**`serve` 的启动与运行中的读取**：

- `startServer` 在启动时用宽松读取把文件读**一次**（`serveStart`）：文件无法解析或读不了时全部用默认值，单个键出错时该键用默认值——`data_dir` 写成绝对路径也一样（用 `./literatures`，硬契约「产品与执行边界」第 2 条 2026-10-14 的修订）——都照常启动；文件不被改写。需重启才生效的键在这里固定、整个进程期间不变：`data_dir`、`port`（命令行参数照旧优先）、`global_dir`、`global_cache_dir`、`log_level`。两个全局目录经 infra 的 `pinGlobalDirs` 固定（`createServer` 收 `globalDirs`，关闭时释放；`createServer` 没收到时按创建时的宽松读取固定）：此后本进程里不带 `config` 的 `resolveGlobalDirs()` / `ensureGlobalDirs()`——infra 的 `credential-store.ts`、`mail/account-store.ts`，server 的 `mail-routes.ts`、`mail-compose-routes.ts`，以及用户日志目录——拿到的都是这一份，运行中改动或改坏文件不会让全局数据换位置，也不会让这些请求失败。`global_dir` / `global_cache_dir` 写成本机平台用不了的绝对路径（schema 按任一平台的写法判，例如 Linux 上的 `C:\x`）时，server 的读取（settings.ts 的 `withPlatformPaths`）把它当作 `must_be_absolute` 问题、该键用默认目录——启动时的问题清单、终端与设置页的问题清单因此一致。

  `serveStart` 同时产出**启动位置状态**（`startupLocations`，交给 `createServer` 的 `startup`，再由 `GET /api/settings` 的 `startup` 字段原样给出，进程期间不变）：项目数据（`data_dir`）、全局数据（`global_dir`）、全局缓存（`global_cache_dir`）三处各自的来源——`flag`（`--data-dir`，只对项目数据）、`file`、`default`——以及启动时该键（或整个文件：`unparseable` / `unreadable`）的问题类别，没有就是 null。不带路径与值。它与同一应答里的 `values` / `sources` / `problems` 不同：后者是文件**现在**的样子，运行中改坏或修好文件立刻变，`startup` 要到下次启动才变。只经 `createServer` 起的 server（测试）没有它，是 null。
- 配置有问题时 `serve` 在 stderr 打出问题清单（`configProblemLines`）：一行说明文件，每个问题一行，只有键名与原因类别，不带值、不带解析器原句；随后按启动位置状态为受影响的每处位置写一行：`project data: the default location ./literatures is in use…`、`project data: the location given by --data-dir is in use`、`global data (Mail, credentials, log): the default directory is in use…`、`global cache: …`；末行说设置页也列出这些问题，只有某处位置因此落在默认位置时才建议改好文件后重启。启动记录 `server.started` 带 `config_problems`（见[用户日志](#用户日志)）。页面在工作台顶部常驻横幅（`ConfigProblemsBanner`，下文「设置页」）。
- 即时生效的键在用到时宽松读取，读不出（文件坏、键坏）当作没设：`auto_ingest_arxiv`（`app.ts` 的 `autoIngestArxiv` 默认实现，按默认值「开」）；`openalex_api_key`、`contact_email`（server 组装来源时经 `AdapterWiring.config` 交给 `realSources` / `realDiscoverySource`，每次组装现读，所以改了不用重启）；ADS token 不在配置文件里：每次组装经 `AdapterWiring.adsToken` 从 server 自己的 ADS 凭据存储现读（票 12，见下文「ADS 凭据」）；`[ui]`（设置接口与送出页面时写进 `<html>` 的属性）。
- 兜底：任务记录与添加文献的失败应答遇到 `ConfigError` 时写固定文案 `config.toml could not be read`（server `jobs.ts` 的 `jobErrorText`），因为严格读取的报错会引用解析器原句（带文件的行）；server 自己已不再严格读取，这只是防线。邮件路由的错误本就是固定文案。
- CLI 的其余命令仍是严格读取，行为不变：`getConfig()`、`resolveGlobalDirs()`（不固定）、`readOpenAlexApiKey()` 的默认参数，坏文件即 `ConfigError`、exit 1。CLI 的 ADS token 由 `realSources` 在组装时经 `readAdsToken()`（默认的 ADS 凭据存储）读取：钥匙串不可用且没有后备文件、文件损坏、读取出错都按「没有 token」处理，不报错（票 12）。

**界面偏好**（`[ui]`）：权威是 `config.toml`。页面的状态在 web 的 `argelander/preferences.tsx`（Shell 持有一份，经 context 交给设置页；标题栏的主题切换、外观速调浮层与 Copilot 的 `set_appearance` 走同一个 setter）。改一项时页面先按新值显示，同时 `PUT` 那一个键；应答回来以应答里的设置为准，被拒绝时退回文件里的值并在页面底部的浮层说明。首次绘制前的值按这个顺序取：

1. server 送出 `index.html` 时写在 `<html>` 上的属性（`lang`、`data-theme`、`data-density`、`data-accent`、`data-labels`，加 `data-ui-from="config"`；每次请求现读配置，取值只会是 schema 的枚举或默认值）。主题的颜色是 CSS 里按 `data-theme` 写的规则，所以从没打开过工作台的浏览器第一帧也是配置的主题；
2. 没有这些属性时（页面不是 server 自己送出的，例如 Vite 开发服务器）用浏览器本地存储里的副本 `argelander.ui`——页面每次应用外观后写下的一份拷贝；
3. 都没有则用默认值。

设置读到之后一律以配置为准，副本随之改写；副本从不写回配置。旧版本存在浏览器里的偏好（本地存储键 `argelander.tweaks`）不再读取，也不迁移进配置，原样留在浏览器里。`ui.labels` 留在 schema 里照常读、写、校验，也照旧写进 `<html data-labels>`，但没有界面读它的值，设置页暂不显示它的开关（用户 2026-10-14 裁决：等定义了含义再做）。

**同一键的连续修改**：页面按键串行：一个键的修改在途时，之后对它的修改只留最后一次，前一次应答回来后再发（`preferences.tsx` 的 lane），所以文件最后是最后一次点击的值；被替换掉的那次的调用方得到最后那次的结果。有修改在途时（任一键），读到的设置只更新页面持有的设置，不移动外观控件；在途的修改全部答复之后，才按读到的设置更新外观。修改发出之前就出发、在它之后才答复的读取被丢弃。「已写入配置文件」浮层只对设置页里发起的修改出现；标题栏、外观速调与 Copilot 的修改不弹成功提示，失败提示在任何入口都出现。Copilot 的 `set_appearance` 等每个键的写入结果，全部成功才报完成，任一被拒报 `unavailable`。

**设置页**：`settings/SettingsView.tsx`，是一个窗格视图（contracts 的 `SETTINGS_VIEW`；`PANE_VIEWS` 是五个工作视图加它，页面错误上报的 `pane` 枚举取自 `PANE_VIEWS`）。它不在 `WORKSPACE_VIEWS` 里，所以 Copilot 的 `switch_view` 不能切到它，发布给 Copilot 的页面上下文里它只有视图名、状态是 `unavailable`。入口是导航栏底部的齿轮。配置文件路径显示 server 给的 `pathDisplay`，复制给出完整路径；桌面应用里路径旁是「打开配置文件」，经宿主请求用系统编辑器打开（desktop-app 票 17，见[桌面宿主](#桌面宿主desktop-app-票-17)；不能安全修改的行下只有这个按钮，保存失败的浮层也带它）；浏览器形态是路径加复制。九个分组里票 10 填了「外观」，票 11 填了「项目」（「当前项目」一行只读显示 server 的工作目录、注明不保存在配置文件中；`data_dir` 输入框显示文件里写的相对路径，旁注进程在用的绝对位置；`auto_ingest_arxiv` 开关「添加文献时自动获取 arXiv PDF」）、「文献服务与凭据」（ADS token 一行，见下文「ADS 凭据」；联系邮箱）、「Copilot」与「邮件」（各一个入口：前者打开 Copilot 面板与它现有的模型设置对话框〔与面板自己的设置按钮是同一个对话框〕，后者把窗格切到邮件页、账户就在那里添加与管理；两行都带「不保存在配置文件中」徽标；两处的存储与行为不变）、「高级」（端口；全局数据目录、全局缓存目录只读显示进程在用的位置，只能在文件里改）。需重启的键（`data_dir`、`port`、两个全局目录）一律带「改后需重启」徽标，`data_dir` 与端口旁注进程正在用的值；`restartPending` 里的键改为「已保存，重启后生效」（只能手改的两个全局目录说「文件已改，重启后生效」，控件处显示文件里的新值）并写出进程仍在用的值；由命令行给出的键另有一行说明本次由命令行参数决定。文本类设置回车或离开输入框时保存（先去掉首尾空白），清空即恢复默认（删去那一行）；正在输入时同一个键在文件里被改动，输入框保留草稿并提示，回车按最新的文件值判断后保存输入、Esc 换成文件里的值；页面能判断的错误（端口越界、`data_dir` 写绝对路径、邮箱不合形态）不发送、在输入框下说明。票 13 填了「TeX 与环境」（见下文「外部程序探测与环境检查」）；「诊断」仍是一行占位；`cli` 分组只属于桌面应用，浏览器形态不列出。

**ADS 凭据**（desktop-app 票 12；server `ads-credential.ts`，contracts `ads-credential-api.ts`，web `settings/AdsCredential.tsx`、`api/ads-credential.ts`）：ADS token 存在凭据存储的 `ads` 用途里，不进 `config.toml`。接口（应答一律 `no-store`；写操作与其他写接口同一个 CSRF 守卫，跨站 403；任何应答都不含 token）：

- `GET /api/credentials/ads` → `{ version: 1, saved: none|keychain|file|unreadable, keychain: available|unavailable, devKey: { exists, path } }`：`unreadable` 是后备文件损坏；`keychain` 是这次读状态时钥匙串有没有应答（页面据此在保存前就给出同意卡）；`devKey` 只说 `~/.ads/dev_key` 在不在（是普通文件）和它的显示路径，从不读内容。
- `PUT /api/credentials/ads` `{ token, fileFallbackConsent? }`：去掉首尾空白后须是 1–1024 个不含空格的可打印 ASCII 字符（contracts `isAdsTokenShaped`，页面同用），否则 400 `invalid_token`；按凭据存储的规则保存，钥匙串不可用且 `fileFallbackConsent` 不是字面量 `true` 时 422 `keychain_unavailable`、什么也不写。
- `DELETE /api/credentials/ads`：钥匙串与文件里的副本都删；钥匙串不可达又没有文件副本可删时 422 `keychain_unavailable`。
- `POST /api/credentials/ads/test` `{ token? }`：带 `token` 测这份输入（不保存），不带测已保存的（没有则 409 `not_saved`）。infra `sources/ads-token-test.ts` 向 ADS 搜索接口发一次 `rows=0` 的请求，token 只在 Authorization 头里：2xx 为 `valid`，401/403 为 `rejected`，429 为 `rate_limited`，其余状态、网络失败与 15 秒超时为 `unreachable`；不读应答内容、不缓存。请求经 `observedFetch` 记进用户日志（只记主机、状态与耗时）。
- `POST /api/credentials/ads/import` `{ fileFallbackConsent? }`：server 只读打开 `~/.ads/dev_key`（至多 8 KiB），去掉首尾空白后按 `PUT` 的规则保存；文件不在 404 `no_dev_key`，读不了 500 `dev_key_unreadable`，内容不像 token 400 `invalid_token`。文件的字节与修改时间不变，也不删除；此后它与工作台保存的 token 是两份。

读取的边界（票 12 修订）：离线组装（`library build --offline` 等 CLI 的 `--offline`、server 的离线 refresh）与在线一样在组装来源时读 ADS 凭据——读到就是 `ok`，读不到是 `no-token`，与票 12 之前离线时的语义一致，所以摘要的 `ads_status` 不会对已保存 token 的用户说「没有 token」（曾在修订轮改为离线不读，父代理同日撤回：那样会让摘要说谎，而新增状态值要改 contracts 的 `AdsStatusSchema`，超出本票）。读取有超时：`readAdsToken` 等待至多 `ADS_TOKEN_READ_TIMEOUT_MS`（5 秒），超时按没有 token 处理，请求与任务照常进行，计时器在任一方结束时清除、不拖住进程退出。**已知局限**：超时只加在读 token 组装来源的这一处，设置页的凭据接口（状态、保存、移除、测试已保存的、导入）直接调用凭据存储、不设超时；而且超时只对返回 Promise 的后端有效；现在的 OS 钥匙串后端（`@napi-rs/keyring` 的同步 `Entry`）的调用在主线程上同步执行，钥匙串锁定时 Secret Service 弹出的解锁提示会占住主线程，计时器打断不了——这与邮箱密码是同一个既有局限，不为此换成 `AsyncEntry`（那会改到邮箱密码的后端）。解锁提示本身是 Secret Service 的行为，工作台不能也不去抑制。导入以非阻塞方式打开 `~/.ads/dev_key` 并先确认是普通文件，那里是 FIFO 或设备时按「没有文件」处理，不会卡住请求；符号链接照旧跟随。`createServer` 的 `adsDevKeyPath` 让测试把导入指向临时文件。

使用方：server 的 `createServer` 建一个 ADS 凭据存储（测试可经 `adsCredentials` 注入假钥匙串），接口与来源组装共用它，组装时 `readAdsToken` 现读——保存或移除后下一个文献补全、文献探索请求即生效，无需重启。CLI 的组装读默认存储。`AdsClient` / `AdsDiscoveryClient` 自己不读任何来源，没传 token 即没有 token。凭据存储的包装 `observedCredentials` 只记钥匙串是否应答（`credentials.keychain_state`），不看标识与值。

设置页的 ADS token 一行按获批原型：没保存（或点「替换…」）时是密码输入框，保存后输入框消失，只显示「已保存 / 未保存」与保护方式徽标；钥匙串不可用时先出同意卡，勾选前「保存」禁用；在文件里时常驻「未受钥匙串保护」警示；「测试」只测已保存的 token，结果四种之一；移除经确认对话框，焦点默认在「取消」；`~/.ads/dev_key` 在时显示导入入口（已保存时注明会替换，并注明不删除原文件）；配置文件里还有 `ads_dev_key` 时在这一行里提示「已不再生效」，「知道了」只在本次打开页面期间有效（用户 2026-10-14 裁决，与原型相同）；提示不带方位词：没有保存 token 时说「ADS token 请在本行填写；可以从配置文件里删掉这一行」，已保存（或状态未知）时只说后半句（用户同日裁决）。

**联系邮箱**（票 11）：Crossref 与 OpenAlex 的请求所带的联系邮箱只有一个来源，`config.toml` 的 `contact_email`。设了时，两边的请求都在查询参数 `mailto` 与请求标识（`User-Agent: ArgelanderSpace/0.1 (mailto:<地址>)`）里带上它；没设、空白或写错时，查询参数与请求标识里都没有任何邮箱（`User-Agent: ArgelanderSpace/0.1`）。源码里不再有写死的地址，环境变量 `OPENALEX_MAILTO` 不再读取（此前它与一个写死的默认地址一起决定两边的 `mailto`；arXiv 下载的请求标识里原也写死了同一个地址，一并去掉；arXiv 请求不带联系邮箱，用户 2026-10-14 裁决维持）。磁盘缓存键不再包含邮箱（换地址不丢缓存）；新键查不到且设了联系邮箱时，再按「参数加当前邮箱作 `mailto`」的旧键查一次（票 11 之前的派生，逐字节相同），命中则按新键另存一份、旧文件不删，没设邮箱时不查旧键（用户 2026-10-14 裁决「新键加旧键回退」，机制在 infra `sources/cache.ts` 的 `readKeyed`；另存是为了以后换地址或清空邮箱也仍命中）。所以票 11 之前写下的条目，只要现在填的是当时那个地址就照常命中；填了别的地址或不填，则各重取一次。**形态规则**（用户 2026-10-14 裁决写进 schema，`isEmailAddress`；保守，不追求 RFC 全集）：只接受可打印 ASCII，因此没有空白、控制字符、bidi 控制符、零宽字符；总长不超过 254；恰好一个 `@`；本地部分 1–64 个字符，取自 RFC 的 atext 字符集、以点分隔（不以点开头或结尾、没有连续的点、不支持带引号的本地部分）；域名至少两段，每段 1–63 个字母、数字或连字符，不以连字符开头或结尾（不支持 IP 字面量与国际化域名）。这些字符里没有括号与反斜杠，所以放进请求标识的注释里不会提前结束或转义它。写错的地址按坏键处理：设置页不让存（接口 400 `invalid_value`）；`serve` 的宽松读取当作没填、进问题清单（`must_be_email`，横幅点名）；CLI 的严格读取报 `ConfigError` 退出，不回显值。联系邮箱是用户的个人信息：不写进用户日志（外部请求的日志只记主机），`GET /api/settings` 把它交给页面。

desktop-app 票 06、07（2026-10-13）。「什么不进日志」与日志目录的并发范围是硬契约，见 [contracts](contracts.md#用户日志2026-10-13-新增)；这里记机制和不属于硬契约的运行约定。它与项目数据目录里的 `logs/arxiv-fetch.jsonl`、任务记录和 Copilot 的操作记录无关，那些都不动。

- **模块**在 infra `log/`（`fields.ts` / `logger.ts` / `files.ts` / `process.ts`），server 与桌面宿主共用，web 运行时不引用。一条记录＝事件名＋字段。事件名来自创建 logger 时给出的目录（`createLogger({ events })`，类型上是字面量联合，运行时不在目录里的名字写成 `log.rejected`、原名与字段都丢弃）；字段值只能由 `f` 的构造函数产生，logger 没有接收文本的方法，不是 `LogField` 的值（字符串、对象）在类型上不通过，运行时被丢弃并计入 `dropped_fields`；字段名须是 `[a-z][a-z0-9_]{0,39}`，否则同样丢弃。
- **字段种类与各自的检查**（`fields.ts`）：
  - `f.id` 标识符：ASCII、无空白、无 `@`、至多 128 字符，否则写 `<invalid-id>`。带空格的标题、邮件地址、中文因此进不来，单个英文单词拦不住。以 `work:`、`latex-`、`upload-` 开头的值（`upload-<uuid>` 这种任务 id 除外）按下面的 Work / Doc 规则写出，不原样写。
  - `f.workId` / `f.docId`：Work / Doc 标识符，判定表见下。
  - `f.oneOf` 枚举：必须是调用处给出的那张表里的值，否则 `<invalid-enum>`；表由调用处的代码提供（请求记录里是 app 注册过的路由模式）。`f.ids` / `f.someOf` 是列表（至多 64 项）。
  - `f.num` 有限数；`f.ms` 非负有限数，保留一位小数。
  - `f.path`：只认绝对路径形态——`/…`、`X:\…` 或 `X:/…`、`\\server\…`，以及已经写成 `~` 或 `~/…` 的；其余（标题、句子、相对路径、文件名）写 `<invalid-path>`。主目录及其 realpath 写成 `~`，控制字符、bidi 控制符（U+061C、U+200E / U+200F、U+202A–U+202E、U+2066–U+2069，与 CLI 冻结契约里 `<q>` 的集合相同）与零宽字符（U+200B–U+200D、U+2060、U+FEFF，以及软连字符 U+00AD）换成 `?`，至多 1024 字符。拦不住的是以 `/` 开头的任意文本；主目录以下的文件夹名（项目文件夹名）照实写出，例外是形如标题派生 Work / Doc 标识符的路径段，见下面的「路径段」。
  - `f.url`：只留协议、主机与端口（`URL` 的 `host`），不含用户名密码、路径、查询。协议须在写定的名单内（`http` `https` `ws` `wss` `ftp` `file` `mailto` `data` `blob` `about` `imap` `imaps` `smtp` `smtps` `tauri`），所以 `dark.matter:halo mass` 这类「词:其余」写成 `<invalid-url>`；没有主机的（`mailto:` `data:` `blob:` `file:`）只写协议；主机连同端口至多 255 字符；传入的不是字符串或 `URL` 对象也写 `<invalid-url>`。
  - `f.error`：见下。
- **Work / Doc 标识符在日志里的写法**（用户 2026-10-13 裁决；标识符的真实构成在 core `canonicalId`、`uploadDocId`、`arxivDocId`，infra `docIdFor`，以及 PDF / 文本 Doc 的 `pdf-<uuid>` / `text-<uuid>`）。原样写出的只有下表左列的形态，并且还要通过 `f.id` 的字符与长度检查；其余一律取哈希，判断不了的形态也取哈希。

  | 原样写出 | 写成哈希 |
  | --- | --- |
  | Work：`doi:10.<4–9 位数字>/<无空白>`、`arxiv:<YYMM.NNNNN>`、`arxiv:<旧式 archive[.xx]/NNNNNNN>`、`openalex:<字母＋数字>` | Work：`work:<标题 slug>[-<年份>]` 及任何其他形态 → `work:#<12 位十六进制>` |
  | Doc：`arxiv-<YYMM.NNNNN>[vN]`、`arxiv-<旧式号，/ 换成 ->[vN]`、`pdf-<uuid>`、`text-<uuid>`、`upload-doi-10-…-<6 位十六进制>`、`upload-arxiv-<YYMM>-<NNNNN>-<6 位>`、`upload-arxiv-<旧式号的 slug>-<6 位>`、`upload-openalex-…-<6 位>`（所属 Work 的 id 是 DOI / arXiv / OpenAlex 时，`uploadDocId` 的 slug 以这三个前缀开头） | Doc：`latex-<本地文件或文件夹名>` → `latex-#<12 位>`；`upload-work-<标题 slug>-…` 及其他 `upload-` → `upload-#<12 位>`；其余形态 → `doc-#<12 位>` |

  哈希是整个标识符的 SHA-256 的前 12 位十六进制，不加盐、不含任何与本次运行有关的东西，所以同一个对象在所有记录、所有运行里是同一个写法，记录之间对得上；代价是知道或猜到标题的人可以验证某条记录说的是不是那篇文献。带这类 id 的事件不再带以 id 命名的文件路径（`library.argument_graph_merged` 原先的 `absorbed_file` / `survivor_file` 已去掉）。

  表的几处细则：
  - **旧式 arXiv 号**的形态与 core 识别它的正则一致（`documents/references.ts`、`pipelines/tex/facts/bbl.ts`：`[a-z-]+(?:\.[A-Z]{2})?\/\d{7}`，不分大小写）：archive 是字母与连字符（`q-bio`、`q-alg`、`hep-th`、`alg-geom`、`cs`），可带两个字母的学科类，后面是七位数字。Doc id 里 `/` 是 `-`；`upload-arxiv-` 后面是它的 slug（全小写，`.` 与 `/` 都是 `-`）。没有七位数字的（`arxiv:some-title`、`arxiv-some-folder`）照旧取哈希。
  - **含特殊字符的真实 DOI 被哈希（已知例外，方向安全）**：原样写出还要通过 `f.id` 的字符集（字母、数字与 `._:/+()-`）和 128 字符的长度检查，所以带 `<`、`>`、`;`、`#` 等字符或超长的真实 DOI（旧的 Wiley SICI 形态如 `10.1002/(sici)1097-4571(199601)47:1<23::aid-asi3>3.0.co;2-p`）写成 `work:#<哈希>`，不是原样。
  - **路径段**：`f.path`、系统错误的 `path`、原因链各层的 `path`、调用栈帧的文件位置都经同一个函数（`renderPath`），它在替换主目录之后按 `/` 与 `\` 把路径拆成段，逐段处理（`renderSegment`）。一段先做 URL 解码（论证图的文件名是 `encodeWorkIdForFile` 把 `[A-Za-z0-9_-]` 以外的字节写成 `%XX` 的结果，如 `work%3A<slug>.json`；解码失败就按原文看），解码后以 `work:`、`doi:`、`arxiv:`、`openalex:`、`latex-`、`upload-` 开头（不分大小写）的才算标识符形态，其余段原样不动。算的段先去掉结尾的扩展名——只认代码里写定的一串（`.json` `.jsonl` `.tmp` `.tmp-<十六进制与连字符>` `.bak` `.lock` `.pdf` `.tex` `.bib` `.zip` `.gz` `.tgz` `.tar` `.js` `.mjs` `.cjs` `.ts` `.map`，可连着几个，如 `.json.tmp-<uuid>`）——剩下的部分按上表判定：带冒号的四种前缀按 Work 的规则，`latex-` / `upload-` 按 Doc 的规则（`upload-<uuid>` 是任务 id，不动）。判定为原样写的，整段不动（保持它原来的编码写法）；判定为哈希的，这一段写成「哈希写法＋扩展名」，哈希与 `f.workId` / `f.docId` 对同一个 id 的写法相同，所以 `output/latex-#8b46d0de00d8/latex-#8b46d0de00d8.json` 与别处的 `latex-#8b46d0de00d8` 对得上。不在名单里的结尾（`latex-my.thesis` 的 `.thesis`）可能就是文件夹名的一部分，连同前面一起取哈希，不保留。
    - 取舍：只看段的**开头**。所以代码路径、`node_modules`、项目文件夹里普通的名字都不动（`pdf-lib`、`latex/`、`uploads/`、`workspace/` 都不是上述前缀；Doc 一侧故意只认 `latex-` 与 `upload-`，不认 `arxiv-` / `pdf-` / `text-`，后三种前缀的 id 本来就原样写，而以它们开头的包名、文件名很常见）；但名字本身以 `latex-` 或 `upload-` 开头的包、源文件或项目文件夹（如 `node_modules/latex-utensils`）会被当成 Doc id 写成哈希。这是有意偏向的一侧：这种名字与「同名本地文件夹产生的 Doc id」在形态上分不开，写成哈希只损失可读性（哈希不加盐，拿已知的名字算一遍就能对上），原样写则可能漏出文件夹名。本仓库的源文件与现有依赖里没有以这两个前缀开头的名字（2026-10-13 核对）。
    - 拦不住的：标识符不在段的开头（如 `backup-of-latex-<名字>`、`.latex-<名字>.swp`）；用户自己的源文件夹（`latex-<名字>` 这个 Doc id 所来自的那个本地文件夹，它的路径里是不带前缀的原名）——后者属于「主目录以下的文件夹名照实写出」。
    - 大小写：前缀换了大小写的（`LaTeX-…`、`WORK%3A…`）不是工作台自己产生的写法，一律取哈希（Doc 一侧因此写成 `doc-#…`），与正常写法的同名 id 不是同一个哈希。

  调用方仍可能绕过的地方：把 Work / Doc id 交给 `f.id` 而它又不是 `work:`、`latex-`、`upload-` 三个前缀之一的形态时，只受 `f.id` 的一般检查；一个真实形态的 DOI 本身若含有词语，按裁决原样写出。
- **错误**：记 `name`（须是 `[A-Za-z_$][A-Za-z0-9_$.]{0,63}`，否则写 `Error`）、`code`（有限数；或字符串，须是 `[A-Za-z0-9_.:-]{1,64}`，再按 `f.id` 的规则写出——所以 `work:<标题 slug>`、`latex-…`、`upload-…` 形态的错误码写成哈希，与 `f.id` 对同一个值的写法相同；不合字符集的不记）；系统错误（带合法的 `syscall`）另记 `syscall` 与 `path`（按 `f.path` 的规则，相对路径写成 `<invalid-path>`）——调用处可以用 `f.error(值, { omitSystemPath: true })` 要求不记这个 `path`，原因链各层同样不记（这个选项只会少写，不会多写；调用栈帧照常写，它们是代码文件的位置。用户 2026-10-13 在票 07 实施中的裁决，现在只有 `job.failed` 用它）；`stack` 是逐帧的 `文件:行:列`，至多 40 帧，丢掉函数名，文件按路径规则写（主目录写成 `~`，标识符形态的路径段写成哈希），`node:` 开头的运行时模块名原样写。帧的形态是 `at 名字 (位置)` 或 `at 位置`，两者前面都可以有 `async `（`at async /path/file.js:5:6` 是一帧，`async` 与 `new Foo` 之类的名字都不写出）；没有 `:行:列` 位置的行（`at async Promise.all (index 0)`、`at <anonymous>`、`at Array.map (<anonymous>)`）不是帧，丢弃；`cause` 按同样规则递归，至多三层；抛出的不是 Error 时只记 `{name: "NonError", thrown: <typeof>}`。**调用栈的首行是 `名称: 消息`，消息可以有多行，其中任何一行都可能长得像栈帧**，所以解析帧之前先把消息按它的原文从栈文本开头切掉：栈必须以 `<消息>`、`<名称>: <消息>` 或（消息为空时）`<名称>` 开头并紧跟换行或结束，其中名称是标识符形态、可带 Node 的 ` [CODE]`；对不上（消息在栈生成后被改过、`stack` 被换成别的文本或不是字符串、`Error.prepareStackTrace` 产出了别的格式、名称里带换行）就不记调用栈，`stack` 为空数组。**残余条件（调用方仍可能绕过的地方）**：切除比对的是错误**当前**的名称与消息，而首行在栈文本生成时就定了（Node v24.15 实测是 `stack` 第一次被读取的时候，不是构造的时候：读取之前改写消息，首行跟着新消息走）。消息在栈文本生成之后被改写成原消息的一个前缀并且恰好停在换行之前（原消息 `a\n    at /x:1:2`，读过 `stack` 之后 `message = "a"`），或 `stack` 被整个换成以「当前名称: 当前消息」开头的任意文本时，比对通过，其后形如栈帧的行会被当成帧写出（位置仍要过路径规则：须是绝对路径形态）。接口拿不到栈文本生成时的消息，挡不住；现在没有产品代码这样做。
- **错误消息**：默认丢弃，引擎内建类型（`TypeError`、`SyntaxError` 等）也不例外。保留的唯一途径是错误类在自己身上声明 `static readonly [LOG_SAFE_MESSAGE] = true`（只对该类本身有效，子类要自己声明）；保留的消息仍替换主目录、把控制字符、bidi 控制符与零宽字符换成空格、截到 500 字符。现在没有任何产品错误类做了声明：`ConfigError` 的文案带配置文件路径，TOML 语法错误时还带解析器摘出的原文行，所以不声明。
- **输出端可注入**：`LogSink` 一个 `write(line)`。生产用 `openLogFile`：`<全局数据目录>/logs/<UTC 时间到毫秒>-<进程种类>-<pid>.jsonl`，一行一条 JSON（`t`、`level`、`event`，然后是字段），目录 0700、文件 0600，同步追加（进程崩溃前写下的记录已经在盘上）。文件以独占创建方式打开（`ax`）：同名的文件或符号链接已经在那里时既不追加也不跟随，改用 `…-<pid>-1.jsonl` 到 `-8` 中第一个空着的名字，都被占了就不记录、不抛错。打开时清理：按文件名（即启动时间）只留最新 20 个（`LOG_KEEP_FILES`），且从新到旧累计不超过 50 MB（`LOG_MAX_TOTAL_BYTES`，50 × 1024 × 1024 字节），超出的连同更旧的一起删；只碰符合上述命名的文件，本次运行的文件不删。单次运行也以 50 MB 为限：第一条写不下的记录换成一条截断标记 `{"t":…,"level":"warn","event":"log.truncated"}`（标记的位置事先留出，文件不会超过上限），此后这次运行不再写任何记录。`discardSink` 上的 logger 什么都不做。测试用的内存输出端不在产品代码里，在 `packages/infra/tests/log-memory-sink.ts`，server / cli 的测试按路径引用。
- **级别**：`debug` / `info` / `warn` / `error`，config.toml 的 `log_level`（默认 `info`；类型或取值不对时，CLI 命令是点名该键的 `ConfigError`，`serve` 用默认值 `info` 启动并在问题清单里点名该键，desktop-app 票 10）。logger 的级别可在运行中用 `setLevel` 改，下一条记录起生效。**不重启生效**（desktop-app 票 14）：server `log.ts` 的 `applyLogLevel(log, configPath)` 按宽松读取把 `config.toml` 现在的 `log_level` 交给 `setLevel`（文件没写或写错时是默认 `info`）；设置接口改写了文件之后（app.ts 设置路由的 `written`）与文件监视发现文件变了之后（server.ts `startSettingsWatcher` 的 `onChange`，手改的情形）各调一次，所以级别跟着文件走，从下一条记录起生效。测试服务器共用的 `silentLog` 不动。
- **谁写**：只有长时间运行的进程写用户日志：`serve` 与桌面宿主（desktop-app 票 17，文件名的进程种类是 `desktop`）。只有 `startServer` 打开日志文件（`openServeLog`）；`createServer` / `createApp` 只往传入的 `log` 里写，没传就是不记录、不解析也不创建日志目录，所以测试服务器默认没有日志。其余 CLI 命令不写日志文件、不创建日志目录，它们的 stdout / stderr / exit code 不因日志而变；`serve` 启动时打印到终端的三行不变。`startServer` 打开日志之后若启动失败（server 建不起来、端口绑不上），日志文件被关闭、对进程的观察被撤掉。
- **写日志失败不影响别的事**：建目录、开文件、写、清理的任何失败都被吞掉，只是没有日志；记录一条请求出错也不改变它的应答。请求不因此失败，进程不因此退出。
- **未捕获的异常与 Promise 拒绝只被记下**：经 `uncaughtExceptionMonitor` 只观察不接管，Node 照旧把错误打印到 stderr 并以原退出码结束。
- **server 的事件**（目录在 server `log.ts` 的 `SERVER_LOG_EVENTS`）：
  - `server.started`：版本、形态（`serve` 为 `browser`，桌面宿主为 `desktop`；宿主另记 `port_fallback` yes / no，回退时加 `port_configured` 与 `port_occupant`：`argelanderspace` / `other`）、端口、项目根（cwd）、项目数据目录、web dist（三者都是绝对路径，按路径规则写）、日志级别、pid、Node 版本、平台与架构，以及配置文件里出现的本版本认识的键（`config_keys`：键的标识符，顶层键名或 `ui.theme` 这样的 `表名.键名`，按 schema 顺序；只会写出 `CONFIG_KEYS` 里有的值）和其余条目的个数（`config_unknown_keys`：顶层的未知条目，加已知表 `[ui]` 里的未知键；`[ui]` 本身不计入。算法见 [`configFileKeys`](#settings-的-schema两种读取与按行修改desktop-app-票-09)），以及配置问题清单（`config_problems`，desktop-app 票 10：每项写成 `<对象>:<原因>`，对象是 schema 的键、表名 `ui` 或表示整个文件的 `file`，原因是问题类别；取值表由 server `settings.ts` 的 `CONFIG_PROBLEM_ENTRIES` 从 schema 与类别生成，不在表里的写不出；不带值）。也就是说端口、数据目录、日志级别记的是生效值；其他配置值不记，不认识的键名也不记。
  - `request.failed`：方法、路由模式（如 `/api/paper/:doc_id`）、状态码、耗时、错误码（有才记）、错误（有才记）。不记实际路径、查询参数、请求体，**也不读应答体**：读应答体（哪怕读的是副本）会改变它的传输形态——流式的 JSON 应答被读完后会从分块变成定长，并且要等整个应答体到齐才发出。错误码取自路由交给 `c.json` 的那个对象的 `code`（请求中间件在 `next()` 之前把这次请求的 `c.json` 包一层，只看经过的对象，原样返回它的应答），并且只在满足三个条件时记：它是字符串；发出的应答的状态码等于这次（最后一次）`c.json` 调用给出的状态码；发出的应答的 `Content-Type` 是 JSON。写出时按 `f.id` 的规则。用别的方式构造的应答（`new Response`、`Response.json`、流）不记 `code`。不按对象同一性比对，是因为子路由自己的错误处理应答之后 Hono 会重建应答对象；残余：路由调了 `c.json` 却丢掉结果、另行构造一个同状态码的 JSON 应答发出时，记下的是被丢掉的那个 `code`（它仍是路由代码里写的值）。状态码 ≥ 500 为 error 级；400–499 为 warn 级；**GET / HEAD 的 404 不算失败**（查一个已不存在的 Doc、页面资源、source map 都是正常问答）。路由模式取自实际应答的那条路由，并且必须是 app 注册过的模式之一。路由里抛出的不是 Error 时（Hono 不交给错误处理，原样交给 HTTP 层应答），记录里没有状态码。路由自己返回 5xx 而没有抛错时，记录里没有调用栈。
  - `request.completed`：debug 级，状态码 < 400 的请求和上面那种 404。

  - **各标识符的构成**：任务 id 是 `<kind>-<随机 uuid>`（`JobRunner.submit`），记录前检查形态（`jobIdField`：种类须是 `JobKindSchema` 里的一个，后面是小写的 uuid），不合的写成固定的 `job-unrecognized`——`JobRunner.recover` 启动时不经 schema 读回 `jobs/*.json`，手改过或别处放进来的任务文件可以带任意文本作 id，产品自己写不出这种 id；Copilot 的对话 id 与运行 id 都是随机 uuid（`CopilotHost`）；邮件账户 id 是 `acc-<12 位随机十六进制>`（`MailAccountService`，`MAIL_ACCOUNT_ID_PATTERN`），不含地址，不合这个形态的写成 `acc-unrecognized`。这三种合乎形态的原样写。`job.created` 的 `work` / `doc` 走 `f.workId` / `f.docId`，由标题或本地文件夹名派生的写成哈希。标注 id、邮件的文件夹与 uid、发送 id 都不记；稿件 id 只在票 08 的 `tex.compile_failed` 里以随机部分出现（见下）。
  - **任务失败不记错误信息的原文**：`job.error`（它可能带 TeX 日志摘录）只留在任务记录和界面上。日志里记抛出物本身（用户 2026-10-13 裁决）：`error` 字段是 `f.error(抛出物, { omitSystemPath: true })`，即名称、错误码、系统调用名、每帧只有代码文件位置与行列号的调用栈，原因链各层同样；消息照日志模块的规则丢弃，系统错误的 `path` 不记——任务处理的是用户自己的文件，本地摄入时那可能是以论文标题命名的文件夹。日志里的 `stage` 是任务最后一条指明步骤的进度消息所属的阶段——只看这条消息以代码里哪个词开头（`Fetching` → `download`、`Unpacking` → `extract`、`Validating` → `validate`、`Compiling` → `compile`、`Fusing` → `fuse`、`Materializing` → `figures`、`Rebuilding library` → `attach`、`Publishing` → `publish`；还没开始是 `queued`，没有进度是 `start`，对不上是 `other`；`warning: …` 行引用 TeX 日志，跳过不看），消息本身不记。`fuse` 与 `figures` 实际上几乎不会出现：infra `ingestTexSource` 的这两条进度（`Fusing…`、`Materializing figures`）是在编译、融合、出图整体返回之后才报的，所以这三步里任何一步失败时最后一条进度仍是 `Compiling…`，记成 `stage: compile`；只有其后写 IR 文件或更晚的步骤失败才会落在这两个值上。阶段推断没有为此改动（进度消息是任务记录的一部分）。`category` 只看抛出物的类别，不看消息：`source_has_no_latex`（`ArxivPdfOnlyError`）、`archive`（zip / tar 损坏）、`tex_workspace`、`http_status`（`HttpError`）、`timeout`、`aborted`、`file_system`（带 `syscall` 的系统错误）、`unclassified`。编译失败抛的是普通 `Error`，所以它是 `stage: compile`、`category: unclassified`，配合 `error` 的调用栈与同一时段 `external_program.exited` 的退出码看。
  - **外部程序与外部服务**：程序只记名字、退出码、耗时，不记参数与输出；程序名来自调用处写定的值，不取自实际执行的命令（沙箱里的 latexmk 记 `program: latexmk`、`sandboxed: yes`）。请求只记服务名与网址的协议、主机、端口，不记路径、查询参数、请求头、请求体，也不读应答（`observedFetch` 把实现返回的 `Response` 原样交回）；没有应答时不记错误对象，只记 `reason`。一次程序调用恰好一条记录：起不来的程序 Node 会先后发 `error` 与 `close` 两个事件，`runTexProcess` 只在没有 pid 的 `error` 上报一次 `not_started`，其后的 `close` 不再上报。 「一次调用一条记录」有一个例外：`spawn` 同步抛出的失败（例如参数过长的 `E2BIG`）在子进程对象建立之前就结束，不上报，日志里没有这次调用。
  - **沙箱探测**（`program: bwrap`；只有探测用这个名字上报，沙箱里的编译记的是 `latexmk`）：每次真实的探测恰好一条记录。找不到 bwrap 是 `not_started`（`code: ENOENT`），跑了而失败是带退出码的 `exited`，10 秒没结束是 `timed_out: yes`；读缓存的结果不是探测，不记。探测在途时来问的调用方都算在这一次探测上：`ensureWriterSandboxProbe(observer)` 与 `writerSandboxAvailable(observer)`（读缓存的那个门，负结果过期时由它发起重探）把各自的观察者加进这次探测的名单，结束时名单里每个观察者被告知一次；`externalObserver(log)` 对同一个 log 返回同一个对象，所以一个 server 一次探测只有一条。**级别的取舍**：负结果至多每分钟重探一次，而没有 bubblewrap 的机器（macOS、Windows 本来就没有）每次都失败，所以「找不到 bwrap」记 info 而不是 warn（它是那里的预期状态，后果只是不让 Copilot 触发 Writer 编译；启动记录的 `tools_missing` 也已列出它）；其他失败（装了但用不了，如禁用了用户命名空间）记 warn；与上一次探测结果相同的失败降为 debug——默认级别下每次状态变化一条，不是每分钟一条。 还有第四种结局：探测在运行 bwrap 之前就失败（例如找 TeX 安装根时出错），记成不带 `code` 的 `not_started`、warn。
  - **邮件**：`observedMail` 只看调用的方法名、第一个参数里的主机，以及结果的 `ok` 与 `code`；用户名、密码、端口、文件夹名、邮件内容与服务器应答文本都不看——应答文本在 infra 的协议层就已经被换成失败码。协议对象抛出异常时只记 `outcome: threw`，不记异常。**主机不原样记**（用户 2026-10-13 裁决，比规格的「记主机」更严）：学校、研究所或个人域名的邮件服务器主机本身就说明了用户是谁。`provider` 是账户对话框的预设 id（contracts `MailPresetIdSchema`，现为 `gmail` / `icloud` / `custom`）：`mailProvider` 直接查 contracts 的 `MAIL_PRESETS`，没有另抄一张表，新增预设时这里自动跟上。匹配规则：IMAP 调用的主机与某个预设的 IMAP 主机、SMTP 调用的主机与某个预设的 SMTP 主机**整个主机名相等**（不分大小写）才记那个预设的名字；不做后缀或子串匹配（`imap.gmail.com.example.org`、`mail.gmail.com`、结尾带点的写法都是 `custom`），预设的 SMTP 主机出现在 IMAP 调用里也是 `custom`；其余一律 `custom`，包括账户对话框里尚未保存的输入。所以预设选了 `custom` 而手填 Gmail 主机的账户记成 `gmail`，预设选了 `gmail` 而改填别的主机的记成 `custom`：记的是实际连接的服务器，不是账户上的预设字段。邮件监听的两个事件本来就不带主机。
  - **钥匙串**：不为日志去问钥匙串。`observedCredentials` 从凭据存储本来就在做的读写结果里看钥匙串有没有应答，每个存储对象在状态变化时记一条；所以没有邮件账户的机器上启动后不会有这条记录。启动时的「钥匙串是否可用」由票 13 的探测写进 `server.environment`（只问 D-Bus 总线守护进程，不问钥匙串，见「外部程序探测与环境检查」）；这条被动记录保留。
  - **接线：infra 的调用点怎样把事件交到 `serve` 的日志**。infra 不认识 logger，只认识一个观察者接口（`lib/observe.ts` 的 `ExternalObserver`：`program(call)` 与 `service(call)`），它是普通的参数，**没有进程级的注册处**：`runTexProcess` 的 `observe` 选项、`compileTex` / `materializeTexFigure` 的第二个参数、`ingestTexSource` 等的 `observer` 选项、`ensureWriterSandboxProbe(observer)`、`observedFetch(impl, service, observer)`。`createServer` 用自己的 log 造出观察者（`externalObserver(log)`），经 server `deps.ts` 的组合函数交给各适配器——`AdapterWiring` 是 `realSources(paths, offline, wiring)` 的第三个参数，是 `realDiscoverySource(paths, wiring)` 与 `realPipelines(paths, wiring)` 的第二个参数；arXiv 有两处自己的接线：e-print 抓取在 infra `ingestTexSource` 里（`observer` / `fetchImpl` 选项），PDF 下载在 `createServer` 里（`fetchArxivPdf` 的 `fetchImpl`），Writer 的编译同样带上观察者。任务的记录是 `JobRunner` 的 `observe` 选项，`createServer` 在**构造 runner 时**就传入：`recover()` 在构造函数里跑，上次没跑完的任务的 `job.interrupted` 是在那里记的（`createApp` 也会给一个还没有观察者的 runner 接上，但那时 `recover()` 已经跑完）；`JobTransition` 类型定义在被观察的一侧 `jobs.ts`，与 infra 的 `lib/observe.ts` 同一个方向。邮件的四个协议对象与凭据存储在 `createDefaultMail*Service(log)`、`createDefaultMailWatcher(…, log)` 里被包一层。`ServerOptions.fetchImpl` 是同一条线上底层 `fetch` 的依赖注入点（生产默认是全局 `fetch`，与 `heartbeatMs`、`providerSettings` 同类）：换掉的只是底层的 `fetch`，适配器与它们的接线仍是真实的。 唯一的例外是沙箱探测：它的结果在进程内缓存、同一时刻只跑一次，所以 `tex/sandbox.ts` 有一个只在探测在途期间存在的模块级观察者名单，探测结束即清空；不传观察者的调用（CLI）不会进这个名单。
  - **记录的先后**：`server.started` 不保证是文件的第一条。`startServer` 在 server 建好并监听之后才写它，而 `job.interrupted`（构造 runner 时）、邮件监听的状态变化与连接结束、钥匙串状态、沙箱探测的结果都可能在它之前写出；读日志时按事件名找启动记录，不按位置。
  - **CLI 为什么必然静默**：短时运行的命令调用同样的组合函数，但不传 `AdapterWiring`（`cli/src/program.ts`），直接调 `ingestTexSource` 时也不传 `observer`。没有观察者时这些函数不包装任何东西——`observedFetch` 返回传入的那个函数本身，`runTexProcess` 不计时也不上报，沙箱探测不告知任何人——所以 CLI 的这些调用没有被包装、没有被计时，stdout / stderr / exit code 与接入日志之前相同；它也从不创建 logger、不打开日志文件。没有 log 的 server（测试服务器的默认情形）在这几处同样不包装：`externalObserver(silentLog)`、`jobLogger(silentLog)` 返回 `undefined`，`observedMail` / `observedCredentials` 返回传入的对象本身，`logRequests` 不注册中间件。这不等于它逐行执行的是接入之前的代码：`JobRunner` 每次状态变化仍会走到一个空的 `observe?.()`，`CopilotHost` 与 `MailWatcher` 仍会调用静默 logger 的方法（什么都不写）；保证的是行为与输出相同，由既有测试钉住。
  - **观察不改变被观察的调用**：观察者与记录函数的任何异常都被吞掉；不重试、不延迟、不改超时与并发；任务的结果、任务记录里的错误信息、HTTP 应答、邮件的发送与监听行为都与接入前相同。
  - **量**：默认 info 级别下，一次上传摄入是 `job.created`、`job.started`、每次 latexmk 一条、`job.done`，外加失败的外部请求；逐张图的转换、成功的请求、成功的邮件调用、每条任务进度、每次结果为 `ok` 的工具调用、重复的沙箱探测失败都在 debug。
- **请求里未处理的异常**：`logRequests` 在所有路由之前注册一个中间件，只做记录，**不给主应用装 `onError`**。路由抛出的 Error 仍由 Hono 的默认处理应答——带 `getResponse` 的错误用它自己的应答（并入已设置的头），其余是纯文本 `Internal Server Error`、500——并照旧由它把整个错误（含消息）用 `console.error` 打印到 `serve` 的 stderr；中间件随后从 context 上取到这个错误，记一条不含消息的 `request.failed`。终端输出是用户自己的终端，不属于用户日志，隐私规则只管日志文件。没有传 `log` 的 `createApp` / `createServer` 不注册这个中间件，日志文件打不开的 `serve` 照常应答与打印，三种情形的应答体和 stderr 都与有日志之前相同。Mail、provider 等自带固定文案的子路由照旧用它们自己的处理，记录从同一处产生。
- **编译失败与页面错误**（desktop-app 票 08，2026-10-13；事件名同在 `SERVER_LOG_EVENTS`，写的地方在 server `compile-failure-log.ts`、`page-errors.ts`）。没有新增字段种类。

  | `tex.compile_failed` | warn | `source`（枚举 `ingest` / `writer`）；摄入带 `job`（标识符，任务 id），Writer 带 `manuscript`（标识符：稿件 id 去掉 `m_` 的 8 位十六进制）；`kind`（枚举 `compile-error` / `compile-timeout` / `unsupported-build`）、`engine`（枚举 `pdflatex` / `xelatex`）、`exit_code`（数字，被杀掉时没有）、`timed_out`（枚举 yes / no）、`missing_tex_files`（标识符列表）、`missing_other_files`（枚举列表）、`log_file`（另存成功才有；摄入是标识符 `jobs/<任务 id>.compile.log`，Writer 是枚举，唯一的值是字面量 `manuscripts/m_<manuscript>/build/compile-failure.log`） | infra `compileTex` 的 `failureLog` 钩子 ← `ingestFailureLog`（每个任务一个）、`logWriterCompileFailure` |
  | `page.error` | error | `kind`（枚举 `error` / `unhandledrejection` / `render`）、`pane`（枚举：contracts `PANE_VIEWS`——五个工作视图加设置页——再加 `none`）、`error`（错误：名称与调用栈帧，没有消息） | `POST /api/page-errors` |
  | `page.errors_dropped` | warn | `reason`（枚举 `per_minute` / `per_launch` / `too_large` / `malformed`）、`count`（数字）、`recorded_this_launch`（数字） | 同上，见「限量」 |

  - **编译失败的记录**：一次失败的编译（`compileTex` 返回失败且 latexmk 确实跑过）恰好一条，说的是返回的那个错误所属的那次尝试（与任务记录里的错误信息是同一次：引擎、退出码相同）。**例外**：最终返回的错误是「latexmk 退出码为 0 但缺 `.aux` / `.fls`」时不另存也不写这条记录，此前失败的尝试已经收集的日志随之丢弃（那次尝试没有失败的 latexmk 运行可说）。另存不成（目标位置写不了、已有同名目录）时记录照写，只是没有 `log_file`。不记源码行、日志内容与错误消息。**缺失的文件**取自失败那次尝试的四处文本——引擎的 `.log`、参考文献程序的 `.blg`、latexmk 自己的 stdout 与 stderr——里的这几种报告：`File `…' not found`、`I can't find file `…'`、字体度量缺失、bibtex 的 `I couldn't open style file …` / `I couldn't open database file …`、biber 的 `Cannot find '…'`；都是文档可以控制的文本（相对硬契约「稿件内容不进日志」的这一处例外写在 [contracts](contracts.md#用户日志2026-10-13-新增) 第一条）：扩展名在写定名单内（`sty` `cls` `clo` `def` `cfg` `fd` `tfm` `vf` `enc` `map` `bst` `ldf` `bbx` `cbx` `lbx`——宏包、文类及其选项 / 定义 / 配置文件，字体定义与度量，参考文献样式，babel 与 biblatex 的语言和样式文件）的算 TeX 发行版一类的文件，名字合乎 `[A-Za-z0-9][A-Za-z0-9._+-]{0,63}`（没有目录、空格）才记进 `missing_tex_files`，不合的整条不记，至多 16 个；其余缺失文件是用户自己的，只在 `missing_other_files` 里记扩展名，而且必须是写定名单里的一个（`tex` `bib` `pdf` `png` 等），不在名单里的写 `other`，没有扩展名的写 `none`（用户 2026-10-13 裁决）。`missing_tex_files` 经 `f.ids`，所以名字以 `latex-` / `upload-` 开头的宏包会被写成哈希；用户自己写的 `.sty` 的名字按裁决照记。**日志的位置**不用路径字段（它只认绝对路径）：摄入的相对路径由代码写的 `jobs/` 与任务 id 构成，任务 id 是 `<kind>-<随机 uuid>`、先验过形态（不合的任务不另存也不记录）；稿件 id 是 `m_<8 位随机十六进制>`（core `newManuscriptId`，contracts `ManuscriptIdSchema`），带下划线、过不了标识符字段，所以相对路径写成一个固定的枚举值，随机部分记在 `manuscript`。两种 id 都不含标题；Doc id 不出现在这条记录里。稿件 id 的随机部分自票 08 起进用户日志（票 07 时「稿件 id 不记」的说法到此改写），只有这一个事件带它。**已知局限**（用户 2026-10-13 裁决，接受）：命令行的摄入与 legacy 同步上传没有任务记录，失败时不另存完整日志，也不写这条记录。另存的文件本身不是用户日志，位置与保留规则见 [tex-pipeline](tex-pipeline.md#执行层) 与 [writer](writer.md#编译与-ir共享主干隔离外层副作用)。
  - **页面错误的接口** `POST /api/page-errors`：页面（web `page-errors.ts`）上报未处理的错误、未处理的 Promise 拒绝，以及顶层错误边界（`PageErrorBoundary.tsx`）接住的渲染错误。受与其他写接口相同的 CSRF 守卫保护。上报内容来自浏览器，逐字段检查后才写，请求里别的字段不看：`kind`、`pane` 是枚举，不合的写成 `<invalid-enum>`；`name` 须在写定名单内（引擎与 DOM 的错误名、页面对非 Error 抛出物用的 `NonError`）或合乎 `[A-Z][A-Za-z0-9]{0,39}` 且以 `Error` / `Exception` 结尾，否则写成 `UnrecognizedName`；`stack` 至多看 30 帧，每帧须是 `文件名:行:列`；文件名只须是不含路径分隔符的脚本文件名形态（字母、数字与 `._-`，以 `.js` / `.mjs` 结尾——Vite 的产物名里名字与哈希都可以带连字符，如 `direct-engine-BMwLK-Tl.js`），真正的闸门是 server 所服务的 web 构建的 `assets/` 目录里确有这个普通文件，其余帧丢弃（没有 web 构建的 server——开发时由 Vite 提供页面——一帧都不留）。**消息文本一律不记**（用户 2026-10-13 裁决，内建类型也不例外）：接口不读消息字段。写出时不新增字段种类：用检查过的名称与帧拼一个 Error 交给 `f.error`，帧的文件写成 `/assets/<文件名>`。页面一侧在发送前就只取这四样（帧只留文件名，去掉地址、查询串、片段与函数名），不读消息、不取 DOM 与地址栏；上报失败静默丢弃，拼装上报时再出的错不上报。不带 `error` 对象的 window `error` 事件（跨源脚本出错时浏览器只给的 "Script error."、`ResizeObserver loop …` 通知）不是页面代码的未捕获错误，不上报、不占预算。页面自己的预算按时间窗口恢复：每 60 秒至多发 20 条（与 server 的每分钟限量同数，页面因此不会在一个窗口里问得比 server 肯记的多；长期不刷新的桌面窗口每个窗口都重新有预算）。**当前窗格名**由 Shell 在渲染时记下（不是在 effect 里：抛错的那次渲染不会提交，effect 不跑），所以记的是抛错那次渲染所在的窗格；分屏时是活动窗格。**错误边界**的「重新加载」是整页重载（地址不变；模块级状态一并重置，桌面窗口没有刷新键——用户 2026-10-13 裁决），不是重挂载子树；兜底出现时键盘焦点移到这个按钮。
  - **限量**：每个 server 进程每分钟至多 20 条、每次启动至多 200 条，请求体至多 8 KiB（先看 `Content-Length`，再在读取中途截断，不把超长的请求体读完）。超出的、过大的、不是 JSON 对象的都丢弃并按原因计数；计数在第一条被丢弃之后满一个窗口时写成 `page.errors_dropped`（每种原因一条，带丢弃条数与本次启动已记条数），所以持续出错的页面每分钟至多多出几条计数记录，而不是每条上报一条。server 优雅关停（`close()`）时把还没写的计数补写出来；进程被杀掉时这一窗口的计数不写。应答说明这条上报有没有记下：`{recorded: true}`，或 `{recorded: false, reason}`（限量是 200，过大是 413，格式不对是 400）；413、400 与跨来源被拒的 403 应答，各自还会由请求记录中间件写一条 `request.failed`（票 06 的既有性质：4xx 一律记），这些记录不受页面错误限量的约束；没有 log 的 server（测试默认）应答 `{recorded: false, reason: "no_log"}`，不计数。错误边界据此显示「已记入日志」或「没有记入日志」，应答之前这一句不显示文字但位置保留（两句叠放在同一格、只显示适用的那句），应答前后布局不变。日志文件打不开的 `serve` 仍会应答 `recorded: true`（接口分辨不了输出端有没有写成）。
- **诊断包的导出**（desktop-app 票 14；事件名同在 `SERVER_LOG_EVENTS`，写的地方在 server `diagnostics.ts`）。没有新增字段种类。

  | 事件 | 级别 | 字段（括号内是字段种类） | 写的地方 |
  | --- | --- | --- | --- |
  | `diagnostics.exported` | info | `compile_logs`（枚举 `yes` / `no`：请求里是否勾选了附带编译失败日志） | `POST /api/diagnostics/export`，在打包之前写，所以这一条在它自己的诊断包里 |

- **改动日志模块时**：新增字段种类、放宽某种字段的检查、把某个错误类型声明为消息安全、给事件加字段，都要对照 [contracts](contracts.md#用户日志2026-10-13-新增) 的「不进用户日志的内容」逐项核对。

### 诊断（desktop-app 票 14）

「应用不自动上传日志」是硬契约，见 [contracts](contracts.md#用户日志2026-10-13-新增)；这里记接口、诊断包的内容与略去规则。机制在 server `diagnostics.ts`，形状在 contracts `diagnostics-api.ts`，页面在 web `settings/SettingsView.tsx` 的 `Diagnostics` 与 `settings/DiagnosticsExport.tsx`。

- **接口**（都带 `Cache-Control: no-store`，都受与其他接口相同的跨来源守卫）：
  - `GET /api/diagnostics` → `DiagnosticsInfo`：日志目录（`{path, display}`，`display` 的主目录写成 `~`）、日志目录里日志文件的个数与合计大小（只算名字合乎日志文件格式的，见下）、本项目的编译失败日志清单（每项是在包里的条目名、大小、是否放得进上限）与上限。设置页的「日志位置」行与页面错误兜底的「日志位置」一行都用它；取不到时两处都如实写「不知道（没能取得）」。
  - `POST /api/diagnostics/export`，请求体 `{includeCompileLogs?: boolean, compileLogs?: string[], client?: string}` → `application/zip` 附件，文件名 `argelanderspace-diagnostics-<UTC 年月日>-<时分秒>.zip`。`compileLogs` 是对话框列出且标为放入的条目名，至多 40 个（`DIAGNOSTICS_COMPILE_LOGS_MAX_FILES`；与 512 字符的 `client` 一起仍在 4 KiB 的请求体上限之内，有测试核对）。`includeCompileLogs: true` 而没给名单是 400：server 从不自己挑编译失败日志，包里只有用户在对话框里看到的。其余键、类型不对、名单过长、超过 4 KiB 也都是 400。包只在页面请求时生成，作为这次请求的应答交给页面；server 不留副本，也不发往任何地方。
- **保存**（用户 2026-10-14 裁决）：浏览器有 `window.showSaveFilePicker` 时，点「导出」先在同一次点击里弹系统保存窗口（必须先于导出请求，否则等待 server 之后点击授予的权限已失效），拿到文件之后才请求诊断包并写入；用户在窗口里取消就什么也不请求、不记日志、不提示，对话框回到可再次导出的状态；写入失败按导出失败处理。没有这个接口的浏览器交给浏览器的下载（对象 URL 加 `<a download>`，一分钟后释放），保存位置按浏览器的设置。完成提示按两种保存方式分别说。
- **日志目录**：`<全局数据目录>/logs`。`startServer` 把它打开日志用的那个目录交给 `createServer`（`logDir`）；没给时（测试服务器）是本进程钉住的全局数据目录下的 `logs/`，没钉住时按宽松读取 `config.toml` 现算。
- **包里有什么**：
  - `logs/<文件名>`：日志目录顶层名字合乎日志文件格式的普通文件（`<UTC 时间到毫秒>-<进程种类>-<pid>[-<n>].jsonl`，与启动时清理用的是同一条规则：infra `isLogFileName`），原样。其他名字的文件、符号链接、子目录都不取，也不计入 `GET` 的个数与大小。
  - `environment-report.json`：`version`、`generated_at`、`app`（版本、形态：`serve` 为 `browser`，桌面宿主为 `desktop`，desktop-app 票 17）、`system`（平台、架构、内核版本）、`node`、`client`（页面送来的 `navigator.userAgent`：可打印 ASCII 之外的字符写成 `?`，至多 512 字符）、`environment`（与 `GET /api/environment` 同一次检查的结果）、`config`（文件状态、生效值、各键来源、问题清单——问题只有键与类别）、`running`（项目根、项目数据目录、端口、命令行给了哪些键）、`credentials`（ADS token：`keychain` / `file` / `none` / `unreadable`）。
  - 只在勾选时：请求名单里的、此刻仍是票 08 保留的编译失败日志的那些——`compile-failures/jobs/<任务 id>.compile.log` 与 `compile-failures/manuscripts/m_<8 位十六进制>/build/compile-failure.log`；正在收集的 `.partial`、其他名字的文件、符号链接、名单里的任意路径或 `../` 都对不上，被忽略。对话框列出之后才出现的日志不在名单里，不进包。按修改时间从新到旧，累计不超过 32 MiB（`DIAGNOSTICS_COMPILE_LOGS_MAX_BYTES`）且不超过 40 个，遇到第一份放不下的就停，其后更早的一律不放（所以不放入的总比放入的旧）；放不进的在 `GET` 的清单里标为不放入，对话框如实列出「另有 N 个较早的文件不放入」。
- **略去规则**（环境报告）：`config` 的值与来源里没有 schema 的全部凭据键（由 `SECRET_SETTING_KEYS` 推导，现在是 `openalex_api_key`、`ads_dev_key`），也没有 `contact_email`、`global_dir`、`global_cache_dir`（`DIAGNOSTICS_OMITTED_KEYS`）；`running` 里没有全局目录；日志目录的路径不进报告。最后对整份报告的每个字符串把主目录写成 `~`（`withoutHome` / `replaceHome`），`{path, display}` 只留按此写过的路径：只在主目录后面紧跟路径分隔符、字符串结尾或路径名里不会有的字符时才替换（`/home/x2`、`/home/x.old` 不动）；Windows 上两种分隔符视为相同、不分大小写（`C:/Users/Wu/…`、`c:\users\wu\…` 都写成 `~`）。设置页自己的 `displayPath` 没有改。凭据只报状态；邮件账户与邮箱密码不在报告里。
- **体积与生成**：日志目录按「用户日志」的清理至多 20 个文件、合计 50 MB（加上正在写的这一份）；编译失败日志另限 32 MiB、40 个。文件异步读取，每个条目在 libuv 线程池里压缩（infra `lib/zip.ts` 的 `zipEntriesAsync`，Node 内置 `zlib`，无新依赖，不支持 Zip64），生成期间 server 照常应答别的请求；整个包仍在内存里拼成一个 Buffer，原样作为应答体。
- **导出记一条日志**：`diagnostics.exported`，只有 `compile_logs`（是否勾选），见上面的事件表；在系统保存窗口里取消的不请求，所以也不记。
- **页面**：设置页「诊断」分组三行——日志位置（浏览器形态显示路径并可复制完整路径；桌面应用显示路径加「显示日志文件夹」，经宿主请求打开，票 17；页面出错的兜底在桌面应用里同样多一个「显示日志文件夹」）、日志级别（`log_level` 的下拉框，改了即生效）、导出诊断包（打开对话框）。对话框按获批原型：说明、一个默认不勾的勾选项「附带最近的编译失败日志（含论文或稿件的源码片段）」、取消与导出；用户 2026-10-14 接受的原型外补充：清单取到之前勾选项不可用，勾选后列出将放入的文件与合计大小，项目里没有编译失败日志时勾选项不可用并写明「没有可附带的编译失败日志」，导出失败的提示（「没能生成诊断包」），取不到时的「不知道（没能取得）」。

## 桌面宿主（desktop-app 票 17）

[ADR 0010](adr/0010-desktop-app-tauri-node-sidecar.md) 里由壳看管的 Node 进程。机制在 server `desktop-host.ts`（入口、行协议、端口、关停）与 `host-routes.ts`（宿主接口），形状在 contracts `host-api.ts`，页面在 web `host.ts`、`api/host.ts`、`settings/PortFallbackBanner.tsx`。欢迎状态、最近项目与切换 Project 是票 18、19；Rust 壳是票 20。

- **入口**：`argelanderspace desktop-host --project <文件夹> [--web-dist <目录>]`，与 CLI 同在 app 的 `bin.js` 里，命令不出现在帮助中。文件夹不在或不是目录时 stderr 一行 `error: …`、exit 1、不输出任何行。两个文件夹参数是相对路径时都按调用方（壳）的工作目录解析。宿主随后把工作目录切到这个文件夹，所以项目数据按与在该文件夹里运行 `serve` 相同的相对路径规则找到（`data_dir` 只来自 config.toml，宿主不接受 `--data-dir` / `--port`），设置页的「当前项目」就是它。随后走 `startServer`（形态 `desktop`）：同一份宽松读取、同一个日志目录（文件名 `…-desktop-<pid>.jsonl`）、启动记录与诊断报告写 `desktop`；`serve` 打到终端的三行改写到 stderr，因为 stdout 只承载行协议。
- **行协议**：标准输入输出上每行一个 JSON 对象，`type` 区分种类。
  - 宿主 → 壳：`ready`（`url`、`port`、`configuredPort`、`portFallback`、`portOccupant`、`project`；监听之后写一次。`project` 是宿主切换后的工作目录，即规范化的绝对路径〔符号链接已解析，`realpath`〕，不一定与 `--project` 给的字面相同，壳比较时按规范化路径比）；`request`（`kind` 为固定枚举 `pick_folder` / `open_in_browser` / `open_devtools` / `open_log_folder` / `open_config_file` / `open_skills_folder`。要打开什么由宿主按自己知道的东西填：`open_in_browser` 带自己的地址 `url`，`open_log_folder` 带日志目录、`open_config_file` 带配置文件的 `path`，`pick_folder` 带一个 `id` 等壳回答；`open_skills_folder` 暂不带路径，随包 skills 的位置由票 24 定。页面经宿主接口请求，接口不读请求体，所以行里没有页面给的路径或网址）；`stopping`（`reason`：`quit` / `input_closed` / `output_closed` / `signal`）与 `stopped`（关停开始、结束；`stopped` 之后端口已释放、进程以 0 退出）；`failed`（`stage: "start"`，server 没能启动，随后 exit 1）。
  - 壳 → 宿主：`{"type":"quit"}`；`{"type":"folder_picked","id":…,"path":<绝对路径>|null}`（对 `pick_folder` 的回答，null 为取消；id 对不上、路径不是绝对路径的不收；本票只记日志 `desktop.folder_picked`〔`picked` / `cancelled`，不记路径〕并交给 `onFolderPicked`，票 18 接上切换）；`{"type":"shell_event","event":…,"fields":{…}}`（壳自己的事件，写进宿主的日志，规则与其他记录相同：事件须在 `SHELL_EVENTS` 表内——`shell.started`、`shell.host_started`、`shell.host_exited`〔`expected: "no"` 时 warn〕、`shell.dialog_answered`、`shell.request_failed`——每个字段按表里写定的构造函数〔标识符、数字、时长或写定的枚举〕写出，类型不对的写成占位或空，表外的字段不写、计入 `dropped_fields`；表外的事件名——包括 server 自己的记录名如 `server.started`、`process.uncaught_exception`——不交给日志模块，而记一条固定的 `desktop.protocol_rejected`〔原因 `unknown_event`，不带事件名与字段〕）。
  - 一行至多 64 KiB，超长的整行丢弃；不是 JSON、种类不认识、形状不对、id 对不上、壳事件名不在表内的行不执行，记 `desktop.protocol_rejected`（只有原因类别：`too_long` / `not_json` / `unknown_type` / `bad_shape` / `unknown_id` / `unknown_event`）。宿主自己的记录还有 `desktop.request`（请求种类）、`desktop.stopping`（原因）与 `desktop.stop_timed_out`（关停时限，见下）。
- **端口回退**：端口取 config.toml `port`（默认 1859），也就是 CLI 深链接用的那个。启动前先在 127.0.0.1 上试绑一次；被占用（或绑不上）时向该端口问一次 `GET /api/host`（1.5 秒、至多读 16 KiB），答的是合法的宿主信息即判为另一个 ArgelanderSpace（`argelanderspace`），否则为别的程序（`other`），两种情况都改由系统挑一个空闲端口监听，不去动占着端口的那个进程。就绪行、`GET /api/host` 的 `portFallback`（`{configured, actual, occupant}`）和启动记录都标明；页面在工作台顶部常驻警告横幅（`port-fallback-banner`，不能关闭）说「CLI 生成的链接这次打不开」并写出两个端口，占着端口的是另一个 ArgelanderSpace 时另一行说那些链接会打开它而不是这个窗口。配置的端口是 0 时不回退。剩余窗口：试绑与真正监听之间端口被别人抢走时启动失败（`failed`，exit 1，由壳提示）；占用者只绑在 `::1` 上时试绑 127.0.0.1 不冲突，宿主照常用配置的端口，而 CLI 链接里的 `localhost` 可能解析到那一个。
- **关停顺序**：收到 `quit`、标准输入结束（壳退出或被杀）、标准输出断开、或 SIGTERM / SIGINT 时，只关停一次：记 `desktop.stopping`、写 `stopping` 行、此后经宿主接口到达的请求不再写请求行（答 409 `shutting_down`；监听端口关闭之后，带页面来源的请求先被跨来源守卫拒绝）；然后是 server 现有的优雅关停（`createServer().close()`：第一步同步 `disposeMailSendServices()`，撤销窗口内的邮件标为 `interrupted`、留在 Drafts、不发出；再停文件监视、WebSocket、Copilot、邮件监听，最后关监听端口，等进行中的请求结束）；日志文件随之关闭；写 `stopped`（等它交给输出后）进程以 0 退出。**关停时限**：因壳已不在（标准输入结束、标准输出断开）而开始的关停，宿主给自己 10 秒（`HOST_STOP_DEADLINE_MS`）；到时仍未关完就记 `desktop.stop_timed_out`（warn，`ms`）并以 1 强制退出，进程一退端口即释放。撤销窗口的邮件在关停第一步已同步标为中断，所以强制退出不会发出邮件。计时器不挡进程退出：卡住关停的若只是一个不再有活句柄的 Promise，事件循环先空掉，进程不等到时限就直接退出（退出码 13，不写 `desktop.stop_timed_out`），端口同样释放。收到 `quit` 或信号时壳还在，宿主不设时限，超时强制结束由壳负责（spec「进程结构」）。
- **宿主接口与能力标志**（同样受跨来源守卫，`no-store`）：`GET /api/host` → `{version: 1, app: "argelanderspace", mode, requests, portFallback}`；`serve` 没有宿主，答 `mode: "browser"`、`requests: []`。`POST /api/host/requests/:kind` → 202；浏览器形态 404 `not_desktop`，种类不认识 404 `unknown_request`，宿主关停中 409 `shutting_down`。页面每次加载问一次（`useHostInfo`），答复到之前、没有可用答复时一律按浏览器形态：桌面专属控件不出现。桌面形态下出现的控件：设置页顶部配置文件路径旁的「打开配置文件」（`open-config-file`）、不能安全修改的行下的同一按钮（只有按钮，带键名）、保存失败浮层里的「打开配置文件」（`settings-save-failed-open-config`）、「诊断」分组的「显示日志文件夹」（`show-log-folder`）、页面出错兜底的「显示日志文件夹」（`page-error-show-logs`）；宿主没有接受请求时设置页底部浮层说明。「命令行与 agent」分组（票 24）与 `tex_dir` 的「选择文件夹…」不在本票，两种形态都还不出现。

## LaTeX 数据流

隔离 workspace → latexmk（编译事实与插桩事件）＋unified-latex 源码树/有界宏展开 → 融合 IR → 图资产物化 → 直接存储/展示。

印刷编号取编译真值，不从结构 id 猜测；编译失败不做无编译全文降级。PDF/EPS 图片转换采用 pdftocairo/gs，旧 pandoc/mupdf/dvisvgm 路线退役。执行护栏、事实盲区、回退和测试范围见 [tex-pipeline](tex-pipeline.md)。Writer 显式 profile 共享主干但不共享摄入/归档副作用。

## Web 与同步

- `serve` 端口：`--port` > config.toml `port` > 1859；Hono REST、SPA、images、`/ws`。写请求的 CSRF 守卫与 `/ws` 升级的来源白名单相同：本机地址（`localhost`、`127.0.0.1`）上的开发端口 5173，加 server 实际绑定的端口（逐请求读取，`--port 0` 的临时端口同样成立）；不带 `Origin` 的本地工具放行。web 的开发代理指向默认端口。
- watcher 轮询 library、plans、per-doc current annotations、manuscript JSON 和模板 JSON 指纹；server 自写可再收到 external，前端幂等重取。没有资产目录 watcher。
- JobRunner 串行、持久化；boot 将未完成 job 标 interrupted，不重跑；hello 回放，失败在详情刷新后仍可见；job.done 先于 library.changed。upload、refresh 和 arXiv ingest 生命周期不能与 Discovery 只读请求混淆。
- 文献 label 色板：red重点 / amber待读 / green已精读 / blue方法 / violet灵感；overlay > 持久 label > star 播种。已读标题灰化及“已读”，未读蓝点。
- 阅读中列流式、100ch 上限；顶部可折叠作者块，多引用 per-ref chip；图片尺寸预留与停稳校正。右栏默认引用，可切标注；DOM 不嵌套高亮 span。
- 文献深链接 `/doc/<doc_id>#<anchor>` 使用 sec-N/fig-N/eq-N/tab-N/ref-N 等结构 id，不是印刷编号；标注使用 `#ann-<annotation_id>`。探索链接及历史见 discovery。

## Agent 接入

CLI + 仓库 `skills/argelander-*` 三件套（ingest/query-library/read-paper），无 MCP 是项目选择；本机安装方式不成为跨机器保证。

- search/read/show/ref/note/label/list + 只读 annot，CLI 直读磁盘，不依赖 HTTP。论证图另有 `argument get` / `argument put`（整图读写，写入带 rev，覆盖非空图须 `--replace`）与只读的 `pdf-path <docId>`（只输出 PDF 原件路径），见 [argument-graph](argument-graph.md)「CLI」。
- `skills/argelander-argument-graph` 读一篇已摄入文献并把论证图写入工作台（读正文走既有 `read`/`show`/`ref`，PDF Doc 经 `pdf-path` 取原件路径，写入走 `argument put`）；覆盖非空图前须问用户，不是第四个文献问答 skill。
- 文献问答从项目根走 CLI/skills，不传 `--data-dir`，不读内部 JSON/源码替代文献接口。开发任务不受此源码禁读限制。
- 仓库 CLI：`node packages/app/dist/bin.js`；全局安装后 `argelanderspace`。
- 深链接端口：config.toml `port` > 1859，不读环境变量；`serve` 用 `--port` 起在别的端口而 config 没写时，CLI 打印的链接仍指向 config 或默认端口。
- search 空 note 提示只走 stderr，stdout JSONL 保持可 pipe；摄入后每篇询问 note 并给建议稿。输出冻结以 contracts 为准。
- `skills/argelander-find-papers` 是三件套之外的独立 skill（2026-10-10）：自带零依赖脚本 `scripts/ads.mjs` 直接查询 ADS（search / similar / useful），token 只读 `~/.ads/dev_key`（与工作台在设置页保存的 ADS token 是两份，互不影响；desktop-app 票 12），不经过 CLI、不读写 Library、不落盘、无缓存。它由 agent 编排多次查询并自行排序，不是 Discovery 的实现，也不改变 [discovery](discovery.md) 的固定查询语义；入库仍是另行的显式动作。
