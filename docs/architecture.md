# 产品与架构

ArgelanderSpace（npm `argelanderspace`，MIT，© Wenjie Wu）是单用户科研工作台。用户通过 webui 独立操作、亲自阅读，也通过 CLI + skills 与 agent 协作。领域语言见 [CONTEXT](../CONTEXT.md)，不可擅改的边界见 [contracts](contracts.md)。

本页记录当前能力和结构，不列待实现任务。产品事实来自 Stage 15 关闭后的记录；阶段结果见 [history](history.md)，新工作由用户决定。

## 能力入口

- **文献库与正文**：arXiv LaTeX / 本地源码摄入，条目内 LaTeX zip 挂载；现支持 Work 内不可变本地 PDF 上传、阅读、原件下载、设主与删除。Web 添加时的 arXiv 获取仍只处理 LaTeX 源码。身份、存储规则及获取场景见 [library](library.md)。
- **文献发现**：从详情页进入 ADS related/useful 临时探索；库图只含已存 Work。边义、失败语义、缓存与用户状态分离见 [discovery](discovery.md)。
- **阅读器**：LaTeX Reader 用共享 IR/标注及共同 epoch；本地 PDF 使用固定 EmbedPDF 2.15.1、同次 hash 校验的原始 bytes 和独立用户 sidecar，PDF 内嵌标注只读。PDF 基础分页/缩放/下载已接入，PDF 工作台标注编辑、搜索/目录和进度保存不属于此边界。LaTeX 规则见 [annotations](annotations.md)，PDF 数据保护见 [contracts](contracts.md)。
- **计划页**：默认 landing，plans→tasks 的列表/看板/时间线/今日聚焦，webui 可独立 CRUD。详细模型和否决项见 [plans](plans.md)。
- **Writer**：独立稿件、八型 cell、CodeMirror、显式 Render/Shift+Enter、共享编译→IR 预览及源码 zip；不展示 PDF。工作流见 [writer](writer.md)，文件协议沿用 [writer-data-model](writer-data-model.md)。
- **web i18n**：zh-CN/en，默认中文、不探测浏览器，Tweaks 即时切换，偏好存 localStorage。server detail/job.error 和用户数据不纳入翻译；CLI 不变。
- **尚未完整的写路径**：文献 note tab 当前只读；持久 note/label 主要通过 CLI，右键色点 overlay 仅会话级。这是能力缺口，不推翻独立应用定位。
- **不在 main**：OCR/出版商 HTML 摄入封存于 `ocr-features` 快照分支。现行 PDF 是不可变原文件阅读，不是 OCR/LaTeX 转换能力。

## 数据与配置

默认项目级 `./literatures`，只按 cwd 相对解析，不向上查找。优先级：

`--data-dir` > `ARGELANDERSPACE_DATA_DIR` > config.toml `data_dir` > `./literatures`。

配置通常在 `~/.config/argelanderspace/config.toml`，支持 XDG_CONFIG_HOME；env 优先，未知键忽略，已知键类型错只报键名、不回显值。隐藏 `auto_ingest_arxiv` 默认 true，语义见 library。

**全局数据**（[ADR 0007](adr/0007-global-data-scope.md)，2026-10-06 决定；目录解析已在 infra 实现，Mail 账户已使用）：属于用户本人、跨项目共享的数据（首个使用者是 Mail 账户）不放 dataDir。全局数据与可丢弃的全局缓存分开，按 `env-paths`（name `argelanderspace`、无 suffix）取各 OS 标准目录：Linux `$XDG_DATA_HOME`/`$XDG_CACHE_HOME`（默认 `~/.local/share`、`~/.cache`），macOS `~/Library/Application Support`、`~/Library/Caches`，Windows `%LOCALAPPDATA%\argelanderspace\Data`、`…\Cache`。覆盖优先级 `ARGELANDERSPACE_GLOBAL_DIR` > config 键 `global_dir` > OS 默认；全局缓存对称：`ARGELANDERSPACE_GLOBAL_CACHE_DIR` > `global_cache_dir` > OS 默认，两者互不影响（改数据目录不移动缓存）。空白 env 视为未设，相对路径一律拒绝（ConfigError，只报来源名；按探测到的平台判断绝对路径，避免随 cwd 分裂全局目录）；`global_dir`/`global_cache_dir` 类型错只报键名。`resolveGlobalDirs` 不访问文件系统（未传 config 时读 config.toml）；OS 默认目录由 env-paths 在 import 时固定 homedir，测试隔离须在导入前把 `HOME`/`XDG_*` 指向 tmp；目录由 `ensureGlobalDirs` 按需创建，权限 0700（infra `global-dirs.ts`）。既有 config.toml 位置不变，项目数据不迁移。

**凭据存储**（Mail 票 02，ADR 0008；infra `credential-store.ts`，Mail 账户服务已调用）：窄接口 `get/set/delete(accountId)`，后端 `@napi-rs/keyring`（MIT，service `argelanderspace.mail`，原生模块惰性加载，失败按“不可用”处理；Linux 上 Entry 显式固定 `{linux:{store:"secret-service"}}`，否则绑定会静默回退到内核 keyutils（仅内存、重启即失），固定后无 Secret Service 时构造抛错即“不可用”；app 包将其列为运行时依赖，因原生 `.node` 不可内联）且可注入。钥匙串任何失败都返回 `keychain-unavailable`，不自动降级；仅当调用方传 `{ fileFallbackConsent: true }`（严格 `true`，表示用户已在 UI 同意）才写全局数据目录下 `credentials.json`（0600，tmp+rename 原子替换，AES-256-GCM 轻度加密，密钥由文件内盐与本机用户名/主机名派生，只防误看，不防同用户读取），结果带 `keychainProtected:false` 供 UI 持续标示。读取时钥匙串优先、其次文件；钥匙串可用后再 `set` 会迁入钥匙串并移除文件副本。钥匙串写成功后若旧文件副本无法移除，结果带 `staleFileCopy:true`；钥匙串不可用但文件副本已删时 `delete` 返回 `{status:"deleted", keychainUnavailable:true}`（钥匙串里可能仍有副本，未检查）；文件重写失败为 `file-write-failed`。失败结果只含状态码（`invalid-input`/`file-unreadable`/`file-write-failed`），不含异常消息或密码；唯一含密码的是成功 `get` 的返回值，调用方不得日志/广播/回显。跨进程：文件读-改-写同刻并发写不同账户可能丢一次写（后写者胜），按 ADR 0007 的要求在此明示并同步写入 contracts，可接受（用户重输一个密码）。账户 id 在文件中以 Map 保存，`__proto__` 等同普通键。

**Mail 账户**（Mail 票 04，ADR 0007/0008；infra `mail/account-store.ts`、`mail/protocol.ts`，server `mail-accounts.ts`/`mail-routes.ts`，contracts `mail.ts`；账户添加/重输密码/移除的最小 Web UI 随票 05 在 Mail 页内，设置编辑等另票）：账户列表是全局数据 `<globalDir>/mail/accounts.json`（`{version, rev, accounts}`，不含密码；每个账户有 id `acc-<12 hex>`、显示名、地址、preset、IMAP/SMTP 主机端口加密方式 `tls|starttls`〔不接受明文〕、两个登录名、`credentialRef`（＝id，凭据存储键）、`credentialProtection`（`keychain|file`，`file` 即未受钥匙串保护，UI 持续标示））。每次修改在 proper-lockfile 跨进程锁（`accounts.lock`）内读—比对 `rev`—写（tmp+rename，0600，rev+1）；rev 不符抛冲突、一字节不写，REST 回 409 `rev_mismatch` 带当前 rev；文件损坏/校验失败为 500 且不覆盖。预设（Gmail/iCloud/自定义，主机端口见 contracts `MAIL_PRESETS`；大学、研究所等其他邮箱一律走自定义，不按机构单列预设，2026-10-09 用户决定）只补全省略字段，显式字段优先；iCloud IMAP 登录名取地址 @ 前部分、SMTP 取完整地址。协议库 imapflow 2.2.7（MIT）与 nodemailer 10.0.15（MIT-0）只在 infra `protocol.ts` 内引用，窄接口 `MailProtocol.verifyImapLogin/verifySmtpLogin` 只返回失败码（`auth_failed`/`host_not_found`/`connection_refused`/`timeout`/`tls_failed`/`starttls_unsupported`/`protocol_error`/`unknown`），库的错误文本与服务器应答一律丢弃；要求 STARTTLS 而服务器不支持时失败，绝不退回明文登录；证书默认严格校验。REST（`/api/mail`，同 provider 的 CSRF 守卫，`no-store`）：`GET /presets`、`GET /accounts`、`POST /accounts/test`（只测不存；`accountId` 且无密码时用已存密码）、`POST /accounts`（先分别测 IMAP 与 SMTP，任一失败 422 `connection_failed` 带两协议各自结果且不保存；钥匙串不可用且无 `fileFallbackConsent` 为 422 `keychain_unavailable`；同地址重复 409 `duplicate_address`）、`PUT /accounts/:id`（body 带 `rev`；连接参数或密码变更才重测，仅改显示名不连接；密码在 rev 校验通过后才写入凭据存储）、`DELETE /accounts/:id?rev=`（锁内先删凭据，再删账户记录，再删 `<globalCache>/mail/<id>`；绝不连接远端，不触碰远端邮件；凭据无法确认已删除〔钥匙串不可达/凭据存储出错〕时拒绝删除并保留账户，可重试；缓存删除失败只带 `cache_not_removed` 警告）；`POST /accounts/test` 用已存密码时，主机端口加密方式与登录名必须与已存账户一致，否则 400，避免已存密码被送往任意主机。错误体只含固定文案与字段名，不含密码、用户名、主机应答或 zod 消息。并发范围见 [contracts](contracts.md)：账户配置是跨进程安全的（上述锁+rev），缓存不加锁。

**Mail 管理与服务端搜索**（Mail 票 06，ADR 0008；contracts `mail-manage.ts`，infra `mail/protocol-manage.ts`〔`MailManage`：`setFlag`/`move`/`remove`/`search`，imapflow 仍只在 `mail/` 协议文件内〕，server 守卫）：`messages/flag`（`seen|flagged` 加 `value`，应答为服务器实际标志）、`messages/move`（`destination`，应答含邮件在目的文件夹的新 uid/uidValidity，供撤销；无 COPYUID 时为 null、不提供撤销）、`messages/delete`、`messages/search`（POST 以免搜索词进 URL/日志）。删除＝移入 Trash（`\Trash` 特殊用途，缺失时按 Trash/Deleted Items/Deleted Messages/Bin/Papierkorb 名称回退，名称回退与 imapflow 的“按名称猜测”都只认顶层或 INBOX 的直接子级，`Projects/Deleted` 这类嵌套自定义夹不会被当成 Trash；服务器声明的 `\\Trash` `not_in_trash`）；永久删除只用 `UID EXPUNGE`，服务器无 UIDPLUS 时 502 `unsupported`（普通 EXPUNGE 会连带清掉他人已标 `\Deleted` 的邮件）；无 MOVE 扩展时自行 COPY＋`UID EXPUNGE`（要求 UIDPLUS），删除失败则撤回源邮件的 `\\Deleted` 并返回 `partial`（目的地已有副本、原邮件仍在，结果未知）；找不到 Trash 绝不退化为永久删除（`trash_not_found`）；expunge 被拒时撤回 `\Deleted` 标记。imapflow 把 STORE/MOVE/EXPUNGE 的 NO 应答只返回 `false`，因此“服务器拒绝”（`refused`）与“连接中途断开”（`connection_lost`，结果未知，UI 提示刷新核对）由会话是否仍可用区分；发出改动命令之后的任何抛错（含超时、读回失败）一律按 `connection_lost`（结果未知）而非 timeout/unknown；另有 `destination_not_found`。UI 对 `connection_lost`/`unreachable`/`unavailable`（服务应答不可读）的文案是“结果未知”（不说没成功也不说仍在原处）：先回滚乐观显示，再对文件夹列表、源文件夹、目的地（移动的目的文件夹/删除的 Trash）静默重载——无转圈、不把已“加载更多”的分页截回第一页、不让统一收件箱该账户的行消失；搜索中则重跑搜索。重载成功提示“已从服务器重新加载”，重载失败保留回滚后的状态并提示“无法从服务器确认”。`loadSource` 的每次写回都是对当前条目的函数式更新（不用启动时抓取的快照，否则失败的重载会把回滚覆盖回乐观状态）。`partial` 状态已知（目的地有副本、原邮件仍在），单独文案，不算“未知”；`message_not_found` 为“邮件已不在此处”且不放回行。在途移动的行若被重载带回，移动成功时仍会移除。搜索：条件 `text`（发件人/主题/正文任一）、`from`/`subject`/`body`、`since`（含）/`before`（不含，日历日）；服务器端 UID SEARCH（日期用 SENTSINCE/SENTBEFORE，即列表显示的信头 Date，不是到达时间；日期必须是真实日历日，`2026-02-30` 被拒；非 ASCII 词由 imapflow 以字面量＋CHARSET UTF-8 发送；搜索会话的 socket 空闲超时单独为 60 s），结果按 uid 降序分页（`before` 游标，`matches` 为总命中数），EXAMINE 只读；搜索失败的提示用独立文案（“服务器拒绝了这次搜索”“搜索没有完成”），不提“更改”；SEARCH 被拒是错误而不是“空结果”（05 的列表 `SEARCH ALL` 同样：被拒按 `protocol_error` 处理，有缓存则作 stale 返回，缓存不被清剪）；搜索结果不入缓存，没有本地全文索引。缓存一致性（缓存写入失败不会把服务器已完成的改动变成错误应答）：成功改标志后更新缓存信头；移动/删除后删除源文件夹缓存信头与已缓存正文；服务器答 `message_not_found` 时同样清除；列表重新取到最新页时，缓存中落在该页 uid 范围内（首页则整个高于页底的范围）而服务器已无的信头被剔除，避免离线视图复活已被他处移走的邮件。Web：阅读栏动作条（星标、已读/未读、移动菜单、删除；Trash 内为“移回收件箱”＋“永久删除”）与列表搜索框（`from:`/`subject:`/`body:`/`since:YYYY-MM-DD`/`before:` 与自由词；Enter 才搜索，搜索中状态/命中数/失败原因一行显示；换文件夹即清除搜索）。乐观更新：标志、移动、移入 Trash 立即显示，失败则原样回滚（标志、行在列表中的原位置、文件夹未读数、被关闭的阅读栏）并以提示条说明原因；同一封邮件在途时动作按钮禁用；移动/移入 Trash 成功后给 8 秒“撤销”（用返回的新 uid **Mail 实时更新与未读角标**（Mail 票 08；contracts `mail-events.ts`，infra `mail/inbox-watch.ts`〔`MailInboxWatcher`，imapflow 仍只在 infra `mail/` 协议文件内〕，server `mail-watch.ts`/`mail-watch-routes.ts`/`mail-watch-default.ts`，web `src/mail/mailLive.ts`/`MailNavItem.tsx`）：每个 server 进程对每个账户只保持**一条** INBOX 连接（只读 SELECT；服务器通告 IDLE 则 IDLE，每 9 分钟重启，否则每 60 秒 STATUS 轮询），收到 EXISTS/EXPUNGE/FLAGS 即在**已选中的 INBOX 内**取快照（总数＝选中邮箱的 EXISTS，未读＝`SEARCH UNSEEN`；RFC 3501 §6.3.10 不建议对已选中邮箱用 STATUS），轮询模式（不 SELECT）才用 `STATUS (MESSAGES UNSEEN UIDVALIDITY)`；快照连同“自上次以来推送了哪些事件”交给 server，server 与上次比较后经 `/ws` 推 `mail.changed`（`accountId`、`cause: inbox|flags|state`：`inbox`＝邮箱内容变化〔新邮件/EXPUNGE/总数或 UIDVALIDITY 变〕，`flags`＝服务器推送了标志变化（已读/星标等）而内容未变，**即使未读数没变也推**，`state`＝只有 watch 状态变或连接后的首次快照、INBOX 未读数、watch 状态、时间；不含邮件内容、地址或服务器文本）。其他文件夹的变化不推送，刷新时才见。watch 状态：`connecting|idle|polling|offline|auth_failed|credential_missing`。断线按指数退避重连（2 s 起、翻倍、上限 5 分钟，±20% 抖动；连接稳定 ≥30 s 才重置），重连后的首个快照与断线前比较，错过的新邮件会报告；**只有真正的凭据拒绝才算 auth_failed 且不重试**（响应码 AUTHENTICATIONFAILED/AUTHORIZATIONFAILED，或 NO 无响应码；`UNAVAILABLE`/`LIMIT`/`INUSE`/`SERVERBUG` 临时码，以及无码/`ALERT` 且文本只谈连接数〔simultaneous、too many connections/sessions、connection limit〕并且**不含**密码/凭据/登录失败/尝试次数/锁定等字样的拒绝归为可退避重试，watcher 内以 `protocol_error`＋`temporaryRefusal` 表示，不改读路径的失败码语义；**连续 3 次**临时拒绝（中间无成功连接）也转为 auth_failed 并停止），直到账户文件 rev 变化；凭据缺失（credential_missing）按同一退避重试，rev 变化时也立即重启。账户增删改由 server 每 5 秒对照 `accounts.json` 并在账户路由成功后立即对账：只启停/重启受影响账户的连接，`stop()`（`server.close()` 先等它）中止全部连接与定时器；多进程各自连接、互不协调。`GET /api/mail/unread`（`{version,accounts:[{accountId,unread,watch}],total}`）给角标与重连补读；`total` 只计未处于 `auth_failed/credential_missing` 的账户的 INBOX 未读（离线账户保留最后一次的数）。`createServer` 默认**不**启动 watcher（测试服务器因此绝不读真实全局账户），只有 `startServer` 传 `mailWatch:true`。Web：`mailLive.ts` 是整页唯一的实时画面，Shell 的 Mail 入口显示数字角标（>99 为 99+，可访问名称含未读数）；Mail 页把自己新取到的 INBOX 未读与登录失败账户回报给它，使角标与文件夹树同数；`mail.changed`（非 `state`）与 WS 重连后，Mail 页静默重载文件夹树与可见 INBOX 列表（最新页替换、已加载的更旧页保留，失败不显示错误）。无系统/浏览器通知。

**Mail 写信与发送**（Mail 票 07，ADR 0008 / 规格 Q16；contracts `mail-compose.ts`，infra `mail/outgoing.ts`〔`composeMail`＝nodemailer MailComposer；`MailOutgoing`：`saveDraft`/`deleteDraft`/`appendSent`/`sendSmtp`，imapflow/nodemailer 仍只在 infra 邮件文件内〕，server `mail-compose.ts`/`mail-send.ts`/`mail-outbox.ts`/`mail-compose-routes.ts`，web `src/mail/compose-session.ts`〔写信会话：自动保存、发送与撤销、结果报告、留在本标签页的文字；非 React〕/`MailCompose.tsx`/`ComposeWindow.tsx`）：只发纯文本正文（富文本不在第一版）。**草稿**存在服务器 Drafts 文件夹（APPEND，标志 `\Draft \Seen`），身份是 Message-ID（客户端生成 `<uuid@账户域名>`，之后每次保存、最终发送都用它）；保存＝先 APPEND 新副本，再只删除同 Message-ID 的**更旧**副本（uid 更小者），所以两次竞争保存最坏留下两份、绝不会零份。Drafts/Sent 文件夹先按 special-use（`\Drafts`/`\Sent`），再按常见名称查找，找不到 Drafts 则拒绝（`drafts_unavailable`，不发送）。回复/全部回复/转发/编辑草稿的初始内容由服务器按原信源生成（`POST init`）：回复收件人＝Reply-To，否则 From（原信是自己发的则取原收件人）；全部回复再加原 To/Cc，去重并去掉自己；`In-Reply-To`＝原 Message-ID，`References`＝原 References＋原 Message-ID；主题加一次 `Re:`/`Fwd:`（同族前缀不叠加）；回复引用 `> ` 逐行，光标在引用之上；转发带“转发的邮件”头与非内联附件（暂存为待发附件）；只有 HTML 的原信用去标签文本引用。**附件**先上传到暂存区 `<globalCache>/mail/_staged/<attId>.bin|.json`（可丢弃缓存，不挂在某个账户目录下，因为写信时可以更换发件账户而附件要跟着草稿走；缺失在发送/保存时报 `attachment_missing`，用户重新添加；发送成功/放弃草稿时删除，其余 7 天后清扫；编辑 Drafts 里的草稿或转发时，原信的非内联附件被暂存到这里），单个 ≤ 40 MiB、整封 ≤ 50 MiB、≤ 50 个；界面按编码后约 4/3 估算大小，超过服务商文档上限（Gmail 25 MB、iCloud 20 MB，未在本票联网复核；自定义未知）时显示警告但不阻止，真正的拒绝由服务器给出（`message_too_large`，草稿保留）。

**发送与 8 秒撤销**（`POST /api/mail/compose/accounts/:id/send`，body `{sendId, draft}`，202）。服务器按下列顺序执行，这个顺序就是“无重复发送、不丢信”的论证：①对该 Message-ID 取独占 claim：先过进程内守卫（`账户+Message-ID` 集合，缓存目录被删时仍有效），再在缓存里 O_EXCL 创建 `outbox/claim-<hash>.json`；已有 claim 的持有者进程不存在、或属主 pid 相同而 boot id 不同（pid 复用）、或超过 10 分钟，视为陈旧并替换；**无法解析的 claim 若 mtime 在 5 秒内按“对方正在创建”视为 live**，更旧的当垃圾。已被占用回 409 `already_pending`；同一 `sendId` 再次提交（双击、重试，含并发）合并为同一次发送；持有 claim 后再查 **sent 守卫**：该 Message-ID 在 7 天内已被 SMTP 接受过则回 409 `already_sent`（应答丢失后换新 `sendId` 重发、迟到的旧请求、另一个标签页里同一草稿都在这里被拦下）。claim 与 sent 守卫都以**“账户＋Message-ID”**为单位，只在同一发件账户内成立：换一个账户发送同一草稿不受它们约束，所以写信窗在应答未确认期间锁定发件人（见下文前端）；②把**最终版**邮件存进 Drafts（失败则不进入窗口，什么都没发；进入前后两次确认账户仍存在，已删除的账户不会被重建缓存目录）；③严格写标记 `outbox/<sendId>.json`（状态、属主 pid 与进程 boot id、截止时间；写不下去也不进入窗口）并启动**内存里**的计时器（`unref`）；④窗口内 `POST …/sends/:sendId/undo` 清计时器、释放 claim、标记 `cancelled`，草稿原样在 Drafts；⑤到点：属主进程**严格写入** `sending` 标记（写不下去就不发，标 `failed/storage`），做**一次** SMTP 事务（SMTP 永不自动重试），成功后先记 `sent` 并写 sent 守卫（`outbox/sent-<hash>.json`，另有进程内副本；写在释放 claim 之前，所以 claim 与 sent 守卫首尾相接、中间没有空档；清理完成后再写一次，记下 Sent 副本的结果。**磁盘写入是尽力而为**：邮件此时已经发出，写不下去不会让发送失败，但那样守卫只存在于本进程内存里，另一个进程和重启后的进程都看不到它），再决定是否 APPEND 到 Sent（`mailServerSavesSent(account)`：账户可选字段 `serverSavesSent` 优先，缺省取 preset 默认 `MAIL_SERVER_SAVES_SENT`——Gmail 为 true〔其 SMTP 自动保存，不重复〕，其余默认 false，iCloud 未经实测；旧账户文件无该字段仍兼容；用户在添加账户对话框或账户⋯菜单“设置”里改，走带 rev 的 PUT，省略该字段的编辑保留原值）并删除 Drafts 副本；清理完成前对外仍报 `sending`；Sent 副本存不下时保留 Drafts 副本并如实告知。收件人被部分拒绝时邮件已发给其余人，计数告知；全部被拒为 `recipient_rejected`。失败（definite）时草稿仍在 Drafts，界面把原文放回写信窗并给出原因。

**SMTP 结果的判定按协议阶段，不按错误文本**：infra 用 nodemailer 的协议跟踪只读取一个事实——客户端已发出 `DATA` 命令（或服务器对它回了 `354`）；之所以以命令发出为界，是因为从那一刻起断线就无法与“已接受、应答丢了”区分。该日志不保存、不记录任何其它内容。`DATA` 之前的任何失败（连接、TLS、认证、MAIL/RCPT 被拒或断线）都是确定未发出；`DATA` 之后若没有服务器应答（断线、超时、TLS 错误文本都算）一律为“结果未知”（`outcome_unknown`，状态 `unknown`，草稿保留，不重试）；服务器给出了应答码（552/5xx/4xx）则是确定的失败。测试覆盖 RCPT 后断线（确定）与 DATA 后断线（未知）。

**窗口内 server 退出（Q16）与优雅关停**：邮件在步骤②已在服务器 Drafts，窗口不读标记也不会发送；重启后没有任何东西会据标记补发。标记只用于如实报告：属主已不存在的 `pending` 报告为 `interrupted`（未发出、已在草稿、不自动补发），`sending` 报告为 `unknown`（窗口已过，可能发出也可能没有，请先查“已发送”，同样不补发）。**优雅关停**：`createServer().close()` 的第一件事（同步）是 `disposeMailSendServices()`：清除所有计时器、置关停守卫（到点触发器与新的发送都直接拒绝）、把仍在窗口内的发送标记为 `interrupted` 并释放 claim——因此关停期间有慢请求或 Copilot run 要等，窗口也不会在这段时间里变成发送；已交给 SMTP 的发送不被打断。只有属主进程会发送；另一个 server 进程只能观察（`ownedElsewhere`），撤销/关闭该发送回 409 `owned_elsewhere`，对同一草稿再发送回 `already_pending`。页面刷新后 `GET /api/mail/compose/outbox` 列出仍需用户注意的发送（窗口内、发送中、failed、interrupted、unknown，以及**尚未被页面确认的近期 sent**，所以用户不在页面时成功发出的邮件，回到 Mail 页也能看到结果），界面据此恢复倒计时或显示结果；用户关闭/确认时 `DELETE …/sends/:sendId` 才忘记该标记（普通的已确认 `sent` 一小时后清扫；带有需告知结果的 `sent`——没有 Sent 副本、有被拒收件人、Drafts 里留有副本——与其它问题一样保留到页面确认，最长 30 天）。内存里的完成记录释放邮件字节并在 10 分钟后淘汰。

**窗口内的草稿被冻结**：对正在发送的 Message-ID，`PUT draft`、`discard`、以草稿模式 `init` 都回 409 `already_pending`（检查在草稿锁内，排在它之前的保存先完成），避免“发出旧版并删掉新编辑”；撤销后恢复可编辑。**已发出的 Message-ID**（sent 守卫期内）`PUT draft` 回 409 `already_sent`，不把已发出的信放回 Drafts（否则又能从那里再发一次）；`discard` 仍允许，用来删掉清理失败时留在 Drafts 的副本；以草稿模式 `init` 打开这样的副本时响应带 `sent: {sentCopy}`（`failed`/null 表示这份副本可能是所发内容的唯一记录）。超过 7 天的 sent 守卫随 outbox 清扫删除。

**为什么标记在全局缓存而不是全局数据，及其代价**（ADR 0007 判断）：进入窗口前最终邮件已在远端 Drafts（远端为权威），所以标记丢了不会丢邮件；它不是用户数据，不需要保全规则，删除账户会连同缓存目录清掉其标记。**代价必须说清：缓存目录被整体删除时，claim 与 sent 守卫文件随之消失，跨进程互斥失效。** 同一进程内仍有内存守卫（claim 与 sent 守卫各一份）；但若此时另一个 server 进程对同一草稿发起发送，两个进程可能各自进入窗口并各发一次（重复发送），重启后的“未发出”提示也会丢（草稿仍在服务器）。这是用户主动删缓存目录且恰好多进程并发发同一草稿时才会遇到的剩余窗口，没有额外加锁。其余已知剩余窗口：①claim 从取得到释放覆盖**“最终版存草稿（APPEND）＋撤销窗口＋SMTP 事务＋Sent 追加与 Drafts 清理”全程**，而它的 10 分钟陈旧期从取得 claim 时算起；这一整段若超过 10 分钟（大附件 APPEND 慢、SMTP 慢、清理慢都算），属主仍活着时另一进程也会把该 claim 当作陈旧而接管。接管发生在 SMTP 接受之后的，会被 sent 守卫拒绝；发生在之前的，同一草稿可能被第二次发送；②三个进程同时判定同一陈旧 claim 并先后删除/创建（仅发生在同刻发送同一草稿且上一属主刚崩溃时）。

**暂存附件**不属于账户目录，因此删除账户**不会**清掉它们；靠 7 天清扫（server 启动时扫一次，暂存新附件时也扫）以及发送成功/放弃草稿时的删除。**前端**：同时可有多条发送各自倒计时与撤销；撤销/SMTP 失败要恢复写信窗时，若用户正在写另一封，不替换它，而是给带“打开”的通知（打开前先把当前稿存到服务器，存不下则保留）；撤销遇 409 先查真实状态再报告；服务器暂时不可达时倒计时归零后显示“正在重新连接，尚不知道是否发出”；离开 Mail 页卸载时先把未存文字存到服务器（正在发放弃请求的窗口除外）；存不下的文字（连同写信窗状态）保存在本标签页的 sessionStorage（`argelander.mail.leftBehind`），每次进入 Mail 都以通知如实说明并提供“打开”恢复，不自动弹出；**显示通知不等于取走**：只有用户点“打开”且写信窗真正接管，或明确关闭该通知并在确认框里确认丢弃后，才从 sessionStorage 删除该条（每条记录带版本：“打开”只删除它接管的那一版，等待期间若迟到附件并入成了新版，新版保留并继续提示；确认丢弃按记录 uid 删除所有版本），因此不点“打开”就离开或刷新，下次仍在；页面挂载时产生的记录也先写入 sessionStorage 再显示。sessionStorage 只属于该浏览器标签页：关闭标签页即消失；浏览器的“复制标签页”或会话恢复可能把它一并带到新标签页（两个标签页都会提示同一段文字）。**发送请求进行中离开** Mail 页：该请求若随后失败（窗口没打开），尽力把原文存进 Drafts，并同样留在本标签页、下次进入时说明“没有发出”（存进了 Drafts 或没能存进）；若请求没有应答，只说“不知道是否正在发送”，绝不说“没有发出”。**附件上传按发起它的写信窗 uid 回写**：上传未完成时关闭写信窗不关闭并提示“仍在上传”；上传中放弃草稿，完成后删除该暂存附件（从确认放弃起，包括等待在途保存期间，离开 Mail 页都不补存该窗口）；上传中离开 Mail 页，完成后**不再写服务器**——服务器上的草稿可能已在别处（回到 Mail 后、另一个标签页）改过，又没有版本检查，用离开时的旧快照加附件去 PUT 会覆盖较新的文字；所以若该窗口的文字本来就只留在本标签页（离开时没存成），附件并入那条记录，否则删除暂存附件并留下通知“没有加入，请从草稿箱重新添加”；其它情况窗口已不在时删除暂存附件并通知“没有加入任何邮件”——永远不会落到另一封信里。**已发出的信**（发送时得知已发出、保存回 `already_sent`、或打开的是已发出信在 Drafts 的残留副本）：写信窗显示“已经发出，不能再发送或保存”并提供“复制为新邮件”（新 Message-ID，保留文字；附件只有从 Drafts 残留副本重新暂存的才带上，发送后服务器已删掉的暂存附件不带，并在窗内提示需重新添加），发送禁用、不再自动保存；关闭不受阻拦，之后的修改记入本标签页（与离开时一样，关闭其通知需确认）并以“作为新邮件打开”提供；离开 Mail 页时这些修改只记一次（不尝试保存）；放弃时说明“已发送”中是否有副本，没有或不知道时以 danger 明确警告这份可能是唯一记录。草稿保存的结果同样只回写发起保存的窗口；放弃草稿先等在途的保存结束，再按其结果决定是否向服务器发放弃请求（保存应答丢失也发）。**发送应答丢失**（网络错误，请求可能已到服务器）时，其 `sendId` 绑定在该写信窗上，并在弄清之前锁定发件人（claim 与 sent 守卫只在同一账户内成立）；再次发送前先查它的状态：在窗口内或正在发送就并入它（内容已改则提示之后的修改不在其中，可撤销后再改），已发出则不再发送并在窗内说明，结果未知（含 `failed` 且 `outcome_unknown`）则报告且本次不发，其余 failed/interrupted/cancelled 才继续，服务器查无此发送（404）也继续——此时旧请求若仍在准备，它持有 claim，新的 `sendId` 只会得到 `already_pending`；状态查不到（仍不可达）则不发送。内容未变的重试仍复用同一 `sendId`。倒计时、撤销应答和状态查询可能先后结束同一次发送，结果只报告一次。写信窗按“有无服务器没有的改动”判定能否关闭：保存后再输入的改动、被取消的延迟保存都算；发送请求进行中窗口被锁定（不可关闭/编辑/换发件人，“打开”恢复入口无效），发送结果只回写发起它的那个写信窗（按窗口 uid），其窗口已不在则以通知＋“打开”恢复；任何新窗口（含回复/转发的初始内容）遇到已打开的写信窗时都只以通知提供。附件大小提示只对有已知服务商上限的预设显示（Gmail 25 MB、iCloud 20 MB）；自定义无已知上限，不显示大小警告，只有服务器的拒绝才会让发送失败（草稿保留）。离开 Mail 页面不会取消服务器端的发送，也无法再撤销；回到 Mail 页时由 outbox 列表显示结果或中断警告。**已知限制（多标签页）**：两个浏览器标签页（或两个工作台进程的页面）同时编辑同一封草稿（同一 Message-ID）不受支持：自动保存互相覆盖，后存者胜，另一页的修改被替换而没有提示；两边同刻发送由 claim 拦下（`already_pending`），一边发出后另一边再发或再存由 sent 守卫拦下（`already_sent`，7 天内；缓存被删后只剩各进程内的副本）；“留在本标签页”的文字只在离开时的那个标签页里。
**Mail 的 Copilot 工具与页面上下文**（Mail 票 09，ADR 0005 / 0008；contracts `mail-ops.ts` 与 `copilot.ts` 的三张确认卡，infra `MailOutgoing.findDraft`，server `copilot-mail-tool.ts`〔`mail` 工具〕/`mail-copilot.ts`〔对同一批 Mail 服务的纯函数封装〕/`mail-compose.ts` 的 `draftSnapshot`，web `src/copilot/MailConfirmation.tsx`、`src/mail/mail-context.ts`）：**能力**——读：`accounts`/`folders`/`list`/`search`/`read`（用 `unread:false` 打开，**不标已读**，正文最多 6 万字符一段，`from` 续读）/`read_draft`；附件只在被点名时读：`read_attachment`（文本文件原文，或 PDF 的逐页真实文字，一次最多 10 页且受字符预算限制，`nextPage` 续读，无文字层的页列入 `imageOnlyPages`）与 `read_attachment_page_image`（PDF 单页 PNG，只给能看图的模型，沿用 Reader 的单图/总图/窗口三条容量规则）；写草稿：`create_draft`（新建/回复/全部回复/转发，初始内容与线程头由同一个 `init` 生成，模型文字写在引用之上）与 `update_draft`（须带上一次读到的 `expectedDigest`，草稿被别处改过则 409 拒绝）——草稿只落在服务器 Drafts，不外发；**只能请求**：`send`/`delete`/`move`，参数里没有任何 confirm/approve 键（TypeBox `additionalProperties:false` 与 zod `.strict()` 双重拒绝，伪造键根本到不了工具），工具只拿到用户的裁决，拿不到确认 id，也没有回答的途径。**确认卡**（复用票 11 的确认机制：先写 `requested` 记录，再显示卡，点击后写 `resolved`，然后才执行；写入前再记 `begin`，结果未明由 journal 报告为 `unknown`）：`send_mail` 显示发件账户、To/Cc/Bcc、主题、**正文全文**、附件名与大小；`delete_mail`/`move_mail` 显示那一封邮件（发件人、主题、文件夹）与去向，Trash 内的删除标明永久；全部以纯文本渲染。**卡片与实际发送一致**：卡片字段来自一次 `draftSnapshot`（按 Message-ID 在 Drafts 里找到最新副本，解析出与 UI 编辑草稿相同的 `MailComposeDraft`，并把附件暂存），摘要 `digest` 覆盖所有字段与附件字节的 SHA-256；批准后交给发送服务的是**同一份快照**的 `draft`，不是重新读取的草稿；点击时（`decide`）与发送前（工具内）各用只读快照复核 digest，草稿在卡片显示后被改（改收件人、正文、附件）即 409 `stale` 并让工具报 `expired`，**必须重新请求并重新确认**；复核时服务器读不了是系统错误，如实报告而不是当作“已变化”。快照里的正文是服务器存的形态（MIME 会给非空文本补一个结尾换行，再解析是固定点），卡片显示的、发出的都是它。**发送走票 07 的同一条路**：`MailSendService.start`（claim、最终稿先存 Drafts、8 秒窗口、一次 SMTP、sent 守卫）；`sendId` 是随机 UUID（应用在发送前生成并先记入 journal，不由 operationId 或模型输入派生；同一 operationId 重试时 journal 返回已记录的结果，或对未完成者报告 `unknown` 并给出该 sendId，不会再发一次）。这条发送带 `origin: "copilot"`（marker、状态、sent 守卫记录都有）：Mail 页挂载拉 outbox 时**只接管 `origin` 为 mail（或无该字段）的记录**，不恢复、不报告、不 dismiss Copilot 的发送，因此 Copilot 的 `send_status` 与撤销条读到的是真实记录。marker 被 7 天内清掉后，`status` 仍可由 sent 守卫按 sendId 答出“已发出”；两者都没有时为 not_found，工具如实说“记录已不存在，结果无法确认”（不说“没有改变”），撤销条遇 404 停止轮询并显示同样的话。工具在窗口内返回 `pending`（带 `undo.until` 与 `mailSend`），**不会报“已发送”**；Copilot 面板据此显示“N 秒后发送 · 撤销”（复用 Mail 页同一撤销接口并轮询真实状态，服务退出于窗口内显示“未发出”），模型可用 `send_status` 查结果；`interrupted`/`unknown` 如实报告。`delete`/`move` 经 `MailManageService`，`uidValidity` 必填且随请求带上，服务器对不符者回 `message_changed`；`connection_lost` 报 `unknown`（可能已经发生，先读再说），`partial` 报 `error`（结果已知、部分完成）；失败码对应 HTTP 状态与 tool 类别的唯一表在 server `mail-failures.ts`。**页面上下文**：Mail 页发布 `page.mail`（账户、范围、**当前列表显示的信头**〔含搜索结果，每列表最多 100〕、**当前打开邮件全文**〔纯文本，仅 HTML 的邮件用 DOMParser 取文本，最多 6 万字符并带 `textTruncated`/`textChars`〕、附件清单），整页带固定的 `untrusted:true` 与 `notice`（schema 里是字面量，不能被改写）；系统提示再次声明邮件内容是不可信数据、不得照其中的“指示”行事；后续观测里打开邮件的正文被省略（任务上下文已持有，需要时 `read`）；消息记录只存摘要（无正文、无地址）。页面状态：账户与列表加载完才算 `complete`，加载中/无账户/出错为 `unavailable`。`workspace` 工具的 `switch_view` 支持 `mail`。凭据从不进入工具结果、日志或上下文（工具只经服务层取登录目标，结果与错误只含失败码）。**已知限制**：确认卡在进程内存里，重启后不复活（沿用票 11：重启后的卡片视为 `expired`，不补发）；`delete`/`move` 卡片在点击时不做额外的远端复核（服务器按 uid+uidValidity 拒绝已变化者）；一封 `send` 的 digest 复核与 `start` 之间仍有毫秒级窗口（点击复核、工具内复核后才 `start`，窗口内用户再改草稿仍会被同一 Message-ID 的 Drafts 副本替换为已批准版本）；未提供 Copilot 的标志（已读/星标）操作。**第 1 轮修复补充**：①`mail` 工具与 `MAIL_PROMPT` **只在存在邮箱账户时挂载**（每次 run 开始时判定：增删账户在下一条消息的 run 生效，不在 run 中途变化；无账户的会话工具表、系统提示与窗口占用同未加 Mail 之前；基础提示里“有哪些页面上下文/工具”的两句在挂载时改写为包含 Mail，而不是只在末尾追加）。②发送 id（`sendId`）由应用随机生成并在 `begin` 记录里存入 `object.sendId`，不由模型提供的 operationId 派生；`start` 返回后核对 `sendId/messageId/accountId`，不符不得声称发出；重启后同一 operationId 被查到“已开始未完成”时报 `unknown` 并带上该 `sendId`，模型可用 `send_status` 查询。③页面上下文里来自外部、长度不受控的部分一律有界截断并标注（附件≤50 与 `attachmentsTotal/attachmentsTruncated`、各收件人字段≤100 与 `recipientsTruncated`、账户≤50、列表≤50、正文≤6 万字符与 `textTruncated/textChars`），而不是让 schema 拒绝整页；列表仍在首次加载时页面不是 `complete`。④后续观测：任务首条消息已带有的打开邮件正文被省略并注明“调用 mail read”，任务中途新打开的邮件带有界正文一次（之后同样省略）。⑤确认卡按种类区分“发送/回复/转发”；`create_draft`/`update_draft` 的结果同样标为不可信（草稿可能引用外部正文）。⑥**需用户知悉**：草稿写入不需要确认卡，因此被注入的模型**可以**改动 Drafts 里的草稿内容、收件人与附件；真正的外发保护只在发送卡（用户在卡上看到最终收件人与正文全文才点发送）。

## LaTeX 数据流

隔离 workspace → latexmk（编译事实与插桩事件）＋unified-latex 源码树/有界宏展开 → 融合 IR → 图资产物化 → 直接存储/展示。

印刷编号取编译真值，不从结构 id 猜测；编译失败不做无编译全文降级。PDF/EPS 图片转换采用 pdftocairo/gs，旧 pandoc/mupdf/dvisvgm 路线退役。执行护栏、事实盲区、回退和测试范围见 [tex-pipeline](tex-pipeline.md)。Writer 显式 profile 共享主干但不共享摄入/归档副作用。

## Web 与同步

- `serve` 默认 8000；Hono REST、SPA、images、`/ws`。
- watcher 轮询 library、plans、per-doc current annotations、manuscript JSON 和模板 JSON 指纹；server 自写可再收到 external，前端幂等重取。没有资产目录 watcher。
- JobRunner 串行、持久化；boot 将未完成 job 标 interrupted，不重跑；hello 回放，失败在详情刷新后仍可见；job.done 先于 library.changed。upload、refresh 和 arXiv ingest 生命周期不能与 Discovery 只读请求混淆。
- 文献 label 色板：red重点 / amber待读 / green已精读 / blue方法 / violet灵感；overlay > 持久 label > star 播种。已读标题灰化及“已读”，未读蓝点。
- 阅读中列流式、100ch 上限；顶部可折叠作者块，多引用 per-ref chip；图片尺寸预留与停稳校正。右栏默认引用，可切标注；DOM 不嵌套高亮 span。
- 文献深链接 `/doc/<doc_id>#<anchor>` 使用 sec-N/fig-N/eq-N/tab-N/ref-N 等结构 id，不是印刷编号；标注使用 `#ann-<annotation_id>`。探索链接及历史见 discovery。

## Agent 接入

CLI + 仓库 `skills/argelander-*` 三件套（ingest/query-library/read-paper），无 MCP 是项目选择；本机安装方式不成为跨机器保证。

- search/read/show/ref/note/label/list + 只读 annot，CLI 直读磁盘，不依赖 HTTP。
- 文献问答从项目根走 CLI/skills，不传 `--data-dir`，不读内部 JSON/源码替代文献接口。开发任务不受此源码禁读限制。
- 仓库 CLI：`node packages/app/dist/bin.js`；全局安装后 `argelanderspace`。
- 深链接端口：`ARGELANDERSPACE_PORT` > config `port` > 8000。
- search 空 note 提示只走 stderr，stdout JSONL 保持可 pipe；摄入后每篇询问 note 并给建议稿。输出冻结以 contracts 为准。
